## 职位描述

一、岗位背景
这不是一个“调API搭Demo”的岗位，也不是把SAP/Oracle的现成接口包装一下。
我们是一家⾃研ERP全链条的企业（覆盖⾤购、⽣产、库存、销售、财务、成本、审批等全链路），现在要将智能体能力原生嵌⼊自研ERP系统，让AI真正跑在核心业务链路上，而不是在外围做“聊天机器人”。
这意味着：
· 没有现成的第三方ERP文档可抄，你需要直接对接内部核心研发团队，理解自研表结构、状态机、业务规则。
· 没有标准的SaaS API可调，你需要把自研ERP的能力封装成智能体可用的工具（Function Tools / MCP Server），并保证权限、幂等、审计。
· 失败代价极大：AI的错误输出可能触发错误的采购订单、库存扣减、财务凭证或审批放行。
因此，我们要找的不是只会搭Demo的AI工程师，而是能把自己的智能体代码与自研ERP全链条业务打通的工程实干者。
二、岗位职责
1. 智能体架构与工作流编排（Microsoft Agent Framework + LangGraph）
· 基于 Microsoft Agent Framework (MAF) 构建有状态多Agent系统。MAF是微软2026年正式发布的1.0版本框架，由AutoGen和Semantic Kernel合并而成，Python包通过 pip install agent-framework 安装，要求Python 3.10+。
· 熟练使用MAF的多智能体编排模式：串行（Sequential）、并行（Concurrent）、交接（Handoff）、群组聊天（Group Chat）、Magentic。能根据ERP业务场景选择正确的编排模式，并解释为什么。
· 设计MasterAgent + SubAgent的Fan-out/Fan-in编排架构，确保并发状态合并的正确性与一致性。子Agent内部严格按照：数据提取 → 多维对比 → 偏差计算 → 分级判定 → 递归下钻 → 归因推理 串行执行。
· 利用MAF的内置检查点与恢复机制实现长任务断点续跑，确保跨模块的复杂ERP流程（如跨月成本结转、多级审批）可恢复、可审计。
· 在LangGraph/MAF中定义完整的State结构（含缺失标记、完整度计分、错误明细等），使用 Annotated + 自定义Reducer处理并发写入，防止状态覆盖或数据丢失。
2. 与自研ERP全链条的深度集成（核心差异）
· 深入理解自研ERP的表结构、状态机与业务规则，与ERP核心研发团队协作，将采购、库存、生产、销售、财务、成本等模块能力封装为原子化、幂等的工具接口。
· 构建MCP Server（Model Context Protocol），将自研ERP的内部RPC/消息队列/数据访问层统一暴露给Agent，确保Agent通过标准协议访问ERP能力，而不是绕过业务层直接读写数据库。
· 实现跨模块的副作用管理：当Agent执行“采购订单创建→库存预占→财务挂账→审批流触发”这类多步操作时，通过Saga模式执行补偿动作，保证跨模块数据一致性。
· 处理自研ERP特有的“脏数据”与“边界逻辑”：历史遗留状态、软删除记录、多组织架构隔离、跨期业务回退等，都需要在Agent工具层做适配和兜底。
· 权限与组织架构的深度对接：Agent必须以真实用户身份执行操作，复用自研ERP的权限体系（功能权限、数据权限、字段权限、审批权限），不得绕开或硬编码。
3. 幻觉治理与事实一致性
· 基于自研ERP业务数据（关系库、图数据库、RAG）构建生成层的事实约束机制，坚持“规则能做的不用模型”原则，将数值计算、阈值判定、编码消歧等确定性逻辑下沉至规则引擎和工具调用。
· 设计claim拆解与证据对齐流程：将Agent输出拆解为原子事实，逐条验证是否被上游数据源支持。引用字段名和值必须真实存在于工具返回结果中，引用不存在的直接判为幻觉。
· 处理多源数据冲突（如图谱结构化数据与RAG文本语义冲突），定义冲突消解策略并在报告中标注不确定性。
· 实现LLM输出的结构化约束（Pydantic BaseModel强校验），确保输出中绑定可溯源的 data_sources 数组。
· 建立幻觉的分层检测与降级机制：结构化校验→引用核验→语义一致性检查→人工兜底，按风险等级逐层拦截。
4. 工具调用与副作用管理
· 利用MAF的 Middleware 能力拦截、记录或修改Agent在工具调用前后的行为，实现统一的权限校验、日志审计和副作用拦截。
· 将自研ERP业务能力封装为原子化、幂等的工具接口，每个写操作必须带业务去重键（单据号+动作类型+业务日期），下游必须认幂等键。
· 通过MAF的 Function Tools 机制注册工具，利用框架自动生成工具Schema，同时确保参数校验的完备性。
· 实现工具调用的权限校验：身份、组织、字段、状态四层权限在服务端校验，Agent不得通过生成新幂等键绕过约束。
· 处理工具失败的分类降级：超时/限流/5xx/参数错误/业务错误分别采取重试、退避、熔断、参数修复、权限升级、人工接管等不同策略。
5. 评测与可观测
· 利用MAF内置的遥测（Telemetry）能力追踪Agent执行链路，并与自研ERP的日志/监控体系打通。
· 构建离线评测集（按ERP业务维度分层，覆盖正常/异常/数据缺失/幻觉触发等场景），追踪偏差识别准确率、归因与专家一致性等指标。
· 建立线上监控与Trace回放机制：记录每个节点的模型IO、工具IO、状态变更、版本号，支持失败Case的完整回放与归因。
· 设计回归测试流程：每次Prompt/模型/工具Schema变更后，自动跑回归集，针对薄弱环节（如单位换算、编码映射等）动态补充Few-shot样例。
· 实现LLM-as-Judge的自动化评估，但必须有校准机制（人工标注交叉验证），避免评估器自身的偏差放大。
6. 人机协同与安全兜底
· 按风险等级设计人机分工：低风险结论由规则引擎直接输出；中风险进入LLM归因节点；高风险结论必须经人工确认后方可生效。
· 实现阈值拦截机制：偏差在阈值内直接输出，超阈值触发递归下钻；关键数据缺失时返回“数据不足无法审查”，不强行出结论。
· 设计人工确认的超时策略：审批超时默认拒绝，高风险动作必须留痕可追溯。
三、任职要求
硬性技术能力

5. 有RAG系统的完整落地经验：混合检索、重排、查询改写、多跳召回、引用对齐。能讲清楚RAG的失效模式及对应解法。
6. 有工具调用（Function Calling）的生产化经验：工具Schema设计、参数校验、幂等实现、失败分类处理、权限控制。
7. 熟悉至少一种图数据库（Neo4j等）及其在Agent中的检索应用场景（多跳查询、实体消歧、关系推理）。

工程化能力（这是区分Demo选手和真做过的人的关键）
1. 状态管理能力：能解释清楚MAF的Workflow中状态如何在Executors之间传递和合并，能写出自定义合并逻辑的实际代码（不是伪代码）。在LangGraph中，能写出自定义Reducer的实际代码，知道并发写入时如何处理去重、折叠、累加、覆盖的语义选择。
2. 容错与降级能力：当某个数据源超时时，Agent不中断整条链路，而是标记数据缺失、扣除完整度分数、继续执行其他查询，最终在报告中标注“建议人工补充核实”。关键数据缺失过多时直接返回“数据不足”。能利用MAF的检查点机制实现失败恢复。
3. 跨模块事务一致性：理解自研ERP中跨模块操作（采购→库存→财务）的副作用链路，能设计Saga补偿机制，保证Agent执行失败时不会留下半吊子数据。
4. 评测闭环能力：能设计离线评测集、定义过程指标（工具准确率、步骤效率、人工接管率、幻觉率），知道如何用LLM-as-Judge但保持对评估器偏差的警惕。
5. 成本与延迟意识：知道逐条语义验证很贵，能设计级联验证（规则先过滤，高风险才上重验证），能讲清模型路由、缓存、批处理的权衡。
软性能力
· 能说清楚“什么时候不该用Agent”——确定性高、安全关键、成本敏感的场景，应该用工作流/规则/小模型。
· 有线上踩坑经验：能讲出至少一个真实的生产事故，以及从发现到修复的完整闭环。
· 不迷信多Agent架构：知道多Agent只在任务可并行、角色独立、通信开销低时才优于单Agent。
· 对幻觉有清醒的认知：承认幻觉不能根治，只能按风险分级控制。
