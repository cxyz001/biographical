# 机器人与硬件设计零基础到项目实战

> 基于[机器人与智能硬件](10-机器人与智能硬件.md)与[硬件工程师与充电桩硬件设计](11-硬件工程师与充电桩硬件设计.md)。GitHub 检索日期：2026-10-23。配套代码与资料记录：[robot-hardware-learning](robot-hardware-learning/README.md)。

这份教程有两条路线：机器人侧学习感知、坐标、运动与通信；硬件侧学习电路、电源、PCB、计量、保护与量产。先学第 1—7 章共同基础，之后按目标选择章节，再通过项目把两者连接起来。不会要求初学者一开始同时掌握 ROS、DDR、机械臂和充电桩认证。

练习分三级：本机离线计算、成熟工具仿真、受控实物验证。市电、充电主回路、漏电/耐压、带载电机和机械运动实验采用团队批准的设备与测试流程；这里提供原理和项目组织方法，不提供可直接投入使用的高压接线方案或安全认证结论。

## 1. 先建立系统观：软件指令怎样变成物理动作

机器人不是“接上 AI 的电机”，充电桩也不是“联网的插座”。一个完整产品要管理能量、测量物理量、判断状态、执行动作并发现失败。

```text
业务目标/人机界面 → 任务与状态机 → 规划与控制 → 通信/驱动 → 执行机构
                          ↑                         ↓
                    状态反馈 ← 校准与时间对齐 ← 传感器/采样

底层支撑：电源、时钟、复位、连接器、结构、散热与可测试性
独立约束：风险分析与所需保护功能，不依赖云端/AI始终在线
```

同一条“执行成功”消息可能只说明命令发送成功，并不说明电机转到目标或触点实际断开。接口需要区分接收、接受、执行中、完成、超时与故障。

**练习**：分别画出差速小车和交流桩的能量流、信息流与故障反馈。完成标准：能指出电源断开、传感器失效、上位机卡死各影响什么，不把所有问题归结为程序异常。

## 2. 单位、误差与基础数学：先让数字有物理含义

区分位置 m、速度 m/s、加速度 m/s²、角速度 rad/s、力矩 N·m、功率 W 与电量 Wh。弧度和角度不能混用；编码器计数到位移需考虑每转计数、减速比、轮径和计数方式。

电压是电势差，电流是电荷流动率，电阻在适用条件下满足 U=IR。直流功率常用 P=UI；交流有功功率需要电压电流波形与相位信息。三相公式 `P≈√3×线电压×线电流×功率因数` 需要对应平衡等假设，不能据此直接选保护器件。

误差包含系统偏差、随机变化和分辨率限制。测到 3.300V 不意味着真值精确到 1mV，量程、准确度、探头、接线和环境都会影响结论。校准是建立测量与参考之间的关系，不能只改一个软件系数让屏幕“看起来正确”。

**练习**：计算 1000W 连续一小时是多少 Wh/kWh，再算 5V、0.4A 负载功率。每个输入都注明单位和测量来源。

## 3. 传感器、执行器与采样：真实信号不是理想数字

传感器把温度、位置、力、电流等变成电信号，ADC 再量化。先确认量程、带宽、接口、采样率、噪声与延迟。12bit ADC 有 4096 个码级，但有效精度并不自动等于 12bit，参考源与前端噪声会影响结果。

奈奎斯特条件不是“采样率大于两倍就万事大吉”：采样前抗混叠、滤波器过渡带、相位延迟和信号本身都要考虑。数字平滑可以减少噪声，也会增加控制反馈延迟。

电机、继电器、接触器和电磁阀不是 MCU 引脚直接输出就能驱动的负载，需要合适的功率级、驱动与反馈。关断感性负载会产生瞬态，器件和抑制方式需结合动作速度、能量与寿命选型。

**验收**：为一个传感器列输入物理量、输出电气量、失效模式、采样间隔与总延迟；对开路、短路、饱和和“值不再变化”分别定义如何检测。

## 4. MCU、SoC 与上位机：按时限和故障边界分工

MCU 常承接采样、定时、执行与局部状态，SoC/Linux 承接界面、视觉、网络与记录。核心板可减少 DDR/电源设计风险，但载板仍需满足供电、接口、热与结构约束。

```text
平台/界面：任务、日志、权限、远程维护、AI结果
    ↕ 有版本、有序号、有时效的通信协议
SoC/边缘层：感知、导航/规划、媒体、缓存
    ↕ 本地执行接口与超时约束
MCU/驱动器：采样、周期控制、局部故障处理
    ↕ 电路/总线
传感器、驱动功率级、执行机构
```

这种职责分层不一定要求每层一块物理板，是否隔核、隔进程或使用独立控制器取决于时限、风险与资源分析。不能把“使用 PREEMPT_RT”当作硬实时或功能安全自动成立的证明。

**练习**：给每个功能写最迟响应时间、最坏执行时间预算、资源与超时状态。将 UI、磁盘写入和模型推理移出有严格时限的控制调用路径。

## 5. C/C++、Python 与工程环境：先做可复现程序

C/C++ 用于驱动、控制与高性能节点；Python 用于工具、原型、数据与测试。先掌握整数范围、浮点、结构体、字节序、资源生命周期、并发与构建。不能把 Python 原型的平均耗时当作 C++ 控制器的最坏时限保证。

版本清单至少包含 OS、编译器、ROS 发行版、中间件、驱动、固件、板卡、模型和配置。ROS、Gazebo、Nav2、MoveIt 与 ros2_control 要按发行版兼容矩阵选择，不能把各仓库默认分支任意混装。

推荐先用一个仍受维护且依赖兼容的固定 ROS 发行版。本文读取部分 Humble 文档作为稳定概念来源，不声称它在未来任意时点都是新项目最佳选择；rolling 适合追踪变化，初学项目通常更应追求可复现。

```bash
# 仓库根目录；Python 3.9+，不需要开发板
python JD/robot-hardware-learning/lab.py kinematics
python JD/robot-hardware-learning/lab.py energy
python JD/robot-hardware-learning/lab.py budget
python JD/robot-hardware-learning/lab.py audit
python -m unittest discover -s JD/robot-hardware-learning -p test_lab.py -v
```

## 6. 通信：协议、物理层和应用语义要分开

RS485 是电气层，Modbus 是协议；CAN 定义总线机制，CANopen 等定义更上层设备模型；EtherCAT 具有自己的过程数据、状态机和同步机制。只知道波特率不够，双方还要约定单位、字节序、缩放、更新周期和错误含义。

| 接口 | 要学习的原理 | 首个实验 |
|---|---|---|
| UART/RS485 | 帧、方向、终端、偏置、电平与共模 | 回环/模拟从站，不先接现场网络 |
| CAN | 仲裁、过滤、错误计数与 bus-off | Linux vcan + can-utils |
| Modbus | RTU/TCP、寄存器、异常响应 | Pymodbus 本机服务/客户端 |
| EtherCAT | PDO/SDO、状态机、WKC、DC | 阅读 SOEM，先用认可测试设备 |

经典 CAN 数据场最多 8 字节，CAN FD 有不同的数据长度与速率机制，不能统称 CAN 每帧只有 8 字节。CAN ID 也不是设备地址的通用同义词，含义由上层协议决定。

报文校验要遵循所在层：CAN 有自身校验，Modbus RTU 有 CRC，Modbus TCP 使用其协议结构和 TCP，不能给所有协议随意追加自定义 CRC。应用序号、时效和幂等仍需单独设计。

## 7. 通信实验与超时：收到数据还不等于数据新鲜

[can-utils][G10] 包含 candump/cansend 等工具。以下为 Linux、已安装工具且具备建虚拟接口权限的隔离实验，未在当前 Windows 主机运行：

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up
candump vcan0
# 另一终端发送；此报文仅是任意测试字节，不映射真实设备动作
cansend vcan0 123#11223344
# 完成后先停止 candump，再清理自己创建的接口
sudo ip link delete vcan0
```

[Pymodbus][G11] 应按所选版本 examples 运行本机模拟端。寄存器地址在手册与库 API 中可能有 1 基/0 基差异，多寄存器浮点的字节和字顺序也需核对。

通信状态应包含最近有效数据时间、序号、错误计数和连接状态。心跳存在不证明传感器新鲜，也不证明执行器已动作。超时后保持最后值还是停止、制动或去能，必须由设备风险与工况决定，不存在通用“保留最后安全值”。

**验收**：测试超时、重复、乱序、重启后序号归零、格式损坏与重新连接。动作命令恢复后不应自动执行已经过期的任务。

## 8. ROS 2：Topic、Service、Action 和 QoS

Topic 适合持续数据，Service 适合短请求响应，Action 适合带反馈和取消的长任务。参数管理配置，launch 管启动组合，lifecycle 节点用于受控配置/激活等过程。ROS 2 是中间件和工具生态，不是电机控制或安全认证的替代品。

[QoS 官方文档][G2] 解释 reliability、history/depth、durability、deadline、lifespan 与 liveliness。发布订阅双方 QoS 不兼容时，即使都存在也可能收不到消息。reliable 不等于无限期保证按时到达，best effort 也不代表数据没有价值。

```bash
# 已安装并 source 对应 ROS 发行版环境后，在不同终端执行
ros2 run demo_nodes_cpp talker
ros2 run demo_nodes_py listener
ros2 topic list
ros2 topic info /chatter --verbose
ros2 topic echo /chatter
```

**练习**：用官方示例改变消息频率与 QoS，观察缓存、丢失和兼容性；明确传感器数据更关注新鲜性还是完整性。ROS1 TCPROS 使用 TCP，不能简单写成“丢包时不可靠”，真正要分析的是恢复、排队、时限和系统故障模型。

## 9. 坐标与 tf2：位置必须回答“相对于谁、在何时”

一个点 `(1,0,0)` 只有在明确坐标系和单位后才有意义。机器人常使用 `map → odom → base_link → sensor`：map 表示全局参考，odom 通常连续但会漂移，base_link 固连机体，传感器有固定或动态外参。

刚体变换可写作 `p_A = R_AB × p_B + t_AB`。旋转矩阵、四元数和欧拉角是不同表示；四元数需规范化，不能像普通数值那样随意逐分量插值。先画坐标轴，再验证变换方向，不靠反复取逆试到“看着对”。

[tf2 入门][G3] 用 turtlesim 展示 broadcaster/listener，并提供检查坐标工具：

```bash
ros2 run tf2_ros tf2_echo world turtle1
ros2 run tf2_tools view_frames
```

需先按官方教程运行对应 demo；不是在空 ROS 环境直接就有这些 frame。检测耗时、传感器曝光时间和机器人运动会造成时间偏差，应按采集时刻查询变换并处理缺失/过期。固定减去“50ms”不是通用运动补偿。

**验收**：有坐标约定、标定数据、时间源与单位；移动机器人后观察变换方向；断开某传感器时能识别 TF 缺失而非继续使用旧姿态。

## 10. 差速运动学：从车体速度到左右轮速度

理想无侧滑、轮半径 r、轮距 L、车体前向速度 v、偏航角速度 ω 时：`ω_left=(v-ωL/2)/r`，`ω_right=(v+ωL/2)/r`。左右轮正方向、坐标轴约定和驱动器单位必须先定义。

```python
from lab import differential_wheels
left, right = differential_wheels(0.2, 0.5, 0.05, 0.3)
print(left, right)  # 约 2.5、5.5 rad/s
```

在配套目录运行片段或使用第 5 章 CLI。本例仅做理想运动学转换，没有动力学、摩擦、延迟、饱和、碰撞或安全约束，不能直接向电机发送结果。真实移动与物理仿真使用成熟机器人框架和仿真器，不在这里手写不完整物理引擎。

轮径误差、轮距误差和打滑导致里程计漂移；编码器不是绝对全局定位。先记录直行距离、原地旋转和闭合路径误差，再讨论融合算法，不能指望增加滤波器就自动消除建模错误。

## 11. 控制原理：PID、前馈、饱和与轨迹

反馈控制根据目标与测量差异修正输出。P 对当前误差反应，I 累积误差，D 反映变化趋势；离散实现必须带实际采样周期。积分遇到执行器限幅可能持续累积，需要 anti-windup；微分放大噪声，对测量微分与滤波有各自代价。

位置、速度、电流串级控制常见，但带宽比例不能机械套固定 5—10 倍。带宽、共振、采样延迟和驱动器内部控制都要一起分析。跟随误差也不一定随速度线性增长，异常应按定义的停机策略处理，不能统一规定“降速而非硬停”。

轨迹规划限制速度、加速度和 jerk。梯形速度存在加速度跳变，S 曲线可以改善部分激励问题，但不代表所有系统都必须先做 S 曲线再调 PID。先验证系统模型、驱动器和反馈方向，再使用经过审查的整定流程，不在带载机构上盲目寻找临界振荡。

[Ruckig][G8] 提供受速度、加速度与 jerk 约束的在线轨迹生成，可从上游 examples 做离线 state-to-state 实验。注意社区版中间 waypoint 路径可能涉及云 API，与本机实时 state-to-state 功能边界不同；按固定版本和许可证核查，不能把所有 API 都放进实时环。

配套 [trajectory_demo.py](robot-hardware-learning/trajectory_demo.py) 使用 Ruckig 生成一维离线轨迹，输出位置、速度和加速度。先在独立虚拟环境安装与当前 Python/平台兼容的 ruckig，记录安装版本；程序没有硬件接口，也没有按真实墙上时钟运行控制周期。

```bash
python -m venv .venv-robot
# 按操作系统激活虚拟环境后执行；如无wheel可能需要编译工具
python -m pip install ruckig
python JD/robot-hardware-learning/trajectory_demo.py
```

目标位移取 1 个位置单位，若约定为米，则速度、加速度和 jerk 分别使用 m/s、m/s²、m/s³。检查末端位置、限值和有限差分变化；库版本依赖与本实验尚未在本机执行，不能把输出直接接电机。

**验收**：记录目标、测量、输出、饱和、周期与故障，比较超调、稳定时间、误差与抖动。先在成熟仿真/测试平台验证，再走批准的实物步骤。

## 12. ROS 控制、Nav2 与 MoveIt：三类问题不要混用

[ros2_control][G4] 组织控制器、硬件接口与资源管理；[Nav2][G5] 面向移动机器人导航；[MoveIt 2][G6] 面向机械臂运动规划与操作。它们相互协作，但不是可互换的软件包。

```text
移动机器人：地图/定位 → Nav2规划与行为 → 速度目标 → 底盘控制 → 轮子
机械臂：目标位姿 → MoveIt规划/碰撞检查 → 关节轨迹 → 轨迹控制器 → 关节
共同接口：机器人描述、坐标、状态反馈、限制、硬件抽象与时间
```

先读官方 README 的发行版与教程入口，再使用匹配版本的演示机器人。URDF/xacro 描述 link/joint 与几何、惯量等；可视几何与碰撞几何不一定相同。错误质量、惯量或关节限制会让仿真与规划得出无意义结果。

**练习**：在 mock/fake hardware 中加载控制器、读取关节状态并发送测试轨迹，不连接真实驱动；导航选择官方仿真场景先完成定位、目标、取消和失败恢复。验收不仅是画面中机器人动了，还包括状态与约束正确。

## 13. Gazebo、SLAM 与感知：仿真成功后还缺什么

[Gazebo Sim][G7] 提供成熟物理、传感器与可视化框架。选择与 ROS 集成包兼容的版本，不把 Gazebo Classic 和新 Gazebo 的安装、命令、插件混为一谈。`gz-sim9` 是本次阅读分支，不是对所有 ROS 项目的安装推荐。

SLAM 同时估计轨迹与地图，定位在已有地图中估计姿态，导航还需规划、控制与障碍处理。IMU、轮速与雷达融合要处理坐标、时间、偏置、噪声与外参；EKF 参数不该随便抄，协方差描述应与实际误差有关。

视觉流程通常包含内参/畸变、外参/手眼标定、检测/特征、位姿解算与坐标变换。2D 检测框不直接等于可抓取的 3D 位姿，需深度、几何与可达性分析。标定用独立验证点和重复姿态测试，不能只用拟合数据评价精度。

**验收**：加入传感器延迟、噪声、遮挡与丢失；记录失败场景；硬件上还需验证摩擦、光照、温漂、振动与遮挡。仿真不能代替电气保护或机械风险验证。

## 14. 实时与故障处理：关心最坏情况，不只平均频率

周期 1ms 与“每秒平均跑 1000 次”不是同一回事。测量唤醒抖动、执行时间、截止期超限次数和最大值，并给定测试负载、时长与硬件。UI 卡住时控制继续执行，也不代表整个系统安全。

预分配、避免缺页、限制锁等待、异步记录、适当线程调度和核亲和性都可能有帮助，但需实测。IRQ 优先级在不同内核模型中不同，不能笼统规定所有控制线程都“低于硬件中断、高于所有通信”。无锁也不自动等于有界时延。

看门狗要验证被监视的任务确实完成关键工作，不能由无关线程不断喂狗掩盖故障。超时、过温、编码器异常和限位的响应都由风险分析定义。急停、STO 等安全功能与普通 ROS Topic/软件按钮不能等同，具体结构和等级由专业设计验证。

**练习**：写故障矩阵：触发条件、检测来源、允许响应时间、动作、人工复位条件、证据。防止网络恢复或节点重启后自动恢复危险动作。

## 15. 电路基础：数据手册怎样读

读芯片资料按功能、推荐工作条件、绝对最大值、时序、参考设计、布局与勘误顺序。绝对最大值是避免损坏的边界，不是正常运行指标。输入信号高于未上电芯片供电时，可能通过保护路径反向供电。

电阻要看容差、功率、温漂和脉冲能力；电容要看直流偏压、ESR、温度与寿命；电感要看饱和、电流与损耗；MOSFET 需看实际 Vgs 下的导通电阻、栅电荷和安全工作区，不能只看阈值电压。

数字信号既有逻辑电平，也有边沿、负载和时序。3.3V 与 5V 接口是否兼容需按发送输出与接收阈值/耐压核对，不能凭名称猜。模拟前端还需输入阻抗、共模范围、偏置与抗混叠设计。

**练习**：选两款低压温度传感器，逐项写供电、范围、精度、接口、上电与失效状态，附数据手册页码；缺失项标待确认，不用 AI 推测填满。

## 16. 电源、热与预算：从负载倒推供电

供电方案先列每路稳态、峰值、启动与同时工作情况，再选转换结构与器件。无线发射和处理器负载突变可能使电压下降，平均电流足够不保证瞬态足够。LDO 损耗近似 `(Vin-Vout)×I`；开关电源还需效率曲线和负载条件。

```bash
python JD/robot-hardware-learning/lab.py budget
```

例中 5V×0.4A 与 3.3V×0.2A 合计 2.66W，假设同一转换级效率 90%，输入约 2.956W、损耗约 0.296W。真实系统常有多级转换，应逐级计算，不能把一个效率套所有电源。这个计算不决定线径、保险丝或安全器件。

热阻公式可帮助理解温升，但 PCB、外壳、风、安装方向和器件相互加热会改变结果。设计预算后用规定工况实测温度与余量；不能统一加 20% 就认为所有风险已覆盖。

**验收**：电源树、负载表、启动/关断顺序、瞬态与温度记录齐全，异常掉电的状态和数据保存策略明确。

## 17. 原理图与 KiCad：从低压传感板练手

[KiCad 文档仓库][G13] 是开源 EDA 阅读入口，具体操作选已安装版本对应的稳定手册。JD 中的 AD/Cadence/PADS 可承担类似工作，学习重点是设计规则与审查，不是只记快捷键。

第一个板卡可采用成熟低压开发板/模块接口、数字温度传感器、指示灯与调试连接器。先画功能框图与连接器定义，列网名、电平、方向、保护和测试点，再建立原理图。器件符号、封装与实际引脚逐项校对。

```text
需求/接口表 → 器件资料与选型 → 原理图/封装核查 → ERC
     → 叠层与规则 → 布局/布线 → DRC/人工审查
     → 制造/装配资料 → 样机测量 → 问题闭环与版本发布
```

ERC/DRC 检查规则一致性，不能证明电路功能、EMC 或安全正确。通过检查后仍要人工审查电源、复位、接口、去耦、回流、测试与结构。生成 BOM、Gerber/钻孔、坐标与装配资料，并记录工具和板卡版本。

**验收**：让另一人只看资料就能核查连接器与器件方向；制造前输出只读基线，不让“手动改的最终最终版”成为唯一记录。

## 18. PCB 原理：回流路径比“线连上了”更重要

电流要形成回路，高频返回路径与参考面关系密切。跨参考面裂缝会改变回流和辐射，不能把到处割地当作降噪万能方法。模拟/数字区域的布局、供电和参考关系应结合完整电流路径分析。

高速信号受边沿速度、传输长度、阻抗、过孔与连接器影响，不只看时钟频率。DDR 还需厂商拓扑、时序、偏斜、电源、训练与 SI/PI 约束；全部等长也不能证明可用。初学载板优先采用受支持核心板并遵守载板指南。

电源走线载流能力取决于铜厚、温升、层位、散热与环境，安全间隙/爬电还与绝缘体系、污染、海拔和标准相关。不要从 GitHub 某块板抄一个毫米数应用于市电产品。

**练习**：在低压板上标出关键电流回路、旁路电容路径与连续参考面，检查连接器和测试点。记录每项设计规则的来源，而非仅保存“DRC 通过”。

## 19. SPICE、仪器与 Bring Up：模型与测量相互校验

[ngspice][G14] 是成熟电路仿真器，适合学习 RC、放大、瞬态与工作点，不自行实现一个近似电路求解器。以下低压 RC 网表可保存为练习文件，安装 ngspice 后仿真；本次未在本机执行：

仓库已提供[rc.cir](robot-hardware-learning/rc.cir)，可运行 `ngspice -b JD/robot-hardware-learning/rc.cir`，再检查输出波形数据。

```spice
RC learning circuit, ideal low-voltage model
V1 in 0 PULSE(0 3.3 1m 1u 1u 10m 20m)
R1 in out 10k
C1 out 0 100n
.tran 10u 40m
.control
run
print v(out)
.endc
.end
```

理想 RC 时间常数为 1ms，阶跃约一个时间常数达到变化量的 63.2%。模型没有包含输入保护、寄生、容差、温漂和仪器加载；实测与理想仿真不同应先检查假设。

Bring Up 先核查外观与短路，再按批准方案逐步验证供电、复位、时钟、启动和接口。低压板在适用额定和正确接线下使用限流供电；高压/大功率测量转入具备条件的流程，不断开示波器保护地规避测量问题。

**记录**：板号、BOM、固件、环境、仪器/探头、接线、量程、负载、原始波形与复现步骤。更换芯片后现象消失不自动等于找到根因。

## 20. 计量：功率、电量与校准链路

有功功率来自对电压电流乘积的适当采样与平均；非理想交流不能只用 Vrms×Irms 当有功功率。计量芯片之外还有传感器、相位、滤波、基准、温漂、PCB 与软件单位链路。

电量是功率对时间积分。配套代码对有序功率样本做梯形积分：

```bash
python JD/robot-hardware-learning/lab.py energy
```

输出 1000Wh，即 1kWh。输入是已经测得的有功功率 W 与秒，不是电流；代码用 Decimal 保存十进制计算，不模拟认证电表。缺样、长时间缺口、负功率/双向能量和计量累计寄存器回绕需要业务专门处理，本例仅处理非负功率。

校准要用可追溯参考设备和规定工况，保留参数版本与完整性。内部趋势统计和用于结算的法定计量要求不同，开源库算出合理数字不等于满足计量法规。

**验收**：单位、倍率、时间、相位与累计规则明确；不同负载点和温度条件有误差记录；断电与恢复不会无声重置结算记录。

## 21. 交流充电桩：能量边界与 CP/PP

交流桩主要提供受控供电与连接控制，车载充电机完成主要 AC/DC 转换；直流桩的功率转换、输出与控制边界不同。7kW/22kW 是产品额定场景，不是复制一个控制板就能实现的保证。

CP 参与连接状态与允许供电能力等交互；PP 在适用连接体系中承担连接/线缆能力相关识别。其波形、阻值、状态与 PWM 语义依接口标准和版本确定，不能把一张网上参数表当通用设计规范。OCPP 是后台协议，不是 CP/PP 电气接口。

```text
云/后台（OCPP） ↔ 联网/业务处理器
                       ↕ 受控接口与状态
                  本地充电控制
                       ↕
连接状态/计量/温度/保护反馈 → 主回路执行与反馈 → 车辆接口

电气保护、接地、隔离与失效处理按系统风险及适用规范独立设计验证
```

模型状态可包含不可用、空闲、已连接、准备、供电、停止、故障，但命名不是标准完整状态机。真正实现必须覆盖所有前置条件、超时、传感器故障、控制器复位和执行器反馈；不能把“软件发出闭合命令”当触点已经正常工作。

## 22. 开源充电软件：EVerest、OCPP 与 OpenEVSE

[EVerest 当前仓库][G16] 提供模块化充电软件框架，涉及本地控制协作、协议与后台集成。已读取的旧 [libocpp README][G17] 明确标记归档并迁移到 EVerest 单体仓库；新项目应从当前仓库 `lib/everest/ocpp` 等有效入口查版本，不把归档仓库当活跃维护源。

OCPP 1.6、2.0.1、2.1 在消息、功能和实现支持上不同，不能仅看到 README 列出版本就认为所有功能均完整或你的整机已认证。ISO 15118、IEC 61851 与 OCPP 分属不同接口/层次，按目标车型、接口和市场选择。

[OpenEVSE][G18] 展示本地控制器、网关与 Web 界面的职责划分，适合阅读架构和故障边界。README 的部分功能状态表述也可能随版本不同，应查实际发行版与测试；硬件与软件许可证分别核对。开源项目不能自动覆盖中国、欧洲和美国所有标准或具体安装条件。

**仿真练习**：按固定 EVerest 版本官方指南启动纯软件示例，连接本地测试后台，验证启动、授权、状态、计量和会话结束；网络中断后恢复时避免重复交易。本文未执行该环境，不编造一条通用 docker 命令冒充完整部署。

## 23. 保护、安全与认证：区分装置、系统和证据

Type A/Type B RCD、RDC-DD 与直流剩余电流检测不是同一个概念。是否采用某种组合，要依据市场、安装、标准和设计；一个 6mA 检测信号不能独自替代完整人身保护链路。电气设计需检测、动作、自检、反馈与失效分析。

接触器选型考虑负载类别、分断能力、寿命、线圈、温升与反馈；软件断开命令不保证触点未粘连。保护设计还要考虑测量开短路、供电失活、MCU 复位、隔离破坏、调试口跨越边界等。

中国 GB/T 18487.1、GB/T 20234.2，IEC/EN 61851、IEC 62196、IEC 62955，UL/SAE 等属于不同适用体系；版本和目录范围要核实。CE 是符合性标志，FCC、能效与电气安全也不是互相替代的结论。不能从项目 README 推导当前认证范围。

**产出**：法规/标准适用矩阵、危险分析、测试计划、关键件清单与变更影响评估。这里没有给出危险试验接线或认证判定参数，按专业测试流程与正式规范执行。

## 24. EMC 与可靠性：从源、路径、对象定位

开关电源、继电器、电机与高速接口可能是干扰源；供电、回流、线缆与空间是路径；复位、模拟采样和通信是受扰对象。先记录失效时刻与工作状态，再提出可验证假设。

```text
原始测试与失效记录 → 假设源/路径/受扰对象 → 改少量变量
    → 同条件复测 → 功能/温升/其他EMC项目回归 → 更新原理图/BOM/报告
```

TVS、滤波、屏蔽或接地修改都可能影响正常信号与其他指标。不能靠“多加电容”或“所有地分开”代替分析。ESD 是相关测试之一，不等于 EMC 全部。

可靠性试验按任务剖面设计，涵盖适用温湿、振动、插拔、温升、供电与长期负载。72h 连续运行是一种观察，不自动等于寿命、现场可靠性或认证通过。保留温度、错误计数、复位原因与故障前后数据。

## 25. 产测自动化：仪器读数如何变成可信记录

[PyVISA][G20] 用于访问多种仪器接口，具体还需厂商 VISA 或 pyvisa-py 等合适后端。先枚举资源、核对设备身份和单位，再按仪器编程手册读取；不要把某台仪器的 SCPI 命令当所有设备通用接口。

产测记录至少有序列号、板卡/BOM/固件/工装版本、测试项、原始值、单位、限值、仪器和校准信息、时间与结论。超时或无法读取不应当作 0 后继续判通过。重测策略显式记录，不能覆盖失败历史只保留最后一次成功。

```bash
python JD/robot-hardware-learning/lab.py audit
```

示例 CSV 三条虚构低压读数输出 pass/review/fail。假设规格 3.20—3.40V，读数 3.39V、假定不确定度 ±0.02V 的区间跨越限值，程序给 review。这个保守区间规则是教学示例，不是所有实验室通用的合格判定规则；实际需明确不确定度含义、覆盖因子、风险与批准的判定规则。

**验收**：缺失版本、重复序列号与非法数值阻止正常报告；边界值有明确定义；测量失效与产品不合格分别记录；未经确认的 review 不能自动进良品。

## 26. 版本、OTA 与量产：软硬件必须一起追溯

设计基线应包含原理图、PCB、BOM/替代料、固件、配置、校准、工装和测试规则。引脚兼容不等于替代料无需验证，热、电气、驱动、EMC 与认证影响都要评估。

A/B 更新要有签名/完整性、兼容、健康判定、失败回退与更新状态持久化。不是所有 MCU 都有足够存储实现同一套 A/B，bootloader 与恢复通道按平台设计。升级期间执行器和充电会话应处在批准状态，不能一律强制自动更新。

EVT/DVT/PVT 阶段名称因企业而异，先统一入口与退出条件。试产验证装配、烧录、校准、产测节拍与良率；量产维护处理批次、ECO、现场问题和重测证据。

**步骤**：定义测试 schema 和原始数据留存 → 确立限值与判定规则 → 解析校验 → review 人工处置 → 仪器适配 → 数据库与报告 → 重测与工装版本管理。

**验收**：设备断开不生成通过报告；序列号重复有显式重测流程；仪器过期/版本不符可阻断；可从成品记录定位测试配置与原始值。不要让生成 PDF 的“PASS”盖过尚未完成的安全试验。

## 31. 项目五：机器人边缘控制与硬件协同平台

**目标**：将机器人任务、MCU/传感板、状态记录和维护平台连接，展示两份 JD 的交叉能力。先 mock 接口，再接已验证设备。

```text
任务/Qt界面/平台 → 上位机规划与状态机 → 协议网关 → 已验证控制器
                              │                    ↕
                     日志/诊断/版本/升级      电机/传感器及局部控制
硬件工程：电源、接口、时钟、保护、热、结构和测试
共同契约：单位、时间、序号、超时、启动状态、故障与兼容版本
```

**验收**：界面、通信或视觉进程失效时有定义的行为；状态数据带时间和质量；升级检查硬件兼容；能够用录制数据复现故障。自然语言或 Agent 可以提交受限任务请求，但不能绕过限位、权限和硬件保护直接生成任意执行命令。

3D 打印方向可延伸阅读 [Klipper 文档入口][G19] 的配置、标定和运动相关章节，研究主机与 MCU 协作。涉及加热器和运动设备时沿用其正式配置/保护与获准测试流程，不把打印机控制配置移植到不同设备后直接运行。

## 32. 学习安排：两条路线，共同交付证据

| 阶段 | 机器人路线 | 硬件/充电路线 | 产出 |
|---|---|---|---|
| 基础 | 单位、编程、通信、时间 | 电路、仪器、数据手册 | 计算练习与接口说明 |
| 入门 | ROS、TF、差速运动学 | 电源、原理图、低压采样 | 节点实验/设计预算 |
| 进阶 | 控制、Nav2/MoveIt、仿真 | PCB、Bring Up、计量 | 仿真报告/测量报告 |
| 系统 | 实时、诊断、版本 | EVSE架构、EMC、产测 | 故障矩阵与测试计划 |
| 项目 | 导航或边缘协同 | 传感板/软件充电仿真/产测 | 可复现项目与验证边界 |

初学者先选一条做 8—12 周的阶段目标，再按基础和设备条件调整。每周交付一个可检查结果：代码、配置、原始数据、设计审查或故障报告，而不是只看完视频。

## 34. 已验证内容与未验证范围

配套 Python 是离线数学与数据检查程序：差速理想运动学、功率积分、电源预算和产测记录校验。它不发送任何设备指令，不实现物理引擎、PID、充电控制或保护回路。测试只能证明这些教学计算在所测输入下满足预期。

ROS/Gazebo、KiCad、ngspice、EVerest、总线、仪器与实物板卡实验未在当前环境完成执行，相关命令和步骤已注明前提。实际项目应保存版本锁定、输入、配置、测量和失败案例，避免把“计划支持”“仿真通过”写成“已量产/已认证”。
