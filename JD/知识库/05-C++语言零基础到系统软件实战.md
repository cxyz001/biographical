# C++ 语言零基础到系统软件实战

> 学习依据：[C++ 系统软件岗位知识索引](05-C++系统软件.md)。本教程按“第一次写程序 → 管好资源 → 并发与通信 → 设备系统 → 可交付项目”组织。配套工程：[cpp-learning](cpp-learning/README.md)。GitHub 检索与资料核验日期：2026-10-23。

## 1. 先知道自己要做出什么

C++ 可以直接操作内存和操作系统资源，也能用类、容器和库组织大型程序。它经常出现在设备上位机、桌面客户端、通信网关、视觉处理和底层 SDK 中。选择它通常是因为需要控制延迟、资源占用、原生接口或部署环境；使用 C++ 本身并不保证速度快。

“系统软件”不等于“写操作系统”。一个能够连续运行、正确回收资源、在断网后恢复、出现故障时提供日志的设备服务，已经包含很多系统工程问题。

先用一个例子串起来：温度计发送数据，程序接收字节，解析出温度，交给处理线程，保存并显示。即使暂时没有温度计，也能先模拟字节流，把核心逻辑做对。

| 岗位要求 | 用白话解释 | 学习产物 |
|---|---|---|
| RAII、智能指针 | 谁负责资源，什么时候释放 | 无手写 delete 的资源管理 |
| STL、算法 | 合适的数据容器和处理方法 | 采样统计、查询、排序 |
| 多线程、同步 | 多个人协作时避免抢同一份数据 | 可关闭的有界队列 |
| Socket、协议 | 收到的字节怎样变成一条完整消息 | 增量拆帧器 |
| Qt | 用事件驱动方式做界面 | 不阻塞的设备上位机 |
| Modbus、CAN、MQTT | 设备和服务之间的通信约定 | 协议适配器与网关 |
| CMake、测试、性能 | 构建、证明正确、定位慢的原因 | 可重复构建与验收报告 |
| SDK、跨平台 | 把能力交给别人稳定使用 | 有版本和所有权约定的接口 |

**先修要求**：会创建文件和打开终端即可。不会 Linux 可以先在 Windows 完成核心练习。先读第 2～10 章并运行工程，再选业务方向。

## 2. 安装工具，理解程序怎样运行

编辑器负责写文字，编译器把 C++ 翻译为机器指令，链接器把目标文件和库拼成程序，调试器负责暂停和检查状态。CMake 描述如何组织构建，它不是编译器。

Windows 可安装 Visual Studio Build Tools 的“使用 C++ 的桌面开发”、Windows SDK 和 CMake；使用 Developer PowerShell。Linux 可用发行版的包管理器安装编译器、CMake、调试器。课程使用 C++17，不要求一开始就学习协程或模块。

第一个完整程序如下，保存为 `hello.cpp`：

```cpp
#include <iostream>
int main() {
    std::cout << "Hello, device!\n";
    return 0;
}
```

Linux / GCC：

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -g hello.cpp -o hello
./hello
```

Windows Developer PowerShell / MSVC：

```powershell
cl /std:c++17 /EHsc /W4 /utf-8 hello.cpp
./hello.exe
```

`#include` 引入声明，`main` 是入口，`std::cout` 输出文字，返回 0 表示成功。编译报错通常指向源码；“找不到符号”通常是链接阶段没有提供实现或库。

头文件通常放声明，`.cpp` 放实现。同一函数在多个源文件里重复定义会破坏单一定义规则。模板一般需要在使用处看到实现，因此课程把模板队列放在头文件。`#pragma once` 是广泛支持的防重复包含写法，也可以使用标准的宏保护。

**练习与验收**：修改输出；故意漏一个分号并读报错；把函数拆到头文件和源文件中，说明为什么两个源文件都要参与构建。

## 3. 变量、函数和输入校验

变量给一块有类型的数据命名。`int` 表示整数，`double` 表示浮点数，`bool` 表示真假，`std::string` 管理字符串。优先初始化变量，不要读取未初始化的值。

```cpp
#include <iostream>
#include <vector>

double average(const std::vector<double>& samples) {
    if (samples.empty()) return 0.0;
    double sum = 0.0;
    for (double value : samples) sum += value;
    return sum / static_cast<double>(samples.size());
}
int main() {
    std::vector<double> samples{21.5, 22.0, 22.5};
    std::cout << average(samples) << '\n';
}
```

函数把输入转为输出。这里 `const ...&` 表示借用现有容器、不复制、不修改它；第 4 章解释借用。示例将空集合平均值定义成 0 只是教学选择，业务中通常应该返回“无数据”，防止把没有采样误认为温度为零。

整数除法会截断，浮点数不能靠精确相等判断所有计算结果。协议字段使用 `std::uint16_t` 等固定宽度类型时要包含 `<cstdint>`，同时约定字节序；固定宽度不等于已经完成序列化。长度使用 `std::size_t`，和负数混算前明确范围与转换。

字符串转数字必须处理非法输入、尾随垃圾、范围溢出和业务边界。例如“23abc”不能因为开头能解析就被当成有效温度。C++17 的整数 `std::from_chars` 可以返回解析终点和错误码；浮点版本的工具链支持需要检查。

**练习与验收**：让平均值函数区分空输入；加入最大、最小值；说明 `size()-1` 在空容器上为什么危险。

## 4. 内存、指针和引用：先分清对象是否还活着

对象有存储位置，也有生命周期。局部对象通常在离开作用域时销毁；动态对象可以活得更久，但必须有人负责释放。初学时先用值对象和标准容器，不需要把所有变量都放到堆上。

| 写法 | 含义 | 需要关注 |
|---|---|---|
| `T value` | 自己持有一个对象 | 拷贝、移动与销毁 |
| `T& ref` | 借用已有对象 | 对象必须活得足够久 |
| `const T& ref` | 只读借用 | const 不会延长所有被引用对象的生命 |
| `T* ptr` | 可以指向对象，也可以为空 | 所有权需要额外说明 |
| `std::unique_ptr<T>` | 独占管理动态对象 | 可以移动，不能复制 |
| `std::shared_ptr<T>` | 多个所有者共同管理 | 引用环、控制块、并发访问 |

下面是错误片段，不要执行：

```cpp
const int* bad() {
    int value = 42;
    return &value; // 返回后局部对象已经结束生命周期
}
```

地址还能打印出来不代表对象仍然存在。访问悬空对象属于未定义行为，可能正常、崩溃或破坏其他数据。编译成功也不能证明运行安全。

`std::vector` 扩容可能移动元素，原来的指针、引用和迭代器可能失效。`std::string_view` 是只读视图，不拥有字符串；如果源字符串被销毁或重新分配，视图可能失效。跨异步边界时，通常复制小数据比保存不清楚生命周期的视图更可靠。

**练习与验收**：画出一个容器和两个借用者的生命周期；解释为什么“函数返回局部 string 的 string_view”错误；找出回调捕获局部引用的风险。

## 5. RAII、拷贝和移动：把清理写进类型

RAII 的核心是：构造成功后，对象负责持有资源；对象销毁时释放资源。资源包括文件、锁、socket、线程和图像缓冲，不只是内存。正常返回和异常退出都走相同的清理路径。

下面是独立可编译的文件资源例子：

```cpp
#include <cstdio>
#include <memory>
#include <stdexcept>
int main() {
    using File = std::unique_ptr<std::FILE, decltype(&std::fclose)>;
    File file(std::fopen("sample.txt", "wb"), &std::fclose);
    if (!file) throw std::runtime_error("cannot open sample.txt");
    if (std::fputs("temperature=23.5\n", file.get()) == EOF)
        throw std::runtime_error("write failed");
}
```

这个例子自动关闭文件，但析构器不能向调用者可靠报告关闭失败；如果业务要求确认数据落盘，需要显式检查刷新、关闭和持久化语义。RAII 不等于断电后数据一定保留。

拷贝表示得到另一份值；移动表示允许接收方接管资源。`std::move` 本身只是转换表达式类别，真正转移由目标类型的构造或赋值操作完成。移动后的标准库对象通常仍可销毁或重新赋值，但状态不应按原值使用，具体保证以类型约定为准。

优先“零法则”：成员已经是 string、vector、unique_ptr 等资源类型时，让编译器生成或删除特殊成员，避免自己编写复杂拷贝控制。确实封装原生句柄时，明确复制是否允许、移动后状态、析构如何处理失败。

`shared_ptr` 只保证共享所有权控制块的相应操作安全，不会自动保护对象内容。`weak_ptr::lock()` 可以尝试取得临时所有权。继承 `enable_shared_from_this` 也不会自动延长对象生命；需要对象已由共享指针管理，并在异步操作中持有正确的共享引用。只捕获裸 `this` 仍可能悬空。

**练习与验收**：让异常发生在写文件前后，观察资源均被关闭；为设备句柄设计不可复制但可移动的接口；说明为什么到处使用 shared_ptr 不能替代所有权设计。参考 [S1] 的资源与所有权规则。

## 6. 容器、算法和复杂度：为什么先用 vector

`vector` 连续存储，遍历通常有较好的缓存局部性；`deque` 适合两端操作；`map` 有序且查找为对数复杂度；`unordered_map` 平均常数查找，但最坏情况、哈希成本和重哈希仍需要考虑。链表支持特定位置的常数插入，不代表整体就比数组快。

```cpp
#include <algorithm>
#include <iostream>
#include <vector>
int main() {
    std::vector<int> samples{5, 2, 5, 3, 1};
    std::sort(samples.begin(), samples.end());
    samples.erase(std::unique(samples.begin(), samples.end()), samples.end());
    for (int x : samples) std::cout << x << ' ';
}
```

输出为 `1 2 3 5`。`unique` 只把相邻重复项移到逻辑末尾，`erase` 才改变容器大小。没有先排序时，它不会删除所有不相邻重复项。

对 100 万条采样逐条插入再反复全量排序，与一次排序后做二分查询，是不同的算法成本。优化之前先问“数据有多少、读写比例怎样、是否要求顺序、内存上限多大”。`reserve` 可以减少扩容，但它不增加元素数量，不能据此越界写入。

**练习与验收**：统计设备 ID 的次数；保存最近 100 条数据；比较线性查找与排序后二分查找。解释为什么一次性查询可能不值得为它排序。

## 7. 类、接口、模板和回调

类把状态与操作放在一起，并守住不变量。例如“队列容量始终大于零”“关闭后不再接受新消息”。`private` 不是安全隔离，而是帮助调用者避免直接破坏内部状态。

设备接入接口可先设计成如下片段，具体网络实现留到项目阶段：

```cpp
#include <string>
struct Device {
    virtual ~Device() = default;
    virtual std::string read() = 0;
};
```

虚函数提供运行时多态；通过基类指针销毁派生对象时需要合适的虚析构函数。虚表是常见实现方式，标准不强制具体内存布局。是否需要去虚拟化或替换虚调用，应由性能测量决定。

模板让一个逻辑用于不同类型，课程的 `BoundedQueue<T>` 同时能装整数或字符串。模板错误长时，从自己代码触发实例化的位置向上找。不要在入门阶段自建大型模板框架。

Lambda 是可调用对象，例如 `[](int x) { return x > 10; }`。`[x]` 捕获副本，`[&x]` 借用变量，`[this]` 只保存对象指针。异步回调执行时间更晚，引用捕获尤其需要证明生命周期。`std::function` 可统一保存可调用对象，但有类型擦除成本，是否分配取决于实现与目标大小。

**练习与验收**：实现只返回固定数据的 FakeDevice；让业务函数只依赖接口；分别使用值捕获和引用捕获，解释修改变量后的输出。参考 [S2] 的 Lambda 章节与 [S3] 的 C++17 特性。

## 8. 错误处理和状态机

预期内的业务结果与程序异常需要区别：队列满是流量策略，帧长度非法是协议错误，内存分配失败是运行环境问题。可以用返回值、错误码或异常，关键是接口必须说明调用者怎么处理。

配套工程约定：`try_push` 在满或关闭时返回 false；`pop` 在关闭且排空后返回 nullopt；非法长度抛 `length_error`；失败的拆帧器禁止继续使用。这个小接口仍有改进空间：真实服务应区分“满”和“关闭”，否则不能准确统计丢弃原因。

连接状态可以从下面开始：

| 当前状态 | 事件 | 新状态 | 必须做的事 |
|---|---|---|---|
| Disconnected | 开始连接 | Connecting | 设置连接截止时间 |
| Connecting | 成功 | Online | 清理重试计数、开始读 |
| Connecting | 失败 | Backoff | 记录原因、延迟重试 |
| Online | 超时或断开 | Backoff | 取消操作、清理半帧 |
| Backoff | 到期 | Connecting | 使用退避与随机扰动 |
| 任意非终态 | 退出 | Stopping | 停止新任务、关闭资源 |

超时必须用单调时钟衡量间隔，不能依赖会被校时调整的墙上时间。重试要有上限或熔断策略；“一直立即重试”会在故障时放大流量。写电机启动命令等有副作用操作前，需要命令 ID、确认和去重，不能见超时就盲目重发。

**练习与验收**：给每个状态列出允许操作；测试连接完成与退出同时发生的情况；说明如何处理晚到的旧连接回调，例如为每次连接分配递增代次。

## 9. 并发原理：线程不等于加速

线程共享进程内存，调度顺序不确定。两个线程同时访问同一内存位置，其中至少一个写且没有正确同步，会产生数据竞争，通常属于未定义行为。`volatile` 不能替代线程同步。

先用互斥锁保护共享状态。条件变量负责等待“状态可能变化”，等待时必须检查谓词，因为可能虚假唤醒，也可能通知发生在等待前。状态读取、修改和谓词判断要遵守同一同步规则。

配套队列的流程是：

1. 生产者加锁，检查关闭与容量，放入数据，解锁并通知。
2. 消费者等待“关闭或非空”，拿出一项，解锁后处理。
3. 关闭操作在锁内设置标记，然后唤醒所有等待者。
4. 消费者处理完已接收任务后退出，主线程 join，最后销毁队列。

有界队列把过载变成可以决策的事情。若每秒产生 1000 条、只能处理 800 条，无界队列会持续积压；增加线程也未必有用，因为瓶颈可能是磁盘、设备或锁。

| 策略 | 适用情况 | 代价 |
|---|---|---|
| 拒绝新数据 | 可以丢失的遥测 | 需要丢弃计数 |
| 丢最旧数据 | 只关心最新画面的预览 | 不适合完整录像 |
| 阻塞生产者 | 上游允许减速 | 小心阻塞 UI 或 IO 事件循环 |
| 持久化后重放 | 不允许丢的数据 | 磁盘容量、重复处理、恢复成本 |

不要持锁执行慢 IO、用户回调或复杂业务。多个锁定义统一顺序，或用 `std::scoped_lock` 等工具避免特定的加锁死锁；它不会让整个程序“不可能死锁”。

原子变量适合简单计数和经证明的同步协议。SPSC 表示单生产者单消费者，MPMC 表示多生产者多消费者，两种算法不能随意互换。原子类型不保证在所有平台无锁；cache line 大小也不保证永远是 64。初学项目采用互斥队列，有测量证据后再研究内存序。

**练习与验收**：运行配套并发测试；解释为什么 close 不会丢掉已入队数据；设计消费者异常时如何通知主线程；给阻塞 IO 增加可取消或超时机制。C++20 的 jthread 能自动 join 并提供停止请求，但不能自动中断任意阻塞调用。

## 10. 可运行实战：字节流 → 拆帧 → 有界队列 → 处理线程

完整源码在 [core.hpp](cpp-learning/include/core.hpp)、[main.cpp](cpp-learning/src/main.cpp)、[core_test.cpp](cpp-learning/tests/core_test.cpp)。本章运行的是内存中的模拟输入，不依赖 Qt、硬件、网络端口或第三方包。

协议定义：前两个字节为大端无符号长度，后跟相应数量的 payload 字节，长度允许 0～1024。字符串 `abc` 编码为十六进制 `00 03 61 62 63`。这只是教学协议，不是 Modbus、MQTT 或某个设备的真实协议。

```text
模拟设备字节
     ↓ 可能每次只有一个字节，也可能多帧合并
FrameDecoder（单线程拥有，增量保存半帧）
     ↓ 完整消息，最长 1024 字节
BoundedQueue（容量 4，满则拒绝）
     ↓ 消费者取出后释放队列锁
处理线程 → 输出 processed: temperature=23.5
```

从仓库根目录运行。Windows 已安装 VS 2022 C++ 工具和 PATH 中的 CMake：

```powershell
cmake -S JD/cpp-learning -B build/cpp-learning -G "Visual Studio 17 2022" -A x64
cmake --build build/cpp-learning --config Debug
ctest --test-dir build/cpp-learning -C Debug --output-on-failure
./build/cpp-learning/Debug/telemetry_demo.exe
```

Linux 安装编译器与 CMake 后：

```bash
cmake -S JD/cpp-learning -B build/cpp-learning -DCMAKE_BUILD_TYPE=Debug
cmake --build build/cpp-learning -j
ctest --test-dir build/cpp-learning --output-on-failure
./build/cpp-learning/telemetry_demo
```

`FrameDecoder` 不会根据网络声明的任意长度立即分配大缓冲：读完头后先验证 1024 上限，再逐字节积累。输入 chunk 本身由调用者持有，真实 socket 接入还必须限制每次读取缓冲、连接数和连接总内存。只限制单帧不能限制全服务资源。

测试覆盖空容量、满队列、关闭后拒绝、关闭排空、等待者退出、两个生产者和三个消费者的总数与总和、每个两段切分位置、逐字节输入、空帧、最大帧、非法长度与截断状态。并发计数与总和测试能发现部分丢失和重复问题，不能证明所有调度下都正确，也不验证全局输出顺序。

拆帧器由一个线程拥有，不允许多个线程同时 feed。回调同步执行，不应再次进入同一个解码器。回调异常需要上层制定处理策略；demo 捕获异常后关闭队列并等待线程退出。示例没有实现进程信号处理、连接超时、持久化或消费者异常上报，不能直接当生产网关。

**练习与验收**：增加消息类型字段；给 reject 计数；测试只收到头就断开；把应用数据从字符串改为明确的 Telemetry 结构。每次先写协议约定，再改代码与测试。

## 11. TCP、UDP、异步 IO 与连接生命周期

TCP 提供有序字节流，不提供应用消息边界。一次发送不保证对应一次接收；收到半个包和多条消息一起到达都正常。“粘包”通常应该通过应用层分帧解决。

UDP 保留数据报边界，但可能丢失、重复、乱序；不能把收到一次 UDP 消息等同于可靠交付。需要可靠性时先判断成熟协议是否适合，不要轻易自建复杂重传系统。

Socket 是操作系统提供的通信句柄。同步接口等待完成，异步接口发起操作后在完成时通知程序。异步并不意味着每个连接都需要一条线程，也不意味着回调能任意并发访问共享对象。

阅读 [S6] 的 Asio echo server，重点跟踪 `socket → async_read_some → async_write → 下一次读取`。例子通过捕获 `self` 延长 session 生命周期，成员数组在异步操作完成前保持有效。若把临时局部字符串的地址交给 async_write，函数返回后缓冲可能失效。

把 echo server 改为设备服务时需要：

1. 每条连接独立持有解码器、收发缓冲和状态。
2. 读到多少字节，只把有效区间交给 feed。
3. 每条连接维护写队列，串行启动写操作，避免消息交错与缓冲失效。
4. 连接错误取消定时器和 IO，清理旧会话，带退避重连。
5. 限制连接数、待发送字节、解析工作量、空闲时长和握手时长。

多个线程执行同一 io_context 时，handler 可能并行；可以用 strand 串行化某个连接的操作，但它不代替其他线程访问时的同步规则。TLS 需要证书验证、主机名校验和更新策略，不能简单关闭验证来“解决连接错误”。

**项目练习**：先运行上游 echo 示例；再接入本课程拆帧器；编写慢客户端、发送超长头和中途断开的测试。本课程只编译验证内存实验，Asio 扩展需额外构建依赖并自行验收。

## 12. Qt：让界面响应和后台任务分开

Qt 是跨平台应用框架。Widgets 适合传统桌面控件，QML 适合声明式交互界面。先做表格、按钮、连接状态和曲线即可，不需要一开始同时掌握两套 UI。

事件循环从队列取事件并执行回调。若在 UI 线程运行耗时循环，按钮、重绘和定时器都可能停住。后台线程做采集或计算，再把结果交给 UI 线程显示。

`QObject` 有线程亲和性。AutoConnection 在信号发出时，根据执行发射的线程与接收对象的线程决定直接或排队调用，不能简单只比较发送对象和接收对象的归属。QueuedConnection 需要接收线程能处理事件；阻塞队列连接在同线程使用会死锁。

Worker-object 模式的结构片段如下；`Worker` 是你要定义的 QObject 子类，不是可独立编译的完整程序：

```cpp
auto* worker = new Worker;
worker->moveToThread(&thread);
connect(&thread, &QThread::finished, worker, &QObject::deleteLater);
connect(worker, &Worker::sampleReady, this, &Window::showSample);
thread.start();
```

需要补充线程退出、窗口销毁、任务取消与 wait。`thread.quit()` 请求结束事件循环，不会打断正在槽函数里执行的永久阻塞任务。Qt 官方也支持继承 QThread 执行特定工作；应根据是否需要事件循环和槽来选，不应理解成绝对禁止继承。

自定义跨线程消息类型需要满足 Qt 对元类型和复制等方面的要求。采样每秒 1000 次时，不要每条都触发全表刷新；UI 可每 100ms 批量刷新，采集队列与显示队列分别设置上限。

**练习与验收**：做一个连接按钮和最新数据列表；后台每秒产生数据；断开后线程退出，重复开关窗口不留后台任务；采样加速后仍能拖动窗口。先读 [S7] QThread 文档注释，再读 [S8] 串口终端的 readyRead、bytesWritten 和错误处理。

## 13. 串口、Modbus、CAN：从字节到工业数据

RS485 是电气层约定，串口参数描述波特率、数据位、校验位等，Modbus 是应用通信协议。三个概念不能互换。线路、接地、终端电阻、收发方向或设备地址错误都可能表现为“程序收不到数据”。

| 方式 | 最先学习 | 常见现场问题 |
|---|---|---|
| 串口 | 端口、参数、字节流、超时 | 端口占用、权限、参数不匹配 |
| Modbus RTU | 站号、功能码、寄存器、CRC、时序 | 地址偏移、响应超时、总线冲突 |
| Modbus TCP | MBAP、事务 ID、请求响应 | 事务关联、断连、设备并发限制 |
| CAN | 仲裁 ID、数据段、过滤、bus-off | 位速率、终端电阻、帧格式不匹配 |

libmodbus 是 C 库，可从 C++ 调用；使用 RAII 管理 context，分别按 API 要求关闭连接和释放 context。不能把其不同资源释放步骤误当成只调用 free 就够了。读 [S9] 单元测试中的单寄存器、多寄存器、异常返回与写后读验证。

设备手册写“40001”不一定等于 API 传参 40001，常见协议偏移需要按手册确认。两个 16 位寄存器组合成浮点数，还要明确寄存器顺序与每寄存器字节序，不能直接 reinterpret_cast 假设所有设备相同。保存原始寄存器值方便追溯。

Linux 的 SocketCAN 把 CAN 暴露为 socket 接口。先用 [S10] 的 candump、cansend、canplayer 观察与回放；有环境支持时用 vcan 做无硬件实验。vcan 不能模拟物理总线错误、电气干扰和真实仲裁负载。

**项目练习**：先只读一个测量寄存器，转换单位并记录原始值；再扩展轮询多个设备。验收必须包含拔线、错地址、异常码、恢复连接和重复命令。运动、充电等控制输出应有设备侧安全机制，桌面软件不能作为唯一保护。

## 14. 网关、MQTT 和本地数据库

网关把不同设备协议转换成统一数据模型。至少包含 device_id、sequence、采样时间、接收时间、值、单位、质量状态与协议版本。设备时间不可信时不能直接用于所有排序与超时判断。

MQTT 是发布订阅协议，broker 转发消息。QoS 0 允许丢失，QoS 1 可能重复，QoS 2 也不等于数据库与物理设备动作端到端恰好执行一次。应用仍需要业务 ID 和去重。retained 消息表示保留主题最新值，不是历史数据库。

阅读 [S11] Paho C++ 的异步客户端、连接选项与示例入口。检查其 C++ 库与底层 C 库的匹配关系，构建选项和 OpenSSL 依赖。不要只复制 publish 调用就假定已具备断网恢复。

本地存储可以从 SQLite 开始：单机部署简单，适合配置、采样缓存和待发送表。MySQL 更适合集中式服务等场景，不能直接用“哪个数据库更快”替代需求分析。SQLite 应使用参数绑定、事务和明确的并发策略。

例如使用 `(device_id, sequence)` 唯一键去重；一批消息写入同一事务；发送成功确认后再更新发送状态。进程可能在“对端已收到、本地未标记”之间崩溃，因此恢复后仍可能重发，接收方也要去重。

断网缓存必须有最大字节数、保留期限、磁盘满策略和重放速率。文件无限增长只是把网络故障转换成磁盘故障。数据库写入成功、MQTT 发布成功与业务处理完成是三个不同事件，日志要分别记录。

**练习与验收**：设计 outbox 表；模拟发出后立刻崩溃；恢复后重发且接收端不重复计数。此章是工程扩展方案，配套核心实验尚未实现数据库与 MQTT。

## 15. 进程、IPC 和平台适配

线程共享地址空间，进程通常有独立地址空间。把不稳定的相机 SDK 放到独立进程可以隔离崩溃，但增加通信、部署和恢复复杂度。进程隔离不代表能自动恢复正确状态。

| IPC | 适合 | 需要明确 |
|---|---|---|
| 管道 | 父子进程数据流 | 关闭、阻塞、消息分界 |
| Unix socket / 本地 socket | 本机控制消息 | 权限、协议、连接生命周期 |
| Windows named pipe | Windows 本机服务接口 | 访问控制、读写模式、取消 |
| 共享内存 | 大图像、批量采样 | 同步、版本、所有权与崩溃恢复 |

共享内存可以减少数据拷贝，但不是所有数据通路都自动零拷贝。内存映射不提供消息协议，也不会自动解决读写竞争。共享区域不要保存普通进程内指针、vector、string；使用偏移、固定布局和版本，或成熟共享内存组件。

稳健互斥锁可以帮助发现持锁进程死亡，但仍需要修复受损数据；它不负责自动删除共享内存对象。若内存里记录“正在写一半”，重启后必须能够判断该帧无效。

跨平台可把串口、时钟、文件、动态库加载等差异放进适配层，业务层依赖接口。Linux fd 与 Windows HANDLE 的无效值和关闭方式不同，不能通用地拿一个 int 包装所有资源。ARM 交叉编译还需匹配目标架构、sysroot、标准库和硬件依赖，x64 编译通过不能替代板端测试。

**练习与验收**：先用子进程 stdin/stdout 传控制消息；再讨论视频帧是否值得放入共享内存；写出进程崩溃后谁重启、谁清理、谁判断请求结果未知。

## 16. OpenCV、FFmpeg 与视频流水线

OpenCV 偏图像处理，FFmpeg 提供多媒体编解码、封装与相关能力，GStreamer 提供管线式媒体处理。RTSP 是流控制协议，不能把“能连接 RTSP 地址”理解成已经解决解码、低延迟、时间戳和断流恢复。ONVIF 与 GB28181 涉及设备发现、控制或平台互联，还需要对应协议栈。

```text
相机/文件 → 读取压缩包 → 解码 → 图像处理 → 显示/编码/存储
                         ↓
                    时间戳与质量统计
```

阅读 [S14] OpenCV VideoCapture 例子：检查打开是否成功、读取后帧是否为空、如何退出；析构释放采集资源。`cv::Mat` 拷贝通常共享底层数据，跨线程后如果另一方复用或写同一缓冲，仍可能竞争。需要独立数据时明确 clone 成本与所有权。

阅读 [S15] FFmpeg decode_video.c：压缩 packet 和解码 frame 是不同对象，send_packet 与 receive_frame 不是固定一对一；EAGAIN、EOF 与结束时 flush 都要按 API 状态处理。不同版本 API 会变化，应跟随固定版本示例编译。

1920×1080、3 字节每像素的一帧约 6.22MB，30FPS 的原始像素数据约 186.6MB/s，未包含对齐和多份缓冲。每多一次全帧复制都会增加带宽与分配压力。先统计队列长度、帧龄、丢帧、解码耗时，不能只看 FPS。

实时预览往往允许丢旧帧保持低延迟，录像通常更重视连续性。两条链路应有不同队列策略，慢磁盘不应无限阻塞预览。GPU 解码与图像处理还要考虑设备内存传输和设备上下文，不是打开一个选项就一定更快。

**练习与验收**：先处理本地视频；再连接摄像头；模拟读取失败、慢处理和断流。记录端到端帧龄分位数、内存峰值和恢复时间。本课程没有硬件媒体联调结果。

## 17. CMake、测试与依赖管理

现代 CMake 以 target 描述依赖：`target_include_directories` 声明头路径，`target_link_libraries` 声明链接依赖，`target_compile_features` 声明语言要求。PUBLIC 会传播给消费者，PRIVATE 只作用于自己，INTERFACE 用于消费者需要的要求。

配套工程的 learning_core 是头文件接口库，两个可执行程序分别引用它；Threads::Threads 处理平台线程库差异。MSVC 使用 `/W4 /WX`，GCC/Clang 使用 `-Wall -Wextra -Wpedantic -Werror`，不要把某个编译器的参数无条件传给所有平台。

Debug 用于调试，Release 用于性能评估。Visual Studio 等多配置生成器在 build 时用 `--config`，单配置生成器通常在 configure 时用 `CMAKE_BUILD_TYPE`。更改编译器或架构时使用新的构建目录。

小实验没有下载依赖。正式项目可以用 find_package 配合固定版本包，或者固定 commit/tag 的 FetchContent；[S17] vcpkg 提供清单、版本和二进制缓存等能力。源码 vendoring 在特定场景也可以成立，但需要许可证、版本和更新机制，不是绝对不能复制源码。

GoogleTest 与 Catch2 都适合行为测试。读 [S5] 中 EXPECT 与 ASSERT 的区别：ASSERT 失败退出当前函数，不会自动终止所有线程或整个进程；资源清理仍应依赖可靠生命周期设计。读 [S18] 的例子理解“正常输入通过”为什么仍会漏掉 0 等边界。

课程测试使用显式 check 抛异常，不使用可能被 NDEBUG 移除的 assert。真实团队可改用成熟测试框架获得更好的行号、参数化和诊断。测试至少分协议单测、并发与生命周期测试、进程集成测试、硬件在环测试；各自证明的范围不同。

**练习与验收**：在干净构建目录成功编译；故意改坏长度上限使测试失败；为新特性补充行为测试；锁定依赖版本并记录许可证。参考 [S4] 官方 CMake 教程逐步补安装与包导出。

## 18. 崩溃、日志与性能：先拿证据

首先收集构建版本、操作系统、设备型号、配置摘要、发生时间、线程、错误码和复现输入。日志应关联 device_id、connection_id、request_id，避免只有“failed”而无法定位链路。

读 [S12] spdlog 的轮转文件、异步模式和 backtrace 缓冲。异步日志同样有队列容量与满载策略；日志刷新可能阻塞，崩溃前缓冲也可能未落盘。不要把高频逐帧大日志当作免费的观测。

| 问题 | 优先证据 | 工具示例与限制 |
|---|---|---|
| 越界/释放后使用 | 访问位置与分配栈 | ASan，不能覆盖所有内存问题 |
| 数据竞争 | 相冲突的访问栈 | TSan，平台和运行时支持有限 |
| 崩溃 | dump、符号、准确二进制 | gdb/WinDbg，符号需匹配版本 |
| CPU 高 | 热点调用栈 | perf 或平台 profiler，权限可能受限 |
| 延迟高 | 队列等待、IO、锁、处理时间 | Tracy / 埋点，CPU 占用低也可能很慢 |
| 内存增长 | 分配、队列、缓存与句柄数量 | 堆分析、ASan/LSan、平台工具 |

Linux GCC/Clang 的可选内存检查构建，要求工具链实际支持：

```bash
cmake -S JD/cpp-learning -B build/cpp-asan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build/cpp-asan -j
ctest --test-dir build/cpp-asan --output-on-failure
```

TSan 应使用独立构建，不与 ASan 混用。Sanitizer 和 Valgrind 的耗时、内存开销随程序不同，不应把固定倍数当承诺。本次未运行这些检查。

优化步骤：固定输入与环境，记录 Release 基线，采样定位，修改单一主要因素，重复测量并回归正确性。[S13] Google Benchmark 提供预热、重复、计时与输出选项；[S16] Tracy 可观测线程、锁、帧和分配。微基准还要防止编译器消除被测代码，并与真实工作负载相互印证。

**练习与验收**：保留同一程序的 Debug 符号与版本号；制造队列满并记录计数；写出一次优化前后对比，包括输入规模、硬件、构建配置和重复次数。不能用本课程功能测试输出宣称任何吞吐指标。

## 19. 四个落地项目：分阶段做出可验收结果

下面是项目实施方案，尚未全部实现。共用原则是“领域逻辑不依赖界面与硬件 API”，这样才能先用模拟器测试。

### 项目 A：设备采集与诊断上位机

**场景**：实验室仪器、产线检测设备、充电设备维护终端。用户能选端口、连接设备、查看参数与告警、导出诊断包。

```text
Qt 窗口（只负责显示与操作）
          ↓命令             ↑采样快照
设备会话与状态机 → 协议编解码 → 串口/Modbus 适配器
          ↓
本地历史、配置、日志与诊断导出
```

第一阶段用 FakeDevice 实现连接、断开和随机读数；第二阶段接入 QSerialPort 并保存原始报文；第三阶段按设备手册解析寄存器、单位和状态码；第四阶段加入 SQLite、日志轮转和安装包。

建议验收：连续运行 8 小时不出现持续资源增长；反复连接断开不泄漏线程；断线后状态明确且可以恢复；每次写参数有请求 ID、权限、范围校验和结果记录。以上是建议目标，需要实测填写数值，不能当已完成结果。

**作品集材料**：协议表、线程归属图、模拟数据脚本、拔线恢复录像、安装与卸载步骤、已知限制。关键难点是取消阻塞工作和 UI 生命周期，而不只是画出漂亮窗口。

### 项目 B：工业边缘采集网关

**场景**：多个 Modbus/CAN 设备向企业服务上报数据，设备网络可能不稳定。

```text
Modbus/CAN 适配器 → 标准采样模型 → 有界队列 → 本地 outbox
                                               ↓
监控与配置接口 ← 质量/延迟/丢弃计数       MQTT 发布 → broker
                                               ↑
                                     确认、退避与恢复重放
```

第一阶段将本课程模拟输入扩展为多个设备，使用明确数据模型；第二阶段接入一种真实协议和只读轮询；第三阶段实现事务缓存、限速重放与接收端去重；第四阶段加入进程托管、配置校验、升级与回滚。

建议验收：断网 10 分钟数据按约定缓存；超容量时有可观察的处理策略；进程在发送中崩溃后可恢复；重复上报不重复计入业务；慢设备不饿死其他设备。容量按采样条数×单条占用×保留时间估算，再计入索引与日志开销。

**需要提交的设计决策**：轮询周期、超时预算、每设备并发限制、时钟策略、唯一键、磁盘上限、设备命令确认语义。先完成一条链路，再增加设备协议，避免同时引入十个库。

### 项目 C：低延迟视频分析工作站

**场景**：摄像头预览、工业缺陷检测、边缘视觉服务。先从本地文件完成正确流程，再连接 RTSP 或工业相机。

```text
输入会话 → 解码 → 最新帧缓冲 → 图像处理 → Qt 显示
               └→ 独立录像队列 → 编码与分段存储
                        ↓
               帧龄、丢帧、队列和磁盘指标
```

第一阶段统计文件帧数并处理空帧；第二阶段添加有界队列和可取消生命周期；第三阶段比较同步与异步的帧龄；第四阶段接入断流恢复、录像分段、磁盘限额和诊断。

建议验收：输入中断后有明确状态；处理故意变慢时内存仍受限；预览不会因为录像磁盘慢而无限积压；关闭程序后相机与线程释放。算法准确率、视频流稳定性和端到端延迟分别评估，不能用 FPS 替代全部指标。

### 项目 D：跨平台设备 SDK

**场景**：把设备接入能力提供给 C++、Java/JNI 或其他语言调用者。SDK 不能默认调用者使用同一编译器、运行库和异常设置。

可从 C ABI 边界设计，下面仅是接口草案：

```c
typedef struct device_handle device_handle;
int device_open(const char* config_utf8, device_handle** out);
int device_read(device_handle* handle, unsigned char* buffer,
                unsigned int capacity, unsigned int* written);
void device_close(device_handle* handle);
```

还要补充 `extern "C"` 包装、导出宏、调用约定、线程安全、超时与错误查询。异常不能逃过 C 边界；跨模块分配的内存要有明确释放者；结构体版本与大小要能兼容扩展；回调注销后是否仍可能到达必须有约定。

第一阶段把核心封成库并写一个消费者；第二阶段加入版本和错误码；第三阶段测试 Debug/Release、不同调用者及库缺失；第四阶段再扩展 JNI，处理线程附着、全局引用、异常和数据拷贝。

建议验收：消费者只依赖公开头与包；文档明确所有权与生命周期；非法句柄、超时和重复关闭的行为有约定；提供符号文件、样例、版本兼容说明与依赖清单。测试多个 ABI/运行时组合后才能宣称兼容，不能从“C 接口”直接推导所有平台通用。

## 20. 学习计划与能力自测

按产物推进，比按阅读页数推进更可靠。时间可以根据基础调整。

| 阶段 | 建议时间 | 阅读 | 必须完成 |
|---|---|---|---|
| 语言入门 | 1～2 周 | 1～4 章 | 编译、函数、容器、输入校验 |
| 资源与设计 | 1～2 周 | 5～8 章 | RAII、模拟设备、状态机 |
| 核心实战 | 1～2 周 | 9～11 章 | 跑通工程、补测试、接 TCP |
| 行业方向 | 2～3 周 | 12～16 章按需 | 选 Qt/网关/视频之一 |
| 工程交付 | 1～2 周 | 17～19 章 | 构建、诊断、安装与验收 |

每天采用“读一个概念 → 写十几行例子 → 故意制造错误 → 记录原因”的方式。不要一次把所有库加入工程，否则很难知道问题出在语言、构建、线程还是设备。

完成后应能回答：对象谁拥有？回调执行时对象还在吗？队列满怎么办？连接半帧断开怎么办？退出时谁取消谁、谁等待谁？一条消息究竟在什么阶段算成功？崩溃时怎样找到对应符号？这些答案比背出更多库名更能说明工程能力。
