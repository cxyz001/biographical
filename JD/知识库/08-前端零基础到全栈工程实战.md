# 前端零基础到全栈工程实战

> 基于[前端与全栈工程岗位知识索引](08-前端与全栈工程.md)，按基础、原理、工程实践与落地项目重新组织。GitHub 检索日期：2026-10-23。配套实验：[frontend-learning](frontend-learning/README.md)。

本教程面向刚开始学习的人：先知道浏览器如何显示页面，再用 JavaScript 处理交互，接着学习 TypeScript、React 或 Vue，最后把接口、数据库、权限、测试和部署串起来。无需同时精通 Java、Python、Go 和 Node.js；先选一条完整路线，再按项目需要扩展。

贯穿案例是一个工单系统：用户创建维修工单、查看列表、修改状态，多人同时操作时避免覆盖。它可以逐渐扩展成 ERP/MES 工作台、AI 助手、数据看板或桌面工具。

## 1. 一次点击背后发生了什么

```text
用户输入地址
  → DNS 查地址 → 建立连接/TLS → 请求 HTML
  → 浏览器解析 HTML/CSS → 下载 JavaScript → 布局与绘制
  → 用户点击 → 更新状态/请求接口 → 服务端校验与数据库事务
  → 返回结果 → 更新界面 → 上报必要的错误与性能信息
```

前端负责交互和展示，后端负责可信规则和数据，数据库负责持久化与并发约束。浏览器中的按钮隐藏、表单校验、TypeScript 类型，都不能代替服务端权限和输入检查。

**第一个练习**：打开任意自己有权调试的页面，在 DevTools 查看 Elements、Console、Network 和 Performance。找到 HTML、JS、图片与 API 请求，分别记录状态码和耗时。完成标准是能区分“页面没有下载下来”“JS 执行出错”“接口失败”三类问题。

## 2. HTML：页面不是一堆 div

HTML 描述内容语义。标题用 h1/h2，操作用 button，导航用 a，输入用 input，表格用 table。语义化让浏览器、键盘、屏幕阅读器和自动测试更容易理解界面。

```html
<form id="ticket-form">
  <label for="title">工单标题</label>
  <input id="title" name="title" required maxlength="120" />
  <button type="submit">创建工单</button>
</form>
<p id="feedback" role="status"></p>
```

这是静态练习片段，需放到完整 HTML 页面。label 关联输入，button 的 type 明确提交行为，role=status 用于通知状态变化。表单仍需 JavaScript 处理提交与后端再次校验。

图片有替代文本，纯装饰图像可用空 alt；图标按钮需要可访问名称。弹窗需处理焦点进入、退出与 Escape；不要用任意 div 模拟按钮后忽略键盘操作。

**验收**：不用鼠标完成输入与提交，焦点可见；错误说明能关联到字段；状态不只靠红绿颜色表达。

## 3. CSS：盒模型、布局与响应式

盒模型包含内容、padding、border 和 margin。`box-sizing: border-box` 让声明宽度包含 padding 和 border，便于稳定布局。Flex 适合一维排列，Grid 适合二维区域；position 和 z-index 还涉及包含块与层叠上下文，数值设成很大并不能穿透所有层级。

```css
* { box-sizing: border-box; }
.workspace { display: grid; grid-template-columns: 14rem minmax(0, 1fr); gap: 1rem; }
.content { min-width: 0; overflow-wrap: anywhere; }
.toolbar { display: flex; flex-wrap: wrap; gap: .5rem; }
@media (max-width: 48rem) {
  .workspace { grid-template-columns: minmax(0, 1fr); }
}
```

`minmax(0,1fr)` 和 min-width:0 可避免长内容把布局撑破。表格可放在带横向滚动的区域，不要靠缩小所有字体强行塞下。图片预留宽高或 aspect-ratio，可减少加载时位移。

**练习**：做工单列表布局，覆盖 360px 手机、平板和桌面，测试长标题、空列表、错误和加载状态。完成标准是内容不被固定高度截断，放大浏览器后仍能操作。

## 4. JavaScript：值、引用、函数与模块

先掌握 let/const、数组、对象、函数、作用域、闭包与模块。const 限制变量重新绑定，不会自动冻结对象。对象赋值通常共享引用，修改嵌套对象可能影响其他位置。

```js
const tickets = [{ id: 1, title: '维修水泵', status: 'open' }];
const next = tickets.map(item => item.id === 1 ? { ...item, status: 'done' } : item);
console.log(tickets[0].status); // open
console.log(next[0].status);    // done
```

展开运算符只做浅拷贝；如果还要改变嵌套内容，应复制相应层级。不要为了复制直接 JSON 序列化所有对象，它会损失 Date、undefined 等语义，也不能处理所有类型。

**练习**：写筛选、排序、统计函数，输入数组不能被意外修改。排序前复制数组或使用兼容环境支持的非原地排序方法。金额运算需要明确精度与币种，不能默认浮点数适合所有账务计算。

## 5. 异步原理：事件循环、Promise 与请求竞态

同步代码先执行，Promise 回调通过微任务调度，计时器回调进入后续任务。事件循环不是说所有计算都自动并行；一个长同步循环仍会阻塞页面交互。Web Worker 可处理适合迁移的计算，但通信、序列化与调度也有成本。

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// 通常观察到 A D C B，计时器 0 不表示立即执行。
```

用户先搜 A 再搜 B，A 的响应却最后回来，是常见竞态。需要取消旧请求或检查请求序号；仅仅写 `await fetch` 不能解决不同调用之间的顺序。取消前端请求也不保证服务端业务操作被撤销。

**练习**：用延时 Promise 模拟两次搜索，确保旧结果不能覆盖新结果。区分防抖与节流：搜索可防抖，滚动采样可节流；它们都不等于缓存或服务端限流。

## 6. TypeScript：类型帮助开发，运行时仍要校验

[TypeScript Narrowing][S2] 从 typeof、控制流和联合类型讲解类型收窄。入门先学对象类型、可选字段、联合类型、泛型与 strict，不急于复杂类型体操。

```ts
type Ticket = { id: number; title: string; status: 'open' | 'done'; version: number };
function isTicket(value: unknown): value is Ticket {
  if (typeof value !== 'object' || value === null) return false;
  const item = value as Record<string, unknown>;
  return typeof item.title === 'string' &&
    typeof item.id === 'number' && Number.isSafeInteger(item.id) && item.id > 0 &&
    typeof item.version === 'number' && Number.isSafeInteger(item.version) && item.version > 0 &&
    (item.status === 'open' || item.status === 'done');
}
```

这是教学校验器，实际项目可采用成熟 schema 库统一输入校验。`response.json() as Ticket` 只是告诉编译器相信你，不会验证网络内容。unknown 需要检查后使用，any 会绕过很多检查。

**验收**：接口返回 null、字段缺失或错误枚举时有受控错误，页面不会因“类型断言已经写了”而崩溃。服务端仍需自己的校验与约束。

## 7. HTTP 与 fetch：成功收到响应不代表业务成功

fetch 通常不会因为 404/500 自动 reject，应检查 response.ok/status。网络错误、HTTP 错误、响应格式错误和业务错误应分别建模。GET 用于读取；创建通常用 POST；幂等语义要通过契约和服务端实现明确。

```ts
async function getTickets(signal: AbortSignal): Promise<unknown> {
  const response = await fetch('/api/tickets', { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json(); // 调用方继续做运行时 schema 校验
}
```

同源由协议、主机与端口共同决定。CORS 是浏览器限制跨源读取的机制，不是认证系统，也不能阻止非浏览器客户端访问接口。开发代理只是方便本机联调，不会自动修复生产跨域和权限配置。

**练习**：在 Network 中模拟离线、慢网、401、409、500，设计加载、空态、错误与重试。写操作重试前检查幂等设计，避免创建重复订单或工单。

## 8. 工具链：Node.js、包管理与 Vite

Node.js 运行构建工具或服务端程序，不等于浏览器环境。Node 没有默认 DOM，浏览器也不能直接使用全部 Node 模块。package.json 描述脚本与依赖，锁文件固定解析结果；安装依赖还可能运行生命周期脚本，应使用可信来源。

先检查 Node/npm 版本，然后选择 React 或 Vue 一条路线。以下脚手架命令需要联网，版本要求以对应 Vite 文档为准；生成项目后保存实际版本和锁文件，不声称 `latest` 是固定教材环境。

```bash
node --version
npm --version
npm create vite@latest ticket-web -- --template react-ts
cd ticket-web
npm install
npm run dev
```

Vue 分支将模板改为 `vue-ts`，不必同时建两个。CI 使用锁文件对应的 `npm ci`，把开发、类型检查、测试和生产构建拆成明确步骤。

[Vite 环境变量文档][S5] 强调客户端可暴露的环境变量。`VITE_` 前缀变量会进入客户端构建，不能放数据库密码、模型 API key 或私钥。`.env` 被 gitignore 忽略，也不意味着打进 JS 的值就保密。

## 9. React：状态快照、组件和 Effect

函数组件根据 props 和 state 描述 UI；更新 state 请求一次后续渲染，不是在当前闭包里立即改变量。批量更新、并发调度和中断是渲染实现的重要部分，但不意味着业务代码自动多线程执行。

```tsx
import { useState } from 'react';
export function TicketCounter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(value => value + 1)}>工单数 {count}</button>;
}
```

列表 key 应代表稳定身份，新增/排序场景避免使用数组下标。派生值可直接由已有状态计算，不应为了每个派生值再设 state 和 Effect。Effect 用于同步外部系统，不是通用的“代码执行区”。[官方 Effect 教程][S3] 讲解订阅、清理与请求竞态。

下面是请求生命周期片段，需在组件中具备 query、setData 和 setError，响应还需按第 6 章校验：

```tsx
useEffect(() => {
  const controller = new AbortController();
  let active = true;
  fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then(response => {
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return response.json();
    })
    .then(value => { if (active) setData(value); })
    .catch(error => {
      if (active && error.name !== 'AbortError') setError(String(error));
    });
  return () => { active = false; controller.abort(); };
}, [query]);
```

Strict Mode 的开发检查会帮助发现缺失清理。应修复资源生命周期，而不是为消除日志关闭检查。生产中复杂服务端缓存通常交给请求库或框架，避免每个组件重复实现缓存和竞态控制。

## 10. Vue 3：响应式依赖与组合式 API

[Vue 响应式基础][S4] 解释 ref、reactive、Proxy 与 nextTick。ref 在 JS 中通过 value 访问；模板中的解包存在具体规则。reactive 对象返回代理，直接改变原始对象不等于改变代理。

```vue
<script setup lang="ts">
import { computed, ref } from 'vue';
const title = ref('');
const canSubmit = computed(() => title.value.trim().length > 0);
</script>
<template>
  <label>标题 <input v-model="title" maxlength="120" /></label>
  <button :disabled="!canSubmit">创建</button>
</template>
```

这是表单状态演示，按钮尚未调用服务。computed 用于派生值，watch 用于合适的外部副作用；不要把所有计算都写进 watch。reactive 的原始值属性被普通解构后可能失去响应关联，应按需要使用 toRefs 等方式。

注意 Vue 2 与 Vue 3 差异：Vue 3 reactive Proxy 一般能追踪新增属性，不应照搬 Vue 2 的新增属性限制；但 Options API 的 this 暴露规则又有边界。大对象或第三方图表实例可考虑 shallowRef/markRaw，但要明确失去的深层追踪能力。

**验收**：过滤条件改变后列表正确更新，切换路由解除订阅，图表销毁不遗留监听器。React 与 Vue 的目标相同，先精通一种再比较实现。

## 11. 状态管理：URL、UI、表单和服务端缓存

| 类型 | 工单系统示例 | 优先位置 |
|---|---|---|
| URL 状态 | 筛选、页码、可分享搜索 | URL 与路由 |
| 本地 UI | 弹窗开关、折叠状态 | 组件本地 state/ref |
| 跨组件客户端状态 | 编辑工作区与偏好 | Context/Pinia/Zustand 等按需求选择 |
| 表单 | 输入、错误、是否修改 | 表单局部或表单库 |
| 服务端数据 | 工单列表与详情 | 请求缓存库/框架数据层 |

[TanStack Query keys][S6] 说明查询键如何描述缓存身份。例如 `['tickets', tenantId, {status,page}]` 应覆盖影响结果的变量。键漏了租户或筛选条件可能错误复用数据；退出登录应清理相应缓存，服务端仍须独立隔离租户。

更新后失效查询与直接更新缓存都可以，按接口返回、复杂度和一致性要求选择，不应绝对要求只能失效。乐观更新要处理回滚、连续修改和版本冲突；高风险业务可先确认服务端成功再更新。

**验收**：快速切换筛选不串数据；更新详情后列表不长期陈旧；请求失败不会无限重试；离线状态不会伪装成操作已保存。

## 12. 接口契约：类型生成之后还要运行时验证

[OpenAPI 3.1.1][S8] 描述路径、方法、参数、请求、响应、schema 与安全方案。先定分页、排序、时间、空值、错误和权限，前后端才有共同依据。响应包裹成 code/message/data 是一种风格，不是所有 REST 接口必须这样做。

工单接口可以约定：POST `/api/tickets` 返回 201 与新工单；GET 返回 items；PATCH `/api/tickets/{id}` 请求包含 status/version；旧版本返回 409。为示例 API 补齐以下 schema 可作为练习：

```yaml
Ticket:
  type: object
  required: [id, title, status, version]
  properties:
    id: { type: integer, minimum: 1 }
    title: { type: string, minLength: 1, maxLength: 120 }
    status: { type: string, enum: [open, done] }
    version: { type: integer, minimum: 1 }
```

这是 components.schemas 下的片段，不是完整可用 OpenAPI 文件。完整练习应加 openapi/info/paths、requestBody 和各状态响应，再用规范工具校验并生成客户端。

生成的 TS 类型不能保证服务器真的遵守契约。[MSW][S9] 允许在网络边界模拟请求，前端可先开发，但 Mock 也可能与真实后端漂移。增加响应 schema 校验与真实 API 契约测试，并把 401/403/409/429/500 纳入样本。

## 13. Node/BFF：服务端不是把 fetch 搬个位置

BFF 为特定前端聚合接口、整理数据与会话，避免前端了解过多内部服务细节。它不应复制所有核心业务规则或吞掉底层错误。小项目可先用模块化单体，只有存在清晰需要才增加独立 BFF 和微服务。

[Express README][S14] 是 Node HTTP 框架入门；生产还需校验、认证、请求大小、超时、日志和错误中间件。Node 的事件循环擅长 IO，并不适合在主线程执行长时间同步 CPU 工作；导出、图像处理、推理应根据负载迁移到 worker 或任务服务。

配套 `ticket-service.mjs` 使用 Node 标准库展示 HTTP 契约和并发控制，降低安装依赖门槛。它不是推荐手写 Web 框架，也不是完整产品后端。

```bash
node --test JD/frontend-learning/ticket-service.test.mjs
node JD/frontend-learning/ticket-service.mjs
```

服务默认仅监听本机 3088。使用方法见[实验说明](frontend-learning/README.md)，测试会使用随机空闲端口并自动关闭服务。

## 14. 数据库与并发：防止两个人互相覆盖

两人都读到 version=1，一个改为 done，另一个按旧数据改为 open。若简单按 ID UPDATE，后提交者可能无声覆盖前者。乐观锁要求请求带读取时的版本，并在同一次数据库操作中比较、修改和增加版本：

```sql
UPDATE ticket
SET status = ?, version = version + 1
WHERE tenant_id = ? AND id = ? AND version = ?;
```

检查影响行数。0 行可能是不存在、无权访问或版本冲突，需要按设计查询和映射，不能仅凭行数就区分所有原因；错误消息也应避免泄露其他租户资源。多个 SQL 构成业务不变量时需事务和必要锁，而不是把 version 当万能并发方案。

实验 API 使用单进程 Map，比较到更新之间没有 await，仅能说明本进程串行执行条件下的原理；进程重启丢数据，多实例也不共享状态。真实系统必须用数据库条件更新与事务验证。

索引从查询模式出发。例如租户内按 status 和创建时间分页，可评估 `(tenant_id,status,created_at,id)`。深分页、范围条件与排序应看执行计划；索引会增加写入成本。金额、时区、软删除、审计字段需按业务明确建模。

## 15. 登录与权限：前端提示，后端裁决

认证确认身份，授权确认能做什么。RBAC 可表达角色权限，还要校验具体资源与租户归属。隐藏“删除”按钮只改善体验，不能阻止攻击者直接调用接口。

Cookie 会话可配 HttpOnly、Secure、适当的 SameSite，并设计 CSRF 防护；Bearer token 也需考虑存储、过期、撤销和 XSS 暴露。localStorage 并不因为使用 JWT 就安全，HttpOnly 也不能消除同源 XSS 的所有危害。

401 不一定都要无条件刷新。依据错误与会话契约，至多受控刷新并重试，合并并发刷新，刷新失败结束会话；避免登录接口自己触发无限刷新循环。403 应区分无权限，不能统一反复重登。

**验收**：跨租户改 ID 无法读取/修改资源；过期令牌、撤销角色、并发刷新和退出后缓存清理有测试；日志与埋点不包含密码或完整 token。

## 16. SSR、SSG 与 Next.js：渲染发生在哪里

CSR 依赖浏览器执行 JS 构建交互；SSR 在请求期间生成 HTML；SSG 在构建等阶段预生成页面。选择受 SEO、个性化、更新频率、缓存和成本影响，不能把 SSR 当必然更快。

[Next.js use-client][S7] 说明客户端边界用于需要 state、事件和浏览器 API 的交互模块。Client Component 不意味着其初始内容一定完全不经过服务端生成；Server/Client Component、SSR 与 hydration 是有关联但不同的概念。

hydration 需要客户端与服务端初始输出兼容。渲染时读取随机数、时间或浏览器专属数据容易产生差异。用户私密数据不能进入跨用户共享缓存；框架缓存默认行为随版本演变，应固定版本并写隔离测试。

**练习**：内容站点使用静态/服务端渲染，登录后的工单工作区用适合的交互方式；记录首包、首屏、JS 体积与服务器成本。不要在服务端模块暴露密钥，也不要用客户端边界包住整棵应用而不评估代价。

## 17. SSE、WebSocket 与 AI 流式界面

SSE 适合服务端持续发送事件，WebSocket 适合双向通信。fetch 读取流也可以消费特定流协议，但不能把网络 chunk 当成完整事件：一个事件可能分多次读取，多事件也可能一次到达。UTF-8 字符也可能跨 chunk，使用 TextDecoder 的流式解码，并按协议分隔与缓存。

```text
浏览器 → POST 创建任务 → task_id
浏览器 → 订阅事件 → queued / running / delta / completed / failed
浏览器 → 取消任务 → 服务端终止/尽力取消 → 明确最终状态
断线 → 从事件序号恢复，或重新查询任务快照
```

原生 EventSource 通常用 GET，不能像 fetch 那样任意设置请求头；鉴权要依据同源 Cookie 或其他适合的安全设计。不要把长期敏感凭据塞进可能被日志记录的 URL。反向代理可能缓冲输出，还需心跳、超时和断线恢复策略。

AI 页面要区分正在生成、用户取消、服务失败与已完成。渲染 Markdown 需防 XSS，工具调用结果应显示来源和状态；前端断开连接不等于后端昂贵任务停止。输入不可信文本也不能直接触发高权限工具。

**验收**：慢输出、重连、重复事件、半个字符、取消和错误中断都不破坏状态；历史消息与增量事件不会重复追加。

## 18. 性能：从用户指标追到具体瓶颈

LCP 反映主要内容呈现，INP 反映交互响应，CLS 反映布局稳定性。[web-vitals][S12] 提供现场指标采集方法。实验室 Lighthouse 与真实用户数据互相补充，不能跑一次分数就声称所有用户都快。

常见良好参考为 LCP≤2.5s、INP≤200ms、CLS≤0.1，并结合移动/桌面等真实分布的第 75 百分位观察；这些不是每个业务的唯一 SLO。隐私与指标采样、页面标识也需要设计。

先看网络瀑布和主线程，再决定优化：图片尺寸/格式、关键资源、代码分割、缓存、长任务、频繁渲染、虚拟列表。动态 import 可能引入新的串行等待，外链 CDN 也增加可用性与供应链依赖，不能保证必然更快。

memo/useMemo/useCallback 用于有依据的场景；Vue 的浅响应也要测量。scheduler.yield 等 API 应检查支持并准备回退，requestIdleCallback 不适合承载必须及时完成的工作。

**验收**：固定设备、网络与数据量，对照优化前后 P75/P95、JS 大小、长任务与错误率；不能只比较开发模式刷新速度。

## 19. 组件、图表与无障碍：复用的是行为契约

公共组件需要明确值、事件、禁用、加载、错误、键盘和焦点行为，不是抽一个视觉外壳。受控与非受控按场景选择，不必为了“通用”强行同时支持；props 数量也不是判断组件是否必须拆分的硬阈值。

[ECharts][S15] 适用于业务看板。图表容器应有稳定尺寸，监听合适的 resize，并在卸载时 dispose。数据更新需避免重复创建实例。图形还需标签、单位、空数据与可访问的表格补充，不能只靠颜色判断业务异常。

**练习**：做工单统计图与可筛选数据表，定义 UTC/本地时间与统计口径。测试一条、零条、大量数据和超长标签；图表漂亮但口径错误不算完成。

## 20. 测试：验证用户结果与关键不变量

单元测试适合纯函数和复杂规则；组件测试适合输入、焦点与交互；API 集成测试适合契约、权限和事务；E2E 验证跨模块流程。[Vitest][S11] 适合现代前端单元测试，[Playwright][S10] 提供浏览器自动化、自动等待与失败追踪。

```ts
// 完成真实工单页面后使用；需 Playwright 配置 baseURL 和测试数据隔离。
import { test, expect } from '@playwright/test';
test('创建工单后可在列表中找到', async ({ page }) => {
  await page.goto('/tickets');
  const title = `测试工单-${Date.now()}`;
  await page.getByLabel('工单标题').fill(title);
  await page.getByRole('button', { name: '创建工单' }).click();
  await expect(page.getByRole('row').filter({ hasText: title })).toBeVisible();
});
```

该片段是未来页面的验收示例，当前仓库没有对应完整 UI，未执行。真实测试需清理数据或隔离数据库；时间戳用于样例命名并非强唯一方案。避免用固定 sleep 等待页面，也不要只验证按钮存在。

配套 4 项 API 测试会真实启动 HTTP 服务，检查创建/读取/更新、并发版本冲突、输入校验、超大请求与不存在资源。未覆盖登录与数据库，因为实验尚未实现这些能力。

## 21. 部署与 CI/CD：发布的是一组相容产物

```text
提交 → lint/类型检查 → 单元与 API 测试 → 生产构建
     → 启动测试环境 → E2E → 固定版本产物 → 部署/灰度
     → 观察错误与性能 → 继续放量或回滚
```

静态带 hash 资源可长缓存，入口 HTML 需要合适的再验证。保留旧资源一段时间，避免旧 HTML 引用已删除 chunk。SSR/后端服务则还需进程、健康检查、超时与连接排空。前端配置都可被用户读取，运行时 config.js 也不能藏密钥。

回滚不仅是切回 HTML：还要考虑 API 兼容、数据库迁移、缓存与 Service Worker。数据库变更可采用先扩展再迁移后收缩的兼容步骤，避免新旧客户端同时在线时断裂。

CI 锁定依赖，按风险限制权限，密钥放 CI secret，审查第三方 Action 与安装脚本。Source Map 可按政策上传错误平台并限制公开访问，关闭公开 Source Map 并不等于已保护所有源码或秘密。

**验收**：在测试环境完成一次发布和回滚演练，记录旧页面、旧 API 客户端与新后端能否共存；监控有版本标识并能定位白屏和资源失败。

## 22. Electron、跨端与微前端：先识别边界再选型

[Electron security][S13] 强调最小权限、contextIsolation、sandbox、禁用不必要的 nodeIntegration、受控 preload 与 IPC 校验。不能把渲染进程传来的任意路径、URL 或 shell 命令直接交给主进程。代码签名和公证有助于分发可信度，但不保证绕过所有安全提示与拦截。

Flutter、React Native、uni-app、小程序应按原生能力、团队、性能、渠道审核和维护成本选型，不能承诺一份代码零适配。桌面更新需验证签名、兼容与恢复，差分支持依平台与工具决定，不是按版本大小自动成立。

微前端用于团队和部署边界，[single-spa][S16] 可帮助理解应用注册与生命周期。iframe 有独立文档上下文，但通信需验证 postMessage 的 origin/source 和消息格式；同源、sandbox、权限策略也影响隔离。Module Federation 的共享依赖需要版本协商，不保证天然去重或安全隔离。

**验收**：写选型表，说明为什么一个普通模块化应用不够。若只是一个团队做中小系统，优先保持简单，先把模块和组件边界做好。

## 23. 落地项目一：ERP/MES 工单与审批工作台

**范围**：工单、状态流转、审批、附件、筛选、角色与审计。前端选 React/Vue，后端按团队选 Spring Boot/FastAPI/Go/Node，数据库选一种关系库，先单体交付。

**步骤**：先画状态机和权限矩阵；定义 OpenAPI 与 Mock；完成列表、表单和详情；落数据库并实现条件更新；补权限和审计；完成测试、部署与监控。附件单独校验类型、大小和访问权限，不直接信任文件名。

**验收**：并发审批不重复生效，版本冲突可提示刷新；跨租户不能越权；列表筛选可分享；重复提交有幂等策略；失败不会显示保存成功。交付架构图、契约、迁移脚本、测试与回滚记录。

## 24. 落地项目二：AI 知识库与流式助手

```text
Web 会话界面 → BFF/鉴权 → 会话与任务服务 → 检索/模型服务
                  │                ├──→ 文档与向量索引
                  └── SSE/流式输出 ←┘
后台：文档上传 → 校验/解析 → 切分/索引 → 状态与失败重试
```

**步骤**：先做假流式与取消；再接后端任务状态；加入文档权限与引用；实现上传索引进度；补历史会话和错误恢复。检索前后都要确保文档权限，不能仅在 UI 隐藏其他人的资料。

**验收**：重连不重复消息，停止后状态明确；引用可定位且用户有权读取；Markdown 不执行不可信脚本；模型 key 留在服务端；记录响应质量与首字延迟。工具执行必须由后端授权和校验。

## 25. 落地项目三：实时运营与设备数据看板

**范围**：设备状态、时间序列、告警列表、历史查询和下钻。实时通道只推必要增量，首次快照与后续事件有版本/序号关系。数据间断应标注缺失，不把未知当作 0。

**步骤**：定义指标口径和时区；分页查询历史；用 ECharts 展示；接 SSE/WebSocket；实现重连和快照恢复；加入告警去重、可访问表格与慢网测试。大量数据在服务端聚合或降采样，不无上限堆入浏览器。

**验收**：长时间运行内存不持续上涨；切换路由释放连接；重复与乱序消息有策略；实时与历史口径一致；图表暂停/恢复不产生巨大积压。

## 26. 落地项目四：桌面设备维护工具

**范围**：设备列表、串口/本地服务连接、日志、配置导入导出与受控升级。UI 在渲染进程，设备权限通过最小 IPC 或本地服务 API，禁止暴露通用执行器。

**步骤**：先模拟设备，定义协议和错误；实现断开重连、超时与取消；校验导入配置；按目标平台打包与签名；验证更新和离线运行。真实固件升级需遵循设备协议与安全要求，不能让普通示例直接操作生产硬件。

**验收**：拔插、错误配置、权限不足与进程崩溃有明确恢复路径；IPC 校验发送者和参数；密钥不在前端包；日志可脱敏导出。项目完成标准是安全可靠地处理异常，而不仅是窗口能打开。
