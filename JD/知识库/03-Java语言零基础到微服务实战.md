# Java 系统学习：从零基础到微服务与行业项目

这份教材根据 [Java 微服务后端架构岗位知识](./03-Java微服务后端架构.md) 中的技术要求编排。原文用于查看岗位能力，本篇用于逐步学习：**理解概念 → 运行代码 → 制造失败 → 解释原理 → 完成项目**。

主线项目是订单服务：先用普通 Java 实现业务规则，再接入 HTTP、Spring、数据库、缓存和消息，最后学习部署、监控与跨服务协作。无人机视频、地图和任务调度放在进阶阶段，不要求初学者一开始就安装整套平台。

整理日期：2026-10-23。资料来自 GitHub 官方仓库、官方入门项目和第三方开源项目；讲解与本地练习是学习整理，并非上游项目全文转载。配套练习采用 **JDK 17+** 的语言能力；虚拟线程另标注为 **JDK 21+**。框架主分支可能需要更新的 JDK，不能直接用本篇最低版本编译所有上游仓库。

## 2. 环境、编译、运行与第一个可验证项目

### 2.1 JDK、JVM、编译器分别是什么

JDK 提供编译、运行与诊断工具。`javac` 把 `.java` 编译为字节码 `.class`；`java` 启动 JVM 加载并执行字节码，运行中可能通过 JIT 把热点代码编译为机器码。Java 不是“每执行一行就重新编译一行”。

先准备一个兼容的 JDK、编辑器和 Git。先不用装 Redis、Kafka、Kubernetes。

```powershell
java -version
javac -version
Get-Command java,javac
Set-Location D:\project\001\biographical\JD\java-learning
$build = Join-Path $env:TEMP 'java-learning-classes'
javac -classpath . -encoding UTF-8 -d $build OrderLab.java OrderLabTest.java
if ($LASTEXITCODE -ne 0) { throw '编译失败' }
java -cp $build OrderLabTest
java -cp $build OrderLab
```

如果显示中文乱码，先将终端输出编码切换为 UTF-8：`[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()`。这是终端显示设置，不是修改 Java 字符串或源文件。

### 2.2 配套实验先做了什么

| 文件 | 用途 |
|---|---|
| [OrderLab.java](./java-learning/OrderLab.java) | 订单输入、不可变对象、幂等、状态迁移、线程池 |
| [OrderLabTest.java](./java-learning/OrderLabTest.java) | 不依赖测试框架的可运行验收 |
| [实验说明](./java-learning/README.md) | 运行方法、验证环境与项目边界 |

运行后，8 次同键创建会得到相同订单，唯一订单数为 1。测试还会检查同键不同参数、非法状态转换、100 次并发提交以及队列满时的拒绝。

这里只是**内存业务实验，不是 HTTP 服务**。状态重启丢失、没有鉴权、没有数据库、不支持多实例幂等。它的作用是先学会验证业务规则，再把规则放进 Web 框架。

### 2.3 JDK 与框架版本不要混在一起

本地实验只需要 JDK 17+。学习 J2/J3 时阅读项目自己的 `pom.xml` 或 Gradle 配置，以其要求的 JDK 为准；使用项目自带 Maven/Gradle Wrapper，例如 Windows 下执行 `.\mvnw.cmd test`。不要直接用机器上较旧的全局 Maven 构建主分支。

**练习**：修改输入校验让数量 0 通过，运行测试，观察失败；恢复规则后重新运行。

**验收**：能解释源码、字节码、classpath、JDK 版本和退出码。

## 3. 基础语法、数值、字符串与控制流程

### 3.1 从一个完整程序开始

保存为 `Hello.java`，用 `javac -encoding UTF-8 Hello.java` 编译，再用 `java Hello` 运行：

```java
public class Hello {
    public static void main(String[] args) {
        int quantity = 2;
        long priceInCents = 1990L;
        long total = Math.multiplyExact(priceInCents, quantity);
        System.out.println("总价：" + total + " 分");
    }
}
```

文件名与公开类名对应。`main` 是入口；`static` 表示不需要先创建 `Hello` 实例。暂时把方法签名当约定，理解对象后再回来看。

### 3.2 类型与数值边界

`int`、`long`、`boolean` 等是基本类型；`String`、数组、集合、业务对象是引用类型。局部变量使用前必须初始化，实例字段有默认值。`null` 表示没有对象，访问其成员会触发空指针异常。

钱通常使用“最小货币单位的整数”或按明确规则使用 `BigDecimal`，不能依赖 `double` 精确表示十进制金额。`new BigDecimal("0.1")` 与 `new BigDecimal(0.1)` 含义不同；除法要指定精度与舍入策略。`BigDecimal.equals` 还比较 scale，数值大小比较通常用 `compareTo`。

整数相加、相乘可能溢出，不会自动变成无限精度；教学订单总价可用 `Math.multiplyExact` 明确检测。金额还必须带币种，不能把不同货币直接相加。

### 3.3 字符串与相等性

`==` 比较基本类型值，或比较引用是否相同；字符串内容比较用 `equals`，允许空值时可用 `Objects.equals`。不要依赖字符串常量池让错误写法“看起来也能运行”。

String 不可变。循环拼接大量文本可以使用 `StringBuilder`；不要在日志和异常中输出密码、令牌与完整敏感载荷。

### 3.4 条件、循环和方法

```java
static long total(long cents, int quantity) {
    if (cents < 0 || quantity < 1 || quantity > 1000) {
        throw new IllegalArgumentException("金额或数量无效");
    }
    return Math.multiplyExact(cents, (long) quantity);
}
```

方法把输入、输出与失败约定封装起来。先理解顺序、分支、循环，再使用 Stream 或异步链，避免只会拼写 API。

**练习**：为 `total` 编写正常、负数、零数量、溢出四类用例；再增加币种字段和可解释的校验错误。

**验收**：能解释 `==` / `equals`、空指针、整数溢出、浮点金额误差。

## 4. 对象、接口、不可变性与异常

### 4.1 类不是数据库表的另一种拼写

类用来组织状态和行为。订单不只包含字段，还包含“已支付订单不能直接变回待支付”等规则。构造器和方法应维护这些规则，不要让任意调用者随意修改状态。

```java
record CreateOrder(String sku, int quantity) {}
interface OrderRepository {
    java.util.Optional<Order> find(long id);
    void save(Order order);
}
```

以上是设计片段，`Order` 需要在项目中定义。接口描述调用方需要的能力，实现可换成内存或数据库。初学者先在配套实验里观察具体类，形成替换需求后再抽象接口。

### 4.2 record 与不可变性

record 适合表达数据值，会生成访问方法、`equals`、`hashCode` 等。它是浅不可变：如果字段是一个可变 List，外部仍可能改变其内容。构造时可用 `List.copyOf` 防御性复制；其中元素本身仍需审视是否可变。

配套订单只包含不可变字段，修改状态时创建新订单对象，减少共享引用被任意改写的问题。

### 4.3 equals 与 hashCode 为什么要一起考虑

HashMap、HashSet 先根据哈希定位，再判断相等。相等对象必须具有相同 hashCode；被用作 key 后，不应修改影响哈希与相等判断的字段，否则可能“放进去了却找不到”。

### 4.4 异常表示失败，不表示“随便忽略”

非法输入、业务冲突、依赖故障需要区分。底层异常可以包装并保留原因，上层映射为稳定错误码，不能把完整堆栈直接返回客户端。

`try-with-resources` 负责关闭实现 AutoCloseable 的资源，例如文件、JDBC 连接与结果集。`finally` 用于清理，但避免在其中 return 覆盖原始结果与异常。

捕获 `InterruptedException` 后，要么向上抛出，要么恢复中断标志并结束当前工作；不能吞掉后继续无限执行。

**练习**：为订单增加取消规则；分别用异常表达“不存在”“状态冲突”“数据库不可用”，设计对应 HTTP 错误。

**验收**：能说明 DTO、领域对象、持久化对象为什么可以分开；能解释 record 不等于深不可变。

## 5. 集合、泛型、Stream 与算法基础

参考 J1。先读集合 API 的行为约定，再研究特定版本的数据结构。

### 5.1 先根据问题选择集合

| 需求 | 常见选择 | 需要注意 |
|---|---|---|
| 按顺序保存订单 | ArrayList | 随机访问快，中间插入删除需要搬移 |
| 按 ID 找订单 | HashMap | 不是线程安全；平均复杂度依赖良好哈希等条件 |
| 去重事件 ID | HashSet | 进程内集合不能替代持久化幂等表 |
| 按时间/优先级取任务 | PriorityQueue | 不是天然线程安全的调度系统 |
| 多线程共享查询 | ConcurrentHashMap | 单个方法原子，不等于多个步骤整体原子 |

“先 containsKey 再 put”之间可能插入别人的操作；可考虑 `putIfAbsent` / `compute`，但其回调里也不宜塞入漫长网络请求。多个字段、多张表的业务不变量通常仍需事务或适当同步。

### 5.2 泛型避免到处强制转换

`List<Order>` 表示列表元素的约定。泛型主要在编译期提供类型检查，涉及类型擦除；不能简单把 `List<Integer>` 当 `List<Number>`。先会使用，再学习通配符：生产数据常见 `? extends T`，接收数据常见 `? super T`，具体看方法契约。

### 5.3 Stream 是数据处理表达式

```java
long paid = orders.stream()
    .filter(order -> order.status() == Status.PAID)
    .count();
```

这是片段，需要已有订单集合与状态类型。中间操作通常惰性执行，终止操作才驱动计算。不要在 `map` 里偷偷修改共享状态，也不要以为 `parallelStream()` 自动适合数据库或网络调用；它涉及线程资源、上下文传播和阻塞问题。

### 5.4 算法学到能做工程判断

掌握 O(1)、O(log n)、O(n)、O(n log n)、O(n²)；能够比较“每条订单循环扫描全部商品”与“先建索引 map”的成本。分页、去重、Top K、滑动窗口、有限队列比一开始刷复杂动态规划更贴近这些岗位。

**练习**：把 1 万条订单按 SKU 聚合数量，先写双重循环，再用 Map；使用同样数据比较耗时并验证结果一致。微基准阶段再学习 JMH，别凭一次 `nanoTime` 结果下结论。

**验收**：能区分数据结构优化、SQL 优化、网络调用优化；不会只换一个集合就宣称解决整个系统性能。

## 7. 并发原理：线程、JMM、锁、线程池与取消

参考 J1，尤其 ThreadPoolExecutor、Executors、ConcurrentHashMap、CompletableFuture。

### 7.1 并发为什么会出错

两条线程同时做 `count++`，实际包含读取、计算、写回，可能丢失更新。即便结果碰巧正确，也不代表程序没有数据竞争。

Java 内存模型（JMM）讨论线程间可见性、顺序性与同步关系；JVM 的堆、栈、元空间是运行时内存区域，两者不是一个概念。

`synchronized` 的解锁与随后对同一监视器的加锁建立规定的 happens-before 关系。`volatile` 能提供相应可见性/顺序性，但不把 `count++` 变成原子操作。计数可用 AtomicInteger；同时修改多个关联字段通常需要更完整的同步。

### 7.2 配套实验为什么锁整个创建过程

“检查幂等键 → 对比参数 → 生成订单 → 保存键”共同维护一个不变量。如果只给每次 map 操作单独加锁，两个线程仍可能同时通过检查并各建一单。

实验使用 `synchronized` 方法与不可变订单。它保证同一个 Store 实例内的规则，不能跨 JVM。多个实例应通过数据库唯一约束与本地事务维护同类不变量。

### 7.3 正确理解线程池的执行顺序

一般提交过程是：核心线程不足则建线程；否则尝试入队；队列满时再尝试扩展到最大线程数；仍无法接收则执行拒绝策略。还要考虑运行状态改变等并发检查，不能把这个概览当全部源码。

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    2, 4, 30, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(8),
    task -> new Thread(task, "order-worker"),
    new ThreadPoolExecutor.AbortPolicy());
```

完整代码见配套实验，包含递增线程名、Future 取错和关闭流程。队列容量是延迟预算与内存预算的一部分，不是越大越安全。

几个必须澄清的细节：

- `newFixedThreadPool` 常用实现是无界工作队列；`newCachedThreadPool` 使用 SynchronousQueue，主要风险是线程增长，不能把二者都说成无界队列。
- `CallerRunsPolicy` 在符合其执行条件时让提交者执行任务；如果提交者是事件循环/请求线程，可能拖慢关键路径。线程池关闭后，该策略也不会保证任务必然执行。
- ThreadLocal 可以使用，但要明确 set / remove 和传播范围。线程复用会保留残余数据；不能认为换一个传播库就自动正确。
- 核数公式只是起点。数据库连接、下游配额、队列等待、CPU 和尾延迟共同决定容量。

### 7.4 Future、CompletableFuture 与超时

`Future.get(timeout)` 只限制等待时间，不自动停止任务。`cancel(true)` 通常是尝试中断，任务需要响应；已经完成的外部写入不会自动撤销。

CompletableFuture 适合组合结果。未显式指定 executor 的异步方法通常涉及公共线程池；阻塞 I/O 要明确隔离。`orTimeout` 不等于底层 HTTP 调用或数据库查询真的停止，仍需设置依赖超时、清理资源。

### 7.5 虚拟线程：JDK 21+ 的另一种执行方式

虚拟线程适合大量会等待的任务，不会让 CPU 计算凭空变快。它降低部分线程成本，不会增加数据库连接数、支付网关容量或内存上限。还要通过 Semaphore、连接池或请求准入控制昂贵资源。

```java
// 仅 JDK 21+；JDK 17 不可编译。示意，需导入 java.util.concurrent.*。
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> result = executor.submit(() -> "ok");
    System.out.println(result.get());
}
```

不要在 JDK 17 配套实验中直接粘贴；固定版本后再学习虚拟线程诊断，部分实现细节随 JDK 演进。

**练习**：运行配套的队列拒绝测试，画出“工作中、排队中、被拒绝”的三个任务；再写一个响应中断的阻塞任务。

**验收**：能解释可见性与原子性不同、限等待与真取消不同、线程上限与下游上限不同。

## 8. HTTP、Spring Boot、IoC、AOP 与接口设计

参考 J2、J4、J5、J6。先跑官方最小例子，再做订单迁移。

### 8.1 把官方例子完整跑起来

```powershell
git clone https://github.com/spring-guides/gs-rest-service.git
Set-Location gs-rest-service\complete
java -version
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
```

先核对该 checkout 的构建配置与 JDK 要求；Windows 脚本若被下载策略拦截，应按本机环境处理，不能跳过编译错误继续称成功。另开终端执行：

```powershell
Invoke-RestMethod 'http://localhost:8080/greeting?name=Java'
```

阅读 `GreetingController`：`@RestController` 表示返回值作为响应体处理，`@GetMapping` 绑定路由，参数注解决定请求怎样进入方法，消息转换器把对象编码为 JSON。

### 8.2 Spring 容器到底代劳了什么

普通 Java 中由自己 `new Repository`、`new Service` 并连接依赖；IoC 容器接管对象创建和装配，调用方通过构造器表达所需能力。它不意味着“所有对象都必须交给容器”。

Spring 的 singleton 通常指每个容器一个 bean 实例，不是整个系统只有一个对象，也不保证线程安全。Web 服务可能并发调用同一 bean，不要把某个用户的订单放进共享 Controller 字段。

Spring Boot 在 Spring 之上根据 classpath、配置和条件等进行自动配置，提供启动与运行约定。自动配置不是魔法，排查时看条件评估、绑定属性、bean 定义和实际调用链。

### 8.3 AOP 与代理

AOP 把事务等横切行为织入方法调用路径。常见 Spring 代理模式下，外部通过代理调用才进入拦截逻辑；同类内部 `this.method()` 自调用通常绕过代理。不能仅凭方法上写了注解就确认事务生效。

### 8.4 把内存订单搬到 HTTP 层

建议接口：

| API | 含义 | 失败语义 |
|---|---|---|
| `POST /orders` | 创建订单，带幂等键 | 参数无效 400、键冲突 409 |
| `GET /orders/{id}` | 查询属于当前用户的订单 | 不存在/不可见按策略返回 |
| `POST /orders/{id}/cancel` | 取消符合条件的订单 | 状态冲突 409 |

Controller 负责协议和输入校验，Service 负责用例，Repository 负责持久化。用 Bean Validation 验证基础格式，再验证库存、归属与业务状态。使用统一异常处理返回稳定错误码和 requestId。

订单归属应来自已验证身份，不能相信 JSON 中任意 `userId`。幂等键要按可信租户/用户及操作域限定。

### 8.5 单体先分模块

```text

order-domain    订单值对象、状态规则、用例接口
order-infra     SQL、Redis、外部 HTTP 客户端
```

**验收**：能从 HTTP 请求一路追到 Service、Repository、响应；能说明哪些校验应在业务层再次保证。

## 9. SQL、MyBatis、索引与事务

参考 J3、J7。先学原生 SQL 与 JDBC 的资源生命周期，再用映射框架。

### 9.1 用约束表达不可突破的规则

以下是 **MySQL 8 教学 DDL**，字段长度、字符集、索引策略需随项目细化：

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  idempotency_key VARCHAR(128) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  request_hash CHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  sku VARCHAR(100) NOT NULL,
  quantity INT NOT NULL,
  status VARCHAR(20) NOT NULL,
  version BIGINT NOT NULL DEFAULT 0,
  created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_tenant_request (tenant_id, idempotency_key),
  CHECK (quantity BETWEEN 1 AND 1000)
);
```

应用先限定幂等键的字符规则；哈希来自规范化后的请求，不是随意对原始 JSON 字符串求哈希。首次插入依赖唯一约束；重复时查询已提交结果并比对请求。并发冲突后事务如何恢复，要按数据库与驱动行为设计，不能抓住所有异常都当“重复”。

### 9.2 本地事务解决哪些原子性

订单、库存预留、Outbox 若在同一数据库事务中，可以一起提交或回滚。远程支付 API 不属于这个数据库事务；本地回滚不会把真实扣款撤销。

Spring `@Transactional` 要关注：代理是否经过、事务管理器是否正确、同一线程/连接内执行了什么、异常是否被吞、哪些异常触发回滚。通常运行时异常和 Error 默认触发回滚，检查型异常需按规则配置。异步线程不会自然加入原调用的线程绑定事务。

### 9.3 库存怎样避免超卖

```sql
UPDATE inventory
SET available = available - :quantity,
    version = version + 1
WHERE sku = :sku AND available >= :quantity;
```

这是带命名参数的示意，具体用 MyBatis 参数语法绑定。影响行数为 1 表示扣减成功，0 可能表示不足或不存在，需要按业务区分。相同订单的库存预留还需要唯一业务键，否则重复请求仍可能重复扣减。

### 9.4 索引与隔离级别

索引减少查找成本，也增加写入维护与空间成本。通过实际 SQL、参数、数据分布与执行计划判断，不能只数索引个数。组合索引需结合过滤、排序、范围和选择性，不是每个字段都建单列索引。

MVCC 让某些读操作通过版本读取减少冲突，不表示没有锁。隔离级别、快照建立时机、锁定读、间隙锁和死锁处理要结合具体数据库。不要把 MySQL 经验直接套到 PostgreSQL。

### 9.5 MyBatis 的几个实用边界

- `#{value}` 通常通过参数绑定处理值；`${value}` 是文本替换，动态表名/排序字段必须服务端白名单处理。
- Mapper 映射结果不是自动优化 SQL；关注 N+1、扫描行数、大偏移分页和大对象传输。
- BATCH 要明确 flush、事务提交与失败结果；每批条数由载荷、驱动、锁时长和压测决定，不固定声称 500 条一定最好。
- 连接池限制并发连接。多副本连接总数约等于实例数乘每实例上限，还需为其他应用和运维预留。

**练习**：运行 J3 的事务失败例子；再用真实数据库并发创建同键订单、模拟库存扣减失败，确认订单和 Outbox 未被部分提交。

**验收**：能用查询结果证明没有重复、没有超卖、失败已回滚，而不只是看日志说“事务成功”。

## 10. Redis、缓存、幂等与分布式锁

参考 J8。缓存首先是额外副本，不是默认真相源。

### 10.1 Cache-aside 的基本路径

查询缓存 → 命中返回 → 未命中查数据库 → 回填带 TTL 的缓存。更新通常先保证数据库事务，再使相关缓存失效，并考虑失效失败的重试。

并发读写仍可能回填旧值；TTL 只限制部分旧值的持续时间。根据一致性要求使用版本、失效事件、回源校验或直接读取数据库，不能说“双删必然解决所有竞争”。

### 10.2 穿透、击穿与雪崩

不存在对象反复查询可用短期空值缓存与入口校验；单热点回源可用进程内合并、互斥或逻辑过期，但要规定等待和失败策略；大量键同时失效可用 TTL 抖动、容量保护和降级。布隆过滤器存在误判与更新维护成本。

### 10.3 分布式锁的保证有限

正确获取通常需要原子设置唯一 owner 与租约，释放时原子比对 owner 再删除。租约到期后旧持有者仍可能继续运行，即使有看门狗，也不能保证任意暂停与网络分区下绝无重叠。

关键外部写入可让资源端验证单调 fencing token，或通过数据库条件更新、唯一约束守住不变量。锁是否需要可重入取决于调用模型，不是所有锁都必须可重入。

Redisson 让一些实现更方便，但看门狗是否启用、显式 leaseTime 与续期怎样交互，要查所用版本文档。Redis 锁不能代替数据库事务，也不提供自动的业务回滚。

### 10.4 幂等与锁解决不同问题

锁帮助互斥；幂等要定义重复请求返回什么、状态保留多久、处理中如何响应、失败是否可重试。同一请求在锁释放后再次到达，仍可能重复执行，因此不能只“加锁就完了”。

**练习**：模拟缓存不可用、热点 key 过期、锁租约提前失效；确认订单正确性仍由数据库保障，缓存故障只影响性能或明确拒绝。

**验收**：能说清真相源、允许多旧、失效失败怎么恢复、锁超时后旧任务怎么办。

## 11. 消息队列、Outbox、补偿与对账

参考 J9、J16。先学习一种队列完成闭环，不要求同时熟练 Kafka、RabbitMQ、RocketMQ。

### 11.1 “发送成功”与“业务完成”是两个事实

订单事务提交后进程可能崩溃，尚未发出的消息就丢了；反过来先发消息再提交，消费者可能看见最终回滚的订单。网络上还可能丢确认，导致重复发送。

### 11.2 Outbox 解决双写窗口

在一个本地事务中写订单和 outbox 事件。独立 relay 扫描未发事件发送到队列，再记录发送结果。发送成功但记录失败会重复，因此消费者仍需幂等。

建议事件包含 `eventId`、`aggregateId`、`eventType`、`schemaVersion`、`occurredAt`、`traceId`、业务 payload。时间不能单独作为可靠顺序依据；同订单的版本号或状态版本更适合做新旧判断。

### 11.3 消费事务与确认时机

消费者在本地事务中“插入 eventId 去重记录 → 更新库存/业务 → 提交”，成功后再确认。崩溃可能重投，唯一约束让重复无关键副作用。若更新与去重不在同一事务，可能出现“标记已处理但业务没做”。

Kafka offset 按分区表达处理进度；异步并发处理时不能越过尚未成功的较早记录提交。分区内有序也不代表全系统有序，更不代表跨服务只处理一次。

### 11.4 补偿不是物理回到过去

订单取消后释放库存可以补偿；支付已扣款则可能要发起退款，退款本身还可能失败。Saga/TCC 需要定义业务状态、重试、空回滚/悬挂等边界，不会自动把复杂远程副作用变成强 ACID。

Seata AT、TCC、Saga 有不同适用与资源约束；先比较本地事务加事件是否足够，再评估引入事务协调器的运维和恢复成本。

### 11.5 对账与人工恢复

周期扫描“已支付但未完成”的订单，向支付方回查真实状态，修复记录并留下审计。失败事件需有重试次数、下一次时间、错误类别、告警与重放入口，不能永远无限重试。

**练习**：在“发消息后标记前”和“业务提交后确认前”分别终止进程，重启后验证不丢业务、不重复扣减。

**验收**：能给出故障窗口表，区分“未收到”“重复收到”“业务已提交但未确认”。

## 12. 微服务拆分、超时、熔断、权限与多租户

参考 J10、J15。

### 12.1 先确认拆分的收益与成本

订单、库存、支付可按业务与数据所有权拆分，但会新增网络失败、发布兼容、观测与一致性成本。小团队先采用模块化单体可能更可控。微服务并不必须依赖某一种注册中心；Kubernetes Service/DNS、平台服务发现也可以承担相关职责。

网关处理公共接入策略，服务端仍需验证身份、权限和租户边界。内网不能默认可信；消息消费者、定时任务也必须遵守业务授权规则。

### 12.2 超时是整个调用链的预算

若入口预算 2 秒，下游调用不能各自无条件使用 2 秒。连接、排队、执行、重试、序列化均消耗预算，应传递 deadline 或剩余时间，并预留响应与清理余量。

重试应选定负责层，设置次数上限、退避与抖动，只对适合重试的失败且具备幂等保障的操作使用。不是所有重试都必须放在最外层，但多层独立重试会形成乘法放大。

熔断根据错误/慢调用信号暂时停止尝试；限流控制进入量；隔离限制某个依赖占用资源。它们互补，不能只装一个 starter 就宣称完成治理。

### 12.3 降级不一定返回“成功的默认值”

商品推荐可退化为空列表，支付结果未知则应明确“处理中/待核实”，不能伪造成功或失败。缓存也要标注新鲜度，不能把过期库存当保证可售。

### 12.4 权限与多租户的实质

认证回答“是谁”，授权回答“可以做什么”。RBAC 适合角色与权限映射，资源归属与租户隔离还需要对象级条件。JWT 必须验证签名、issuer、audience、有效期等适用约束，解析成功不等于可信。

租户隔离要贯穿查询条件、唯一索引、缓存 key、文件路径、消息和后台任务。分页总数、导出和日志也可能泄露其他租户数据。

**练习**：伪造另一个租户订单 ID；压慢库存服务；让重试与熔断同时触发，观察总调用数和线程队列。

**验收**：越权被拒绝；依赖故障不会无限排队；用户可区分业务失败与结果未知。

## 13. JVM、GC、JFR 与性能排查

参考 J1。先建立测量与假设，不从复制一串 JVM 参数开始。

### 13.1 堆不是进程全部内存

进程内存还包括线程栈、元空间、代码缓存、直接缓冲区及其他本地内存。`-Xmx` 只限制堆，不能直接设成容器内存上限；需要为其他部分留预算。容器感知行为还取决于 JDK 更新版本、平台与 cgroup 支持。

堆的组织随 GC 实现变化，不能把所有回收器都理解为固定 Eden/Survivor/老年代布局。GC Roots、对象可达性、分配率、存活率、停顿与并发开销是更稳定的入门概念。

### 13.2 GC 选择不要死记堆大小区间

G1 常用于平衡吞吐与停顿；Parallel 关注吞吐；ZGC 关注低停顿，但具体特性与代际支持依赖版本。低停顿目标不是所有业务请求的延迟保证，还要看 CPU、锁、I/O、调度与依赖。

从默认配置、合理堆预算和压测开始，对比吞吐、P95/P99、CPU、RSS、分配率与 GC 记录。固定 Xms/Xmx 是一种策略，不是每个服务必需；元空间上限也不能消除类加载泄漏。

### 13.3 一次可复现的诊断路径

```powershell
jcmd -l
# 把 12345 换成自己的练习进程 PID
jcmd 12345 Thread.print
jcmd 12345 JFR.start name=lab settings=profile duration=60s filename=lab.jfr
jcmd 12345 GC.heap_info
```

这些命令针对自己控制的进程；是否可用取决于 JDK、权限和工具组件。生成 JFR 后用兼容的分析工具观察 CPU、分配、锁与 I/O，不是只看一个“热点榜”就做结论。Heap dump、某些存活对象统计可能造成显著开销，并包含敏感业务数据。

### 13.4 CPU 高、内存涨、接口慢分别怎么想

| 现象 | 先收集 | 常见方向 |
|---|---|---|
| CPU 高 | CPU profile、线程状态、GC | 热循环、序列化、计算、频繁分配 |
| 堆持续增长 | 堆趋势、对象保留路径 | 无界缓存、队列积压、监听器引用 |
| RSS 高但堆不高 | 本地内存、线程数、直接缓冲 | 栈、直接内存、native 分配 |
| 响应慢但 CPU 低 | 依赖耗时、连接池、锁等待 | 慢 SQL、排队、网络、锁竞争 |

**练习**：对“CPU 计算”和“等待慢依赖”分别生成录制，比较热点与线程状态。对优化前后使用相同数据和负载。

**验收**：每项优化都有证据、假设、改动与复测，不以关闭校验、丢消息或降低正确性换吞吐。

## 14. Netty、设备接入与协议解析

参考 J11 的 Echo 示例。

### 14.1 TCP 不是一条 write 对应一条 read

TCP 提供字节流，应用要定义消息边界，例如长度字段、分隔符或固定格式。处理半包、粘包、最大帧长、非法长度、版本号和校验，否则容易被异常载荷拖垮。

### 14.2 EventLoop 与 Pipeline

EventLoop 调度连接相关 I/O 与任务；Pipeline 把解码、验证、业务、编码串起来。不要把慢 SQL、阻塞外部 HTTP 或大计算直接放进事件循环，应按需要转移到受控执行器，并处理返回顺序、超时和断线。

ByteBuf 的引用计数需要遵守所有权；SimpleChannelInboundHandler 的自动释放有特定生命周期，跨异步边界转交缓冲区时要理解 retain/release，不能见到异常就随便补一个 release。

### 14.3 长连接是资源管理问题

心跳用于观察活性，不能证明设备下一刻仍在线。需限制单连接积压、总连接、消息频率、最大报文和离线重连风暴。写缓冲高低水位会影响可写状态，业务必须响应压力，不能继续无限写入。

**练习**：运行 Echo 示例，再添加长度字段；用分两次发送、两帧合并发送、超长帧和断线测试解码。

**验收**：异常帧被拒绝；慢业务不堵塞其他连接；断线后任务和缓冲区被正确清理。

## 15. 监控、容器、发布与故障演练

参考 J4、J14。

### 15.1 日志、指标、链路各自回答什么

日志记录具体事件；指标观察总体趋势；链路关联跨组件耗时。用 requestId/traceId 串联订单，不把 userId、orderId 直接作为无限增长的指标标签。订单号可放日志或受控追踪属性，但注意隐私与保留策略。

最小指标：请求量与错误、延迟分布、活动线程、队列深度、拒绝数、数据库连接等待、消息 lag、Outbox 最老未发事件年龄，以及业务完成率。

### 15.2 容器里运行 JVM

镜像固定可追溯版本、非 root、配置外置、秘密由适当机制注入。应用监听地址要符合容器网络需要，日志写标准输出或统一采集位置。内存预算考虑堆外与线程栈，不能简单 `Xmx = 容器上限`。

活性探针判断是否需重启；就绪探针判断是否接流量；启动探针保护慢启动。数据库短暂失败通常不应使所有副本同时被活性探针重启。

### 15.3 优雅退出有顺序和时间预算

停止接新请求/撤流 → 停止领取新任务 → 等待在途操作 → 提交已完成进度 → 关闭连接与线程池 → 退出。终止宽限期要覆盖该流程，超时后还需要下一次重启能恢复。

### 15.4 CI/CD 最小闭环

编译与静态检查 → 单元测试 → 必要集成测试 → 构建镜像与版本标记 → 部署 → 冒烟与业务指标验证 → 回滚。数据库变更尽量采用扩展—迁移—收缩，避免新旧应用并存时字段立即不可用。

**练习**：停止一个副本、拖慢数据库、阻塞消费者，再恢复；记录错误率、队列增长、恢复耗时和是否有重复副作用。

**验收**：不是只证明容器能启动，还要证明探针合理、退出可控、旧版本可恢复服务。

## 16. 落地项目一：订单、库存、支付闭环

### 16.1 从单进程到可运营项目

| 版本 | 本次新增 | 验收证据 |
|---|---|---|
| V0 | 配套纯 JDK 实验 | 幂等、状态与拒绝测试通过 |
| V1 | Spring REST 与权限 | HTTP 测试、非法参数与越权用例 |
| V2 | MySQL + MyBatis | 真实事务、迁移与唯一约束测试 |

| V5 | Redis、限流与观测 | 缓存失效不损坏订单正确性 |
| V6 | 容器、CI、回滚 | 新环境复现、退出和故障报告 |

V0 已提供代码；V1～V6 是后续实现任务，不是已经交付的生产系统。先用模拟支付，不需要真实扣款就能测试关键失败窗口。

### 16.2 架构与数据所有权

入口 API 负责认证；订单模块持有订单与 Outbox；库存模块持有预留与释放记录；支付模块持有支付请求与回调记录。先在一个服务中按包隔离，后续独立部署时通过接口与事件协作。

每个订单事件有 eventId；每次支付请求有支付业务号；每个库存预留有订单维度唯一键。不能把三个不同领域的去重键混成一个 Redis key。

### 16.3 核心状态机与失败矩阵

订单可建模为待支付、已支付、已取消、履约中、已完成，实际迁移要与支付回调、关闭时限及退款流程协调。配套实验只演示 CREATED 到 PAID/CANCELLED 的最小子集。

| 故障注入 | 期望结果 |
|---|---|
| 同键重复创建 100 次 | 一张订单；同键不同请求冲突 |
| 库存不足 | 没有已确认订单与孤立扣减 |
| 支付接口超时 | 标记未知/待查询，不盲目重复扣款 |
| 回调重复、乱序 | 不重复履约；旧事件不倒退状态 |
| 消费者提交后崩溃 | 重投后业务结果不重复 |
| 退款失败 | 保留可重试状态和审计，不宣称已退款 |

### 16.4 项目交付物

源码、版本清单、数据库迁移、模拟器、正常与失败测试、API 说明、事件格式、监控图表、恢复手册与限制。性能报告包含机器、依赖、数据量、负载、错误率、P95/P99 与瓶颈。

**验收**：从空数据库启动；能通过 ID 追踪一次订单完整生命周期；人为制造崩溃后恢复最终结果。

## 17. 落地项目二：ERP / MES / WMS 集成

适合原文中的企业流程、仓储、生产和供应链场景。重点是跨系统状态与数据映射，不是 CRUD 表单数量。

### 17.1 最小业务闭环

ERP 下发销售单 → WMS 接收出库任务 → 库存预留 → 拣货/出库 → 回传 ERP → 定期对账。MES 可替换为工单、报工、物料消耗流程，先选一个闭环。

外部单号、本地单号、租户、外部版本、业务日期、单位/精度和状态映射必须明确。不能只根据商品名称关联；公斤、件、箱等单位转换要有明确依据。

### 17.2 适配层与重试

每个外部系统有独立适配器，转换协议、鉴权和数据结构。保留原始接收记录及规范化结果，用 Inbox 防重复；异步执行避免长时间占住 HTTP 连接。

设置每租户/供应商并发和配额，区分暂时失败、永久无效、需人工处理。把“HTTP 200 但业务码失败”视为业务失败，不直接当已完成。

### 17.3 对账是产品功能

按时间窗口和稳定游标拉取，处理分页中数据变化；比较订单状态、数量和版本，输出缺单、重复与差异项。重放必须留下操作者、原因、范围和前后结果。

**练习**：用两个模拟系统分别产生重复推送、字段缺失、配额限制和回传超时，展示差异列表及修复过程。

**验收**：同一个外部单据不会重复出库；无法自动修复的差异能被定位和人工接管。

## 18. 落地项目三：无人机视频、GIS 与任务平台

参考 J17～J20，对应原文的重点专题。先用文件、模拟遥测与虚拟设备验证平台逻辑，再按实际设备、SDK、固件和协议接入。

### 18.1 分清五个模块

| 模块 | 负责什么 | 不应混淆 |
|---|---|---|
| Java 业务服务 | 权限、任务、媒体会话、审计 | 不默认转发全部视频字节 |
| 媒体服务 | 接流、转封装、播放分发及能力范围内转码 | ZLMediaKit 不是 GB28181 协议本身 |
| GIS 数据服务 | 图层、空间数据发布、坐标定义 | 地图显示正常不等于坐标计算正确 |
| 移动端/网关 | 设备 SDK、连接、命令与遥测 | Android MSDK 不能直接当服务器 API |
| 设备/模拟器 | 状态与实际执行 | 收到命令不等于完成任务 |

### 18.2 视频：控制面与媒体面分离

用户申请观看 → Java 检查设备权限 → 创建短期播放会话 → 媒体服务提供地址 → 浏览器按兼容协议播放。媒体服务回调验证来源与会话；关闭会话、断流和重试都需要状态。

RTMP、RTSP、WebRTC、HLS 的浏览器支持、延迟、网络穿透与编码兼容不同；不能拿一个协议名保证端到端低延迟。GB28181 涉及信令、会话与媒体传输；需要匹配的信令实现与设备能力，不能仅部署媒体服务就认为全部接入完成。

黑屏按设备出流、网络、服务收流、编码、封装、播放鉴权、浏览器解码逐段定位；Java 接口 200 只说明业务请求完成，不证明媒体可播放。

### 18.3 GIS：先保证坐标和时间含义

存储经纬度必须带坐标参考系，明确经纬度顺序、单位、时间和定位质量。WGS84、Web Mercator 和不同底图偏移体系不能随意混用。WMS 常用于渲染地图，WFS 用于要素访问，空间计算可交给合适的空间数据库或几何库。

JTS 主要处理平面几何，输入经纬度后所得长度/面积不自动变成米/平方米。距离、缓冲与面积需选择适合的投影或测地计算。多边形包含关系的边界点语义也要明确，例如 contains 与 covers 对边界的处理不同。

### 18.4 遥测、轨迹与围栏

遥测建议保存 deviceId、sequence、deviceTime、receivedTime、位置、高度参考、速度、质量与原始载荷引用。迟到点不能直接覆盖当前最新状态；轨迹回放可按可靠时间/序号重建并显示断点。

围栏事件需处理定位抖动：连续样本、进入/退出缓冲区、速度和精度门槛。不能一次边界抖动就反复触发告警。火点标绘区分人工点选、设备上报与视觉估计，并记录误差、来源和确认状态。

### 18.5 航线与任务状态机

航线文件上传 → 大小/格式和解压安全检查 → 版本化解析 → 坐标/高度/设备能力校验 → 预览 → 审批 → 分发。WPML 具体结构、字段和限制按适用官方文档验证，不从“XML 能解析”推断“设备可执行”。

任务可包含草稿、已批准、待设备确认、执行中、暂停、取消中、完成、失败、未知状态。命令有 commandId、有效期与目标任务版本；多实例调度需数据库领取/版本检查等防重机制。

超时可能是“未执行”，也可能是“执行了但回执丢失”。先查询真实设备状态，再决定是否重发；必须避免把普通 HTTP 重试直接套到有物理副作用的动作上。

### 18.6 三阶段项目验收

1. **模拟阶段**：上传轨迹文件、创建围栏、回放进入退出事件、模拟任务迁移；不连接设备。
2. **媒体阶段**：用测试视频源跑通会话申请、播放、过期、断流与重连；保存逐段诊断记录。
3. **联调阶段**：按支持的设备版本接入遥测与命令回执，验证失联、重复、乱序、取消和未知状态恢复。

**验收**：能分别解释业务状态、设备状态、信令状态与媒体状态；轨迹坐标不偏移；命令不因简单超时被盲目重复。

## 19. 落地项目四：Java 业务接入 AI 与流式响应

对应原文的大模型、Agent、RAG、SSE 与异步业务场景。本节先做业务网关，不绑定某个供应商 SDK。

### 19.1 最小架构

已认证用户 → Java 业务 API → 权限过滤后的业务数据/检索 → 模型适配器 → 结果校验 → 返回或执行后续业务。模型输出不能替代权限判断、金额校验或库存事务。

先做只读“订单状态解释助手”，再考虑具有写权限的工具。工具请求必须验证参数、对象归属、幂等键和操作状态；高影响操作沿用现有业务确认机制。

### 19.2 SSE 不是一次普通 JSON 响应

响应使用 `text/event-stream`，事件以空行分隔；服务端适时刷新，代理配置避免不合适的缓冲。使用 Spring MVC SseEmitter 或 WebFlux 时，遵守各自执行模型，不把阻塞依赖直接放到非阻塞事件循环。

客户端断开后清理订阅和任务，并尝试取消上游调用；上游是否真正停止、是否仍计费要由实际实现确认。流已经发送后不能再可靠地把 HTTP 200 改成 500，应定义流内 error 和 done 事件，客户端检查终止状态。

### 19.3 质量与成本同样需要测试

设置用户/租户并发、超时、Token 或费用预算；记录可审计但适度脱敏的调用信息。RAG 测试覆盖无证据、过期资料、越权文档与提示注入，不能只展示一个能回答的演示。

**练习**：用本地模拟模型每 200ms 产生一条事件，模拟中途失败与客户端断开；加入租户知识隔离测试。

**验收**：客户端能区分完成与中断，断开后资源下降，不泄露其他租户资料，模型不能绕过既有业务规则。

### 20.2 原文经验说法应怎样理解

| 容易误解的说法 | 更准确的理解 |
|---|---|
| JMM 就是堆栈划分 | JMM 讨论并发可见性与顺序，运行时区域是另一维度 |
| cached/fixed 线程池都是无界队列 | cached 主要是线程增长风险，fixed 主要是队列积压风险 |
| CallerRuns 永远是温和背压 | 可能阻塞请求线程/事件循环，关闭后也不保证执行 |
| ThreadLocal 一律不能用 | 要明确清理与跨线程传播，传播库也需要正确边界 |
| volatile 能保护复合业务 | 不保证多个操作整体原子 |
| Future 超时等于远程操作失败 | 可能只是没等到结果，外部写入可能已发生 |
| 虚拟线程不用做容量限制 | 依赖连接、CPU、内存和配额仍有限 |
| 有 @Transactional 就会回滚一切 | 取决于代理、资源、线程、异常与规则 |
| 有 Redis 锁就不会重复扣款 | 需要租约边界、业务幂等与资源端约束 |
| TCC/Saga 自动获得强 ACID | 业务确认与补偿有中间态及恢复成本 |
| 网关鉴权后内部无需校验 | 对象权限、租户隔离、消息和任务仍需控制 |
| K8s/JDK 版本较新就无需内存预算 | 堆外、线程栈、平台支持与实际负载都需验证 |
| Java 接口成功就证明视频成功 | 业务、信令、媒体、解码必须分别检查 |

### 20.3 毕业项目必须能回答的问题

为什么同键不同请求要冲突？数据库唯一约束防住了哪种竞争？事务外的支付如何处理未知结果？为什么消息需要幂等和对账？如何证明资源已随取消释放？多副本会把数据库连接放大多少？缓存故障时正确性由谁保证？一次发布失败怎样恢复？

每个答案尽量附一个可运行用例、SQL 结果或诊断记录。回到 [原岗位知识文档](./03-Java微服务后端架构.md)，把技能名转换成自己能解释、能实现、能验证的能力。
