# 嵌入式 Linux 零基础到边缘计算实战

> 基于[嵌入式 Linux 与边缘计算岗位知识索引](06-嵌入式Linux与边缘计算.md)，按照“认识硬件 → 使用 Linux → 启动系统 → 外设与驱动 → 实时协同 → 联网与升级 → 边缘 AI → 产品交付”组织。GitHub 检索日期：2026-10-23。配套练习：[embedded-learning](embedded-learning/README.md)。

## 1. 先认识这份工作：让一个小系统长期可靠工作

想象一台工厂里的小盒子：下面连接温度传感器，上面连接管理平台，里面可能还有摄像头和 AI 模型。它需要读数据、识别异常、断网缓存、恢复补发，也需要升级和远程诊断。嵌入式 Linux 工程师负责把这些能力放到真实硬件上，并保证资源、时间和故障行为都可控。

Linux 内核管理 CPU、内存和设备；驱动把硬件能力接到操作系统；用户态应用实现业务；云端负责设备管理。你不需要第一天就写驱动，更合理的起点是先在 Linux 上写一个正确读取数据的程序。

| 原文技能 | 白话解释 | 本教程中的产物 |
|---|---|---|
| ARM、SoC、BSP | 认识芯片和让板子工作的软件包 | 板级资源表 |
| U-Boot、内核、rootfs | 设备上电后怎样到达应用 | 启动链与故障检查表 |
| C、文件、进程、线程 | 应用怎样请求系统服务 | 有界输入与采集程序 |
| GPIO、I2C、SPI、UART、CAN | 应用怎样跟外设交换数据 | 总线实验与时序记录 |
| 驱动、中断、DMA | 内核怎样处理设备事件和搬数据 | 资源与并发设计 |
| RTOS、RPMsg、PREEMPT_RT | 谁负责及时执行、怎样跨核配合 | 时限与消息契约 |
| MQTT、OTA、看门狗 | 怎样联网、升级和恢复 | 可靠上报与升级方案 |
| RKNN、NPU、边缘 AI | 怎样在端侧运行模型 | 精度、延迟和功耗报告 |

**学习原则**：每章都做一个可观察的小实验；先会解释运行结果，再扩展范围。没有开发板可以完成 Linux 基础、QEMU 路线和便携可靠性实验。外设电气、DMA、实时与功耗结论必须回到目标板测量。

## 2. MCU、MPU、SoC、Linux 与 RTOS：不要混在一起

MCU 常把处理器、片上 RAM、Flash 和外设集成在一起，适合较小的控制系统；MPU 平台常配合外部内存，适合运行 Linux 等复杂系统。SoC 表示片上系统，可能包含 Cortex-A、Cortex-M、GPU、NPU、视频编解码等多个模块。分类有交叉，不能仅靠名称判断全部能力。

ARM 是架构体系，不是具体开发板。Cortex-A 常见于带 MMU 的应用处理器，Cortex-M 常见于微控制器。MMU 支持地址转换和内存保护；没有 MMU 不代表不能运行任何操作系统，但常规嵌入式 Linux 产品通常采用相应的 MMU 平台。

| 选择 | 适合的工作 | 不能直接推导的结论 |
|---|---|---|
| 裸机 | 简单控制、极小系统 | 没有 OS 就一定实时 |
| RTOS | 可分析的任务调度、周期采样和控制 | 使用 RTOS 就满足所有截止时间 |
| Linux | 网络、文件、进程隔离、复杂应用和 AI | CPU 快就能做严格实时控制 |
| Linux + MCU/RTOS | 业务复杂且有明确控制时限 | 两颗核天然互不影响 |

Linux 处理网络和界面，MCU 处理快速采样和保护，是常见分工。它们仍可能共享内存、总线、供电和外设，所以故障隔离与资源争用要另行分析。

**练习与验收**：列出一块候选板的 CPU、RAM、存储、网络、调试接口、内核/BSP 版本和购买可获得性；用一句话解释每个资源为什么需要。先使用文档完整的评估板，再做定制硬件。

## 3. 搭建学习环境：分清宿主机、目标机与模拟器

宿主机是写代码和构建的电脑，目标机是运行最终程序的设备，交叉工具链让宿主机生成目标 CPU 的程序。QEMU 模拟另一套硬件平台，适合学习启动链；WSL 或 Linux 虚拟机适合开发，但不能直接替代板级电气实验。

本教程涉及三种实验，运行条件不同：

1. **Python 便携实验**：Windows/Linux 都能运行，学习缓存、去重与失败恢复，已在本机验证。
2. **Linux 用户态与 QEMU 实验**：需要可用 Linux、编译器和相应工具，提供命令与验收方法，当前主机未实际运行。
3. **开发板实验**：需要目标板、串口、传感器及匹配 BSP，按具体板卡调整，不能直接复制通用引脚和分区地址。

Linux 开发环境通常需要 git、make、编译器、调试器、Python 和文档指定的构建依赖。Buildroot 与 Yocto 对宿主环境有具体要求，应按固定版本文档准备，不应把不同发行版依赖命令拼起来使用。

建议目录按 `sources/`、`build/`、`images/`、`logs/`、`reports/` 划分。记录源码 commit、defconfig、工具链、补丁、设备树、构建命令与镜像摘要。以后看到“我机器上能跑”时，先检查这些输入是否真的相同。

**练习与验收**：在 Linux 输出 `uname -m`、`cc --version`、`make --version`；在目标板也记录架构与内核版本；明确下一条命令是在宿主机还是目标机执行。

## 4. Linux 入门：文件、权限、进程和日志

Linux 中目录组织文件，路径定位对象。`/dev` 提供设备接口，`/proc` 和 `/sys` 暴露部分运行状态与内核对象，它们不等于普通磁盘目录。不要因为接口看起来像文件，就假设可以任意读写或永久保存内容。

```bash
pwd
ls -l
uname -a
cat /proc/cpuinfo
cat /proc/meminfo
ps
df -h
mount
dmesg | tail -n 30
```

这些命令用于观察。部分系统需要额外权限才能读内核日志，BusyBox 的命令选项也可能与桌面发行版不同。遇到某条选项不支持，先读目标系统的帮助。

进程是运行中的程序，PID 用于标识进程；线程共享进程资源。信号可以通知进程停止，正常退出应停止新工作、结束后台任务并释放资源。SIGKILL 不能被捕获，不能把清理工作寄托在它上面。

权限问题先看当前用户、文件属主和组，再看设备规则与安全策略。不要把“chmod 777”当通用修复；设备服务应只获得所需设备和数据目录的访问权。日志必须记录错误码和上下文，而不是只写“打开失败”。

环境变量影响运行路径、动态库和配置，交互终端与系统服务可能不同。程序在终端能运行、systemd 下失败时，应对比工作目录、用户、PATH、配置路径与设备权限。

**练习与验收**：启动一个普通程序，找到 PID，正常终止；制造文件路径错误和权限错误并区分；整理一份“CPU、内存、磁盘、进程、内核日志”的诊断快照。

## 5. C 与系统编程：从正确读写一个文件开始

C 是驱动和 MCU 常见语言。先掌握整数、数组、结构体、指针、函数、头文件与资源清理。不会 C/C++ 的读者可以配合 [C++ 基础教程](05-C++语言零基础到系统软件实战.md) 理解内存与生命周期，但 Linux 内核代码不能直接使用 C++ 标准库。

文件描述符 fd 是进程访问内核对象的句柄。`open` 可能失败，`read` 可能只返回一部分，返回 0 在不同对象与配置下有不同语义；`write` 也可能短写。系统调用返回 -1 后读 errno，不能不检查返回值就使用缓冲区。

典型资源顺序是：打开 → 配置 → 读写 → 清理。C 代码常用统一退出路径释放已经获取的资源；不要在后续步骤失败时忘记关闭前面的 fd。文件描述符 0 也是有效值，不能用 `fd <= 0` 判断打开失败。

协议解析要明确长度、边界和对齐。不要把一段网络数据强制转换成结构体就当作解析完成，因为填充、字节序、对齐与版本可能不同。`volatile` 也不能替代锁、原子操作或 DMA 同步。

配套 [read_lines.c](embedded-learning/read_lines.c) 是完整 Linux 用户态练习：使用 poll 等待标准输入，处理超时、EINTR、短读、EOF；每行最多 80 字节，超长行丢弃至下一换行，避免把后半段误认成一条合法消息。

```bash
mkdir -p build/edge-lab
cc -std=c11 -Wall -Wextra -Werror -O0 -g JD/embedded-learning/read_lines.c -o build/edge-lab/read_lines
printf 'temperature=23.5\nstatus=ok\n' | build/edge-lab/read_lines
printf 'unfinished' | build/edge-lab/read_lines
```

第一个管道应输出两行并退出 0，第二个报告截断并退出 2。该程序演示行边界，没有配置串口，也没有验证温度字段。poll 的 timeout 不是消息完整性超时；如果输入每隔一秒来一个字节，仍可能一直积累，实际服务还需整帧截止时间。

**练习与验收**：测试空行、80/81 字节、一次多行、分段慢输入和 EOF；把输入错误、协议错误与空闲超时分别统计。

## 6. 看懂启动链：上电后每一步都发生了什么

常见 Linux 板卡启动路径如下，具体阶段随 SoC 与安全启动方案变化：

```text
上电/复位
   ↓
芯片 Boot ROM → 早期固件/SPL → DRAM 初始化
   ↓
U-Boot / 平台固件 → 选择内核、DTB 与启动参数
   ↓
Linux 内核 → 探测设备 → 挂载根文件系统
   ↓
init / systemd / BusyBox init → 服务 → 业务就绪
```

Boot ROM 通常固化在芯片里；SPL 等早期阶段完成有限环境下的初始化；U-Boot 可以选择镜像并传递启动信息；内核启动不等于应用已经可用。TF-A、OP-TEE 等可能出现在特定平台中，不是所有开发板必需。

| 现象 | 优先检查 | 保留的证据 |
|---|---|---|
| 串口完全没输出 | 电源、复位、串口电平、接线、波特率、启动介质 | 原理图与电源/复位测量 |
| 早期固件停住 | DRAM、时钟、启动介质与固件匹配 | 最后一条串口日志 |
| 内核启动后挂 rootfs 失败 | root=、分区、存储驱动、文件系统支持 | 完整内核命令行与日志 |
| 进入 shell 但业务没启动 | init 配置、依赖、权限与路径 | 服务状态与应用日志 |

串口调试要确认电平兼容，TTL 串口不能直接当 RS232 接口连接。不要只截取最后一行错误，真正原因可能在前面的电源、驱动或挂载失败信息中。

启动优化先定义终点：从上电到串口、登录、首帧、可接收控制命令是不同指标。给各阶段加时间点，再优化最耗时部分，保留可靠性与诊断能力。

**练习与验收**：保存一份从上电到业务就绪的完整日志，标记阶段和耗时；用“最后成功阶段”定位故障。阅读 [G3] U-Boot QEMU ARM 文档，区分模拟器 virt 板与真实板卡。

## 7. 交叉编译、ABI 与 sysroot：为什么编译成功仍跑不起来

宿主机 x86_64 编译器默认生成 x86_64 程序，不能直接放到 AArch64 板上。交叉编译器生成目标指令，链接目标运行库，sysroot 提供目标头文件与库目录。

在安装相应交叉工具链的 Linux 宿主机上，可以做下面的应用练习：

```bash
aarch64-linux-gnu-gcc -std=c11 -Wall -Wextra -O0 -g hello.c -o hello-arm64
file hello-arm64
readelf -h hello-arm64
readelf -l hello-arm64
```

这里 `hello.c` 需要你创建普通 C 的 Hello World。编译器名字只是示例；供应商 SDK 的工具链前缀可能不同。检查 ELF 架构、解释器路径、动态库需求，目标板必须具有相容运行时。

常见故障：Exec format error 可能是架构不匹配；文件存在却提示 No such file or directory，可能缺少动态加载器；库找到但符号版本不匹配，可能是运行库版本问题。不要把宿主机 `/usr/lib` 混进交叉链接。

静态链接可以减少部分动态依赖，但不能解决内核接口、许可证、DNS/插件机制以及所有 ABI 问题。不要用“不管目标系统版本，全部静态链接”替代兼容性设计。

**练习与验收**：分别构建宿主与目标二进制，比较 file/readelf；在目标板运行并保留日志；记录工具链、libc 与 BSP 版本。同一源码能分别构建，才有资格讨论可重复交付。

## 8. Buildroot、Yocto、BusyBox 与 QEMU：先做出一个系统

BusyBox 把许多常用命令放进较小程序；Buildroot 组织工具链、内核和用户态软件构建；Yocto/OpenEmbedded 用配方与 layer 管理定制发行版；它们不是同一层的替代品。OpenWrt 偏网络设备生态，也有自己的构建、配置与软件包体系。

| 路线 | 适合先解决的问题 | 学习成本 |
|---|---|---|
| 厂商现成镜像 | 快速验证板卡和外设 | 快，但要识别隐藏依赖 |
| Buildroot | 较直接地产生定制系统镜像 | 适合第一套完整系统练习 |
| Yocto / OpenEmbedded | 多产品配置、layer、配方和长期维护 | 概念与构建环境较多 |
| 手工根文件系统 | 理解 init、动态库和挂载 | 原理直观，长期维护工作多 |

建议先按 [G2] 官方 quickstart 使用 Buildroot。构建应由普通用户执行，不应为了绕过权限问题整套 sudo make。下面是路线示例，配置名和产物路径需以固定版本为准：

```bash
# Linux 宿主机，位于已检出的 Buildroot 源码目录
make qemu_aarch64_virt_defconfig
make
# 若当前配置生成了脚本，先读脚本再执行
./output/images/start-qemu.sh
```

构建会下载依赖，磁盘、网络与宿主依赖需提前准备。不是所有配置都有同名启动脚本。QEMU virt 只对应模拟硬件，不能把其 DTB 和内核配置直接用于 RK3588 或 STM32MP1 板。

第一次成功后，保存 defconfig，增加一个小应用，再确认镜像包含它。产品配置放入独立的板级目录或 br2-external 工程，避免大量手工修改构建输出；输出目录不是长期配置源。

Yocto 下一步再学习 machine、distro、image、recipe、layer 和 SDK：machine 描述机器，recipe 描述软件构建，image 描述系统组成。不要为了加入一个文件直接在临时 rootfs 手工修改后称为“可重复构建”。

**练习与验收**：干净环境按记录重建同一功能镜像；启动后确认应用和依赖；记录构建输入。功能可重复不自动意味着逐字节可复现，还需要控制时间戳、工具与其他构建变量。

## 9. 设备树：描述硬件，不是把驱动写进文本

设备树用于描述不能完整自发现的硬件，例如总线上的某个传感器、时钟、复位、引脚和中断连接。DTS 是文本，DTSI 便于共享片段，DTB 是编译后的数据。内核根据绑定约定解释属性并匹配驱动。

下面只是形状示意，不能直接用于任意板卡：

```dts
&i2c_controller_label {
    status = "okay";
    sensor@48 {
        compatible = "vendor,specific-chip";
        reg = <0x48>;
    };
};
```

控制器标签、地址、compatible、供电、引脚和中断必须按原理图与实际芯片填写。`status = "okay"` 只表示启用描述，不保证电源与驱动匹配都正确。`reg` 在不同父总线下含义不同，不是永远表示 I2C 地址。

阅读 [G5] Linux 设备树用法后，再查目标驱动对应的 YAML binding。使用 dtc 编译、按当前内核工具运行 dtbs_check；能编译不等于电气连接正确，binding 检查也不能代替真实硬件测试。

**练习与验收**：从板级 DTS 找一个 UART 或 I2C 节点，向上追踪控制器、pinctrl、clock 和 regulator；在原理图上找到同一接口；说明为什么节点启用后仍可能 probe defer。

## 10. 外设入门：先走标准用户态接口

很多外设已经有内核驱动，业务开发先使用子系统接口。不要为读取一个已有温度芯片先造一个私有 ioctl 协议。

| 外设 | 先认识什么 | 推荐调查顺序 |
|---|---|---|
| UART | 波特率、校验、流控、电平、帧边界 | 串口工具 → termios → 协议解析 |
| I2C | 设备地址、寄存器、ACK、组合事务 | 原理图 → adapter 能力 → 标准驱动 |
| SPI | mode、时钟、片选、位序与传输 | 数据手册 → 波形 → 适配器/驱动 |
| GPIO | 输入输出、中断、电平有效性 | pinmux → gpio character device/libgpiod |
| CAN | 位速率、仲裁 ID、过滤与错误状态 | candump/cansend → SocketCAN |
| USB | 枚举、描述符、接口与驱动 | dmesg/lsusb → 子系统接口 |

I2C 用户态接口见 [G4]。adapter 编号可能动态分配，应检查 `/sys/class/i2c-dev/` 或 `i2cdetect -l`；列出总线不同于主动扫描设备。对未知总线盲目探测可能影响某些芯片状态，应先确认设备与驱动约束。

有些寄存器读取要求“写寄存器地址 + repeated START + 读数据”组合事务，不能随意替换为两次独立 read/write。Linux I2C_RDWR 与适配器功能位需要匹配；SMBus 协议与任意 I2C 事务也不是完全相同。

串口初始化要保存/设置 termios 参数，业务协议还需要长度上限、完整帧超时和校验。RS485 半双工还要考虑方向控制、收发切换和线路终端。SPI 的 CPOL/CPHA 配错时，应用可能收到看似随机的数据。

CAN 先读 [G10] 的工具列表，用 candump 观察，cansend 发已知帧，canplayer 回放；Linux vcan 可用于接口与解析实验，不能验证真实总线的电气错误、仲裁延迟或 bus-off 恢复。

**练习与验收**：接入一个文档明确的传感器，保存原始字节与转换值；故意设置错误参数并记录差异；用逻辑分析仪核对时序。传感器值“看起来合理”不足以证明解析正确。

## 11. 驱动原理：匹配、probe、资源和退出

驱动运行在内核上下文，错误可能影响整机。先理解设备模型，再照目标内核的现有同类驱动扩展。很旧的驱动教程仍能解释部分概念，但 API、资源管理和安全实践需要按当前目标内核核对。

常见流程：设备被描述或枚举 → 总线匹配 → 调用 probe → 获取供电、时钟、寄存器、中断等资源 → 注册子系统接口。依赖未就绪时可能返回延迟探测；probe 失败必须回收已获取资源。

```text
硬件/设备树 → 总线设备模型 → 匹配驱动 → probe
                                            ↓
                             标准子系统（IIO/hwmon/input/net 等）
                                            ↓
                                      用户态应用
```

devm 等托管资源 API 可以减少退出路径遗漏，但不能替代所有生命周期设计。例如异步 work、正在执行的 IRQ 或用户请求，仍需在资源释放前停止并同步。销毁顺序通常应与获取和启动顺序相协调。

优先使用 IIO 处理采集、hwmon 处理监测、input 处理输入、netdev 处理网络等合适子系统。不是所有驱动都需要自己创建字符设备，也不应把大量临时调试接口当作稳定产品 ABI。sysfs 通常用于约定的简单属性，debugfs 也不是稳定用户接口。

**实践路线**：在虚拟机或专用开发环境阅读一个简单平台驱动，画出 probe/remove 与失败路径；再编写小型模块实验。内核模块必须用匹配的内核构建配置和头文件，不能只拿桌面头文件对着供应商内核编译。

**验收**：加载失败无资源泄漏，重复加载卸载无悬挂工作，读写边界明确，并发访问有规则。当前配套工程没有内核模块，不以用户态程序冒充驱动实践。

## 12. 中断、锁、DMA 与缓存一致性

中断通知 CPU 有事件发生。硬中断处理应尽量短，只完成必要确认和调度后续工作。线程化 IRQ 或工作队列适合部分可睡眠处理，但仍需遵守锁、资源和时限约束；softirq 等上下文不可随意睡眠。

mutex 用于可睡眠上下文中的互斥；自旋锁适合特定短临界区与上下文。普通非 RT 内核中的自旋锁临界区不能睡眠；PREEMPT_RT 会改变 spinlock_t 的实现语义，raw_spinlock_t 仍保留原始自旋行为，所以不能把一套口诀套所有配置。

DMA 让设备参与数据搬运，减少 CPU 逐字节拷贝，但需要正确的地址和所有权转换。CPU 虚拟地址、CPU 物理地址与设备 DMA 地址可能不同，尤其存在 IOMMU 时不能直接互换。先读 [G6] 的地址图与 dma_map_single/dma_mapping_error 说明。

典型 DMA 逻辑是：分配适合的缓冲 → 建立映射 → 检查错误 → 交给设备 → 等待完成 → 按方向同步/解除映射 → CPU 访问或回收。具体步骤取决于 coherent/streaming 类型和平台，不能随意删掉“在 x86 看似没用”的同步操作。

共享缓冲要回答：此时归 CPU 还是设备？另一个核能写吗？设备完成信号到达前能释放吗？缓存行是否覆盖了其他数据？`volatile` 不回答这些问题，也不等于内存屏障。

**练习与验收**：给采集环画所有权状态；模拟消费者太慢导致环满时的策略；记录溢出和丢帧。性能优化之前先证明缓冲不会在设备仍使用时被释放。

## 13. RTOS：任务、队列、优先级与 ISR

RTOS 的关键是可分析的调度与时限，而不是函数名字带“实时”。周期任务要有周期、截止时间、最坏执行时间和允许抖动。平均执行 1ms 不代表每次都能在 2ms 截止前结束。

[G7] FreeRTOS-Kernel 仓库只包含内核与端口等内容，初学者应从匹配板卡的官方 demo 开始，不应只复制几个内核文件就假定时钟、中断优先级和堆栈配置正确。

ISR 中通常不能使用可能阻塞的普通任务 API，要使用相应 FromISR API，并满足端口对中断优先级的限制。是否立即调度更高优先级任务也需要按端口规则处理。任务处理耗时工作，中断负责短通知，是常见起点。

优先级反转：低优先级任务持有高优先级任务需要的锁，中优先级任务持续运行，间接拖住高优先级任务。互斥量的优先级继承可以缓解，但不能消除所有阻塞和嵌套锁问题；二值信号量不能直接当作同样的互斥量。

```text
定时器/外设 ISR → 有界队列或任务通知 → 控制任务
                                      ↓
                              计算 → 更新输出 → 记录状态
```

队列深度按峰值与处理预算估算；静态分配有助于控制内存，但配置不足仍会失败。测量栈水位并保留溢出钩子与异常上下文，不应把某个 demo 的栈数值直接用于所有产品。

**练习与验收**：创建采样与记录两个任务，人工拖慢记录，观察队列和时限；分别用信号量与互斥量解释优先级反转；记录丢样、栈水位和最大执行时长。

## 14. 异构多核：Cortex-A 与 Cortex-M 怎样合作

Linux 侧适合管理网络、UI、日志和模型，MCU 侧适合周期采样、快速控制与保护。跨核通信不能只约定“发一个结构体”，还需要版本、字节序、长度、超时、重启代次与错误处理。

remoteproc 通常负责远端处理器生命周期；RPMsg 提供消息通信抽象；OpenAMP 提供面向裸机/RTOS 等场景的相关组件。支持与资源表、共享内存、mailbox、cache、固件布局都与平台有关。[G8] OpenAMP 与 [G9] Zephyr OpenAMP 示例适合学习两端镜像及消息流程。

建议控制消息字段：version、type、length、boot_id、sequence、deadline、payload；回复区分 received、accepted、executed 和 failed。传输层收到不代表执行器已经动作。

| 故障 | 必须约定的行为 |
|---|---|
| Linux 重启 | MCU 是否继续控制，旧命令何时失效 |
| MCU 重启 | Linux 如何识别新代次，是否重新配置 |
| 通信超时 | 谁进入降级状态，多久进入 |
| 重复/乱序命令 | 如何拒绝旧消息，如何去重 |
| 共享缓冲耗尽 | 背压、丢弃还是安全停止 |

对执行命令设置 TTL 或绝对/相对有效期，明确时钟域。如果两端时间未同步，不能直接比较彼此墙上时间。共享内存中保存地址时还要考虑双方地址空间不同，通常需要约定偏移和映射。

**练习与验收**：先跑官方 echo，再实现“设置目标值/查询实际值”；给通信注入延迟、重复和重启；证明旧命令不会在重连后突然执行。无硬件模拟能验证状态机，不能证明 cache 与中断配置正确。

## 15. 实时性、功耗与看门狗：测量整条链路

快是平均耗时短，实时是规定时间内完成。测量链路应从事件发生开始，到真实输出生效结束，中间包含采样、调度、通信、算法、总线和执行器延迟。只测一个函数会漏掉大部分排队与外设时间。

Linux PREEMPT_RT 可以降低部分不可抢占区间和调度延迟，但平台驱动、IRQ、内存分配、功耗状态与固件仍会影响尾延迟。实时策略使用不当还可能饿死系统服务，不能仅把线程优先级拉满。

建议报告 p50/p95/p99、最大观测值、超时次数与负载条件；统计分位数不是最坏情况证明。硬实时要求还需边界分析与相应验证。逻辑分析仪或示波器测 GPIO 打点可以观察实际输出，软件日志本身也有扰动。

功耗测量按工作、空闲、休眠、唤醒、联网和推理等状态分开。降低频率可能减少瞬时功率但延长任务时间，最终应比较能量与温度。热降频后的性能与冷机短测不同。

看门狗应由“业务健康”决定是否喂，不是启动一个独立线程无条件喂狗。健康条件可能包括采集进展、控制周期、存储可写与关键线程响应；也要避免云端临时不可达导致设备无限重启。

**练习与验收**：人为挂住关键工作线程，确认健康检测能发现；保留 reset cause、重启计数与最近版本；在正常、CPU/IO 压力和热稳态下分别测尾延迟与功耗。

## 16. MQTT 与断网可靠上报：协议确认不等于业务完成

MQTT 采用发布订阅，broker 转发消息。[G11] Mosquitto 提供 broker、客户端库和命令工具；[G12] Paho C 的 publish 示例帮助理解创建、连接、发布、等待和释放。上游样例中的公共服务器和固定 client ID 只是教学配置，自己的实验应改为本地与唯一 ID。

如果已在开发环境安装并启动仅用于本地实验的 broker，可在两个终端使用：

```bash
mosquitto_sub -h 127.0.0.1 -t lab/sensor/temperature -q 1
mosquitto_pub -h 127.0.0.1 -t lab/sensor/temperature -q 1 -m '23.5'
```

能收到数据只证明最小链路连通。产品需要 TLS 身份验证、主题权限、证书更新、连接超时、随机退避、离线缓存与指标。

QoS 0 可能丢，QoS 1 可能重复，QoS 2 的交付语义不等于设备到数据库及执行器端到端恰好一次。持久会话也不是无限离线存储：需配置订阅、会话/消息期限和 broker 限额；未发布的本地数据不能依靠 broker 自动补回。

推荐业务数据带 device_id、boot/session ID、sequence、schema、采样时间、接收时间、质量状态。重启后 sequence 从零开始而没有 session，会与历史数据冲突。重试必须沿用原始业务 ID，而不是每次发送生成新 ID。

断网队列要有条数、字节、保留时间、磁盘上限与溢出策略。恢复时限速重放，给新鲜数据和控制消息留资源；否则网络恢复后历史数据可能把设备再次压垮。

**练习与验收**：下一章先在无网络模型验证最棘手的确认窗口；之后替换为真实 MQTT 与业务接收服务，分别注入 broker 重启、网络黑洞、证书过期和重复消息。

## 17. 完整可运行实验：缓存、失败、重启与去重

本章用 Python 标准库 SQLite 实现最小可靠性模型，目的是不让 Linux 新手同时被工具链和硬件问题挡住。它不是驱动或 MQTT，学会流程后可以用 C/C++ 与真实网络重新实现。

```text
模拟采样 → 校验 → 本地 SQLite outbox（容量限制）
                         ↓ 读取有限批次
                    模拟接收服务 SQLite
                         ↓ 主键去重并提交
                    本地删除已确认消息
```

完整代码见 [edge_lab.py](embedded-learning/edge_lab.py)，测试见 [test_edge_lab.py](embedded-learning/test_edge_lab.py)。从仓库根目录运行，使用新的练习目录：

```powershell
New-Item -ItemType Directory -Force build/edge-lab
python JD/embedded-learning/edge_lab.py --db build/edge-lab/local.db --capacity 3 collect --count 5
python JD/embedded-learning/edge_lab.py --db build/edge-lab/local.db --remote build/edge-lab/remote.db flush --fail-after-receive
python JD/embedded-learning/edge_lab.py --db build/edge-lab/local.db --remote build/edge-lab/remote.db flush
python -m unittest discover -s JD/embedded-learning -p test_edge_lab.py -v
```

Linux 把第一条改为 `mkdir -p build/edge-lab` 并使用适合环境的 python3。第一次 collect 接受 3 条、拒绝 2 条。故障注入命令在接收端提交后、删除本地记录前抛异常并非零退出，这是预期；下一次重发，接收端识别重复，最终 pending=0、remote_unique=3。

为什么先远端提交、后本地删除？如果先删再发，发送失败就丢失。先发后删会出现重复窗口，因此接收端也需要持久化去重。这个流程实现的是“允许重试、效果去重”的教学模型，不是一个能跨两个数据库原子提交的事务。

`BEGIN IMMEDIATE` 把容量检查和插入放到同一 SQLite 写事务里，减少多个写入连接同时突破容量的问题。每次采集生成独立 session，序号在该 session 内递增；同一次消息重试时读取原始 payload，不能重生成时间戳造成同 ID 不同内容。

7 项测试覆盖容量拒绝与释放、重复/session、非法数据、重开数据库、接收后确认前失败、ID 内容冲突，以及独立进程失败后由新进程恢复。模拟故障采用异常退出，不是突然断电；没有验证 flash 写缓存、文件系统掉电一致性或真实网络。

容量按行数限制，SQLite 文件不一定因 DELETE 立即缩小，远端去重表也会增长。扩展时要增加磁盘字节预算、清理/保留策略、发送重试预算与指标；去重保留窗口必须覆盖允许重发时间，过早清理会重新产生重复效果。

**练习与验收**：将容量设成 1；暂停发送后重开进程；修改接收端制造失败；记录 accepted、full、pending、retry、unique 与冲突。所有错误路径都要说明数据在哪里，而不是只看程序有没有崩溃。

## 18. OTA：升级的是系统状态，不只是一个文件

OTA 需要同时处理镜像可信、写入中断、启动选择、健康确认和数据兼容。下载成功与安装成功不同，启动新内核与业务健康也不同。[G13] RAUC 与 [G14] SWUpdate 是可研究的成熟方案，不建议把一段 shell 写分区脚本当完整产品 OTA。

```text
当前槽 A 运行 → 下载并验证 bundle → 写非活动槽 B
                                       ↓
                              设置有限次数试启动
                                       ↓
                              B 启动 + 业务健康检查
                               ↙              ↘
                          确认新版本        失败回滚 A
```

A/B 不是简单把 rootfs 分两份：bootloader 必须理解启动尝试与确认状态，状态更新也要可靠，布局、内核/DTB、恢复环境和共享数据都要匹配。RAUC mark-good 类操作应由真实健康条件触发，不能开机立即确认。

签名证明来源与完整性，普通哈希只能检验是否与某摘要相同。设备端需要受信任公钥与轮换机制；安全启动验证启动链，OTA 签名验证更新来源，防回滚控制旧版本重放，它们解决不同问题。

共享数据分区中的数据库迁移尤其容易破坏回滚：新版本修改 schema 后，旧版本可能无法读取。设计向前/向后兼容窗口、延迟不可逆迁移或备份恢复，并测试升级后再回滚的数据状态。

验证矩阵应覆盖下载中断、写入中断、启动标记切换、新版本内核失败、应用不健康、磁盘满、签名错误、错机型包、数据迁移失败和连续重启。断电试验要在受控测试设备与恢复条件下执行，不能从单次成功断言“任意时刻断电可恢复”。

**练习与验收**：先画分区与状态机，再在 QEMU/测试板实现 A→B→确认及 A→B→失败→A；记录每个失败点还能启动哪个版本，保留包摘要、版本和回滚原因。

## 19. 边缘 AI：先保证输入输出一致，再追求 NPU 速度

端侧模型部署通常包括训练模型导出、算子检查、转换、量化、运行时集成、前后处理与实测。ONNX 是模型表示格式之一，不保证所有运行时都支持所有算子；NPU TOPS 也不等于应用实际吞吐。

RKNN 工具链见 [G15]，模型示例见 [G16]；ONNX Runtime 入口见 [G17]。PC 上使用 RKNN-Toolkit2 转换和评估模型；板端使用 RKNN-Toolkit-Lite2 的 Python 接口或 RKNN Runtime 的 C/C++ 接口，底层由 RKNPU 驱动访问硬件。选择前先列硬件、BSP、驱动、运行时、模型转换器和模型版本的兼容矩阵，不能把另一块板的二进制库直接混用。

```text
原模型 → 固定版本导出 → 算子/shape 检查 → 转换与校准
                                                 ↓
摄像头/文件 → 解码/resize/归一化 → 推理 → 后处理 → 业务输出
                   ↓                 ↓            ↓
                  时间、内存、精度与质量观测
```

前处理要逐项对齐 RGB/BGR、NCHW/NHWC、resize/letterbox、归一化、量化零点与尺度；后处理要对齐阈值、坐标恢复和 NMS 等。模型加载成功但结果很差时，先比较相同输入上的中间输出，而不是立即重新训练。

PTQ 使用代表性校准集，QAT 在训练中考虑量化影响。校准数据数量没有通用保证，必须覆盖真实光照、噪声、距离和异常工况。某算子回退到 CPU 可能造成性能跳变，需要检查实际执行路径。

批处理可以提高吞吐，也会增加等批时间和内存；实时单路输入不一定适合大 batch。衡量采集到结果的端到端延迟、帧龄、精度、丢帧、CPU/NPU 利用率、温度、功耗与热稳态表现，不能只报一次纯推理耗时。

**练习路线**：先在 CPU 跑固定输入建立基线；用官方模型完成目标板推理；替换自己的模型并逐步对比；最后再接摄像头与多路数据。当前便携实验不运行模型，不提供未经测量的帧率承诺。

## 20. 服务托管、容器和边缘运维

一个板子上的单一服务，systemd 或简洁的 init 管理通常足以起步；需要多应用隔离与一致交付时再考虑容器；需要多节点编排时再评估 K3s。边缘设备不是因为“在边缘”就必须运行 Kubernetes。

[G19] systemd.service 区分 oneshot、exec、notify 等类型与启动判定。进程启动成功不代表业务就绪；长服务需要适当就绪通知、重启限速与依赖关系。`After=network.target` 或 network-online.target 都不等于远端云服务一定可达，应用仍需重试。

配套 [edge-lab.service](embedded-learning/edge-lab.service) 只执行一次采集，采用专用用户和 StateDirectory，它不是守护进程。安装前需创建用户、部署脚本与验证目标 systemd 版本；当前没有在 Linux 加载验证。

容器共享宿主内核，不能修复宿主驱动或 ABI 不兼容。设备访问、GPU/NPU 运行库、挂载、网络与数据目录都要显式配置，避免为了方便把整个容器设为高权限。只读根文件系统仍需要为日志、数据库与临时文件提供正确可写位置。

[G18] K3s 可以作为轻量 Kubernetes 研究入口，但控制面、网络、镜像分发、证书、存储与离线恢复仍有成本。必须对目标设备的 RAM、磁盘写入量与运维能力做预算。

**练习与验收**：在目标系统执行服务启动、停止、配置错误与重启测试；限制数据目录与设备权限；模拟云不可达，确认不会无限快速重启。日志轮转、指标上报和诊断导出都要有大小上限。

## 21. 安全、量产、功能安全与可追溯交付

设备安全从身份开始：每台设备应有可管理的唯一身份和凭据，禁止把同一私钥直接烘焙到全部镜像。配置与日志避免泄漏密钥；更新机制需要证书轮换和吊销计划。TPM 工具入口 [G20] 可帮助进一步学习密钥保护，但 TPM 不会自动让整个产品安全。

量产交付至少包含镜像、烧录方法、分区布局、硬件版本、校准数据、设备身份注入、出厂自测、恢复模式、版本追溯和售后诊断。开发板启动成功不代表已经具备批量生产能力。

| 质量问题 | 需要的证据 |
|---|---|
| 长期运行 | 内存/句柄/磁盘/温度趋势、异常统计 |
| 启动与恢复 | 完整启动日志、reset cause、恢复步骤 |
| 硬件通信 | 波形、总线错误计数、软硬件版本 |
| 升级 | 包签名、版本、状态变迁、失败与回滚记录 |
| 供应链 | SBOM、许可证、依赖版本与漏洞处理记录 |

ISO 26262 关注汽车功能安全生命周期，ASPICE 关注开发过程能力，两者不能互相替代。ASIL 不是开发者为了显得可靠而自行贴的标签，而来自相应的系统安全分析与流程。双核、看门狗或冗余代码也不自动构成功能安全合规。

对于原文的照明/控制场景，应把安全目标、故障反应时间、降级模式、需求—设计—代码—测试追踪与变更记录连接起来；PWM 精度还要结合时钟分辨率、频率、通道同步、抖动和实际驱动输出测量。

**练习与验收**：为一个故障建立完整链：通信超时 → 检测条件 → 指定时限内降级 → 测试注入 → 波形与日志证据。学习项目只能展示方法，不应宣称通过认证。

## 22. 四条落地项目路线：每一步都有完成标准

### A. 工业传感器边缘网关

**场景**：采集 UART/Modbus/CAN 设备，经 MQTT 上传，断网可恢复。第一版只支持一种协议与只读采样。

```text
传感器 → Linux 标准设备接口 → 协议适配器 → 统一采样模型
                                                ↓
                        配置/健康/日志 ← 有界缓存与本地 outbox
                                                ↓
                                        限速发送 → 云端去重
```

阶段 1 跑通第 17 章模拟器；阶段 2 用 C 用户态接入一只传感器并记录原始值；阶段 3 接入本地 broker 和业务接收端；阶段 4 加入服务托管、日志、磁盘配额和 OTA。

验收建议：断网期间缓存不超约定预算，恢复后不重复计数；拔线不拖死其他设备；异常退出后仍能追踪待发消息；长时间运行资源受限。项目报告说明采样率、负载、保留时间和实测结果，不能用建议目标当已达到指标。

### B. Cortex-A + Cortex-M 异构控制平台

**场景**：Linux 管理配置、网络和算法，MCU 负责采样、PWM 与保护，适合学习原文中的 SoC/照明数据通路。

```text
配置/算法（Linux） → 带版本与期限的命令 → RPMsg/共享内存
                                                   ↓
                                    MCU 状态机 → 定时器/PWM → 输出
                                                   ↓
                                   执行反馈/故障 → Linux 诊断
```

阶段 1 各核独立启动并记录版本；阶段 2 echo 通信；阶段 3 命令确认与实际状态查询；阶段 4 超时、乱序、旧代次、核重启与失联降级测试。先控制无危险的测试负载，不直接接关键执行机构。

验收必须区分命令到达与执行完成；测量周期抖动、跨核延迟和失联反应时间；证明 Linux 更新或故障时 MCU 的行为符合约定。硬件测量、故障注入和需求追踪是作品集重点。

### C. RK3588 边缘视觉盒子

**场景**：摄像头采集、NPU 推理、结果上报，可选显示和录像。

```text
摄像头 → 解码/预处理 → 最新帧缓冲 → RKNN 推理 → 后处理 → 结果上报
                └→ 独立录像队列 → 分段存储
健康管理：帧龄、队列、温度、功耗、模型版本、丢帧与重连
```

阶段 1 官方模型处理固定图片，建立精度基线；阶段 2 对比自定义模型的 CPU 与 NPU 输出；阶段 3 接入视频并限制每条队列；阶段 4 热稳态、断流恢复、磁盘满与模型回滚。

验收同时给精度、端到端延迟分位数、吞吐、内存、功耗和温度。慢处理时不能无限积帧；录像与预览有不同策略；模型和运行时升级需要兼容性验证。

### D. 可升级的最小 Linux 产品系统

**场景**：从 Buildroot/QEMU 起步，形成可移植到开发板的基础产品镜像。

阶段 1 构建最小系统并启动自己的应用；阶段 2 分离只读系统与可写数据，定义健康检查；阶段 3 选择 RAUC/SWUpdate 设计双槽与回滚；阶段 4 加入身份注入、诊断包、SBOM 和恢复文档。

验收提供从源码到镜像的完整输入、构建命令与摘要；证明错误签名/错机型包被拒绝；新版本不健康时能回到旧版；数据迁移有兼容方案。QEMU 通过后仍要对目标存储和 bootloader 执行专门验证。
