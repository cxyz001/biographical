# 音视频零基础到流媒体平台实战

> 根据[音视频与流媒体岗位知识索引](07-音视频与流媒体.md)整理。GitHub 检索与正文核查日期：2026-10-23。学习目标：从“知道一个文件为什么能播放”，走到“能设计、验证和运维一套视频平台”。配套代码：[media-learning](media-learning/README.md)。

第一次学习先完成第 1—9 章，做出能分析、转换和播放的本地媒体工具，再进入网络、切片、设备和平台。各章解释问题与原理，配合练习和验收条件。C/C++、网络和 Linux 不熟悉时，可先用 Python 与 FFmpeg 命令观察现象，再读底层源码。

## 1. 先看全貌：视频从哪里来，又到哪里去

手机拍摄时，摄像头先产生图像，麦克风产生声音。原始数据太大，编码器将其压缩；封装器把音视频和时间信息组织到文件或网络消息里；接收端按相反顺序处理，最后呈现画面和声音。

```text
摄像头/麦克风
  → 原始图像与 PCM 音频
  → 编码：H.264 / H.265 / AAC / Opus
  → 封装：MP4 / MPEG-TS / FLV，或按 RTP 载荷规则打包
  → 文件存储或网络传输
  → 解封装/重组 → 解码 → 按时钟播放
```

三个容易混淆的东西：H.264 是视频编码，MP4 是容器，RTSP 是会话控制协议。把文件后缀改成 `.mp4` 不会改变编码，也不会得到一个可播放的 MP4。

岗位中的工作可拆为五条链路：采集与接入、实时分发、录像回放、AI 分析、语音交互。它们复用部分基础设施，但可靠性和延迟目标不同。例如，实时 AI 可以丢过时的已解码图像，录像一般不能为了低延迟随意丢数据。

**练习**：列出一次远程监控预览经过的组件，每个组件注明输入、输出、缓冲和失败方式。完成标准是能解释“接口返回成功，但画面黑屏”为什么可能是媒体链路故障。

## 2. 像素与帧率：为什么原始视频这么大

一张 RGB 图像由像素组成，RGB24 通常每像素占 3 字节。1920×1080、30 帧/秒时，紧密排列的 RGB 数据约为 `1920×1080×3×30 = 186624000 B/s`，约 186.6 MB/s，不含行对齐和元数据。

YUV 将亮度与色度分开。YUV420P 常见存储量约为每像素 1.5 字节，所以同尺寸每帧约 3.11 MB。NV12 同样是 4:2:0，但 UV 交错布局不同。不能因为字节数一样就直接把一种格式当另一种读。

| 概念 | 初学者的理解 | 工程上要检查的细节 |
|---|---|---|
| 分辨率 | 一帧有多少像素 | 裁剪、旋转、宽高对齐 |
| 帧率 | 每秒呈现多少帧 | 25/30/29.97、可变帧率、丢帧 |
| stride / linesize | 每一行实际跨多少字节 | 可能大于有效宽度，不能整帧盲目 memcpy |
| 色彩空间 | 数值怎样对应颜色 | BT.601/709/2020、full/limited range |
| 像素格式 | 像素怎样放进内存 | RGB/BGR、YUV420P/NV12、位深 |

**现象诊断**：颜色发紫可能是 UV 顺序错误；画面倾斜可能是 stride 处理错误；整体发灰可能是色彩范围错误。这些都不一定是编码器坏了。

**练习**：算出 1280×720、25fps 的 RGB24 与 YUV420P 数据量。再比较 2Mbps 压缩视频，理解压缩比为什么很高。注意 MB/s 与 Mb/s 相差 8 倍。

## 3. 音频从 PCM 开始：采样率、位深和声道

PCM 是按固定时间间隔记录声音幅值。16kHz 表示每秒每声道 16000 个样本；16bit 表示每个样本通常占 2 字节；单声道两秒数据量为 `16000×2×1×2 = 64000` 字节。WAV 文件还包含文件头和可能的其他块，不等于纯 PCM 字节数。

采样率限制可表达的频率范围。采样前需要抗混叠滤波；把 16kHz 改写为 48kHz 文件头不是重采样，会改变播放速度与音调。重采样要真正计算新的样本。

AAC 常用于 MP4/HLS，Opus 常用于实时通话。压缩音频也有帧和编解码延迟。例如 48kHz 下 1024 个样本的时长为约 21.33ms，但并非所有编码器都固定使用这个帧长。

```powershell
# 在仓库根目录运行，不需要 FFmpeg 或麦克风
New-Item -ItemType Directory -Force build/media-lab
python JD/media-learning/media_lab.py tone build/media-lab/tone.wav
python JD/media-learning/media_lab.py inspect build/media-lab/tone.wav
```

预期单声道、16kHz、16bit、32000 个样本、2 秒、64000 字节 PCM。这个正弦波只用于格式实验，不能用于检验 ASR 准确率。

**完成标准**：能解释采样率与码率的区别，能在代码里区分字节数、样本数、声道数和持续时间。

## 4. 编码原理：I/P/B 帧、GOP 与码率

视频压缩利用画面内部相似性和相邻画面的相似性。I 帧主要利用帧内信息；P/B 帧利用参考关系。IDR 是用于刷新参考状态的重要随机访问点，不能简单把所有 I 帧都当成任意位置可独立起播的 IDR。H.265 还有 CRA 等随机访问类型。

GOP 表示一组图像的组织方式。25fps、关键帧间隔 50 帧意味着大约 2 秒一个关键帧。短 GOP 往往让新观众更快获得可解码入口，但相同画质可能需要更高码率。B 帧可提高压缩效率，也可能引入重排延迟。

CBR/VBR/CRF 是不同的质量与码率控制思路。`-b:v` 不等于每秒严格相同字节数，`-maxrate` 与 `-bufsize` 要结合编码器的 VBV 模型理解；bufsize 是比特容量，与码率之比才是时间尺度。

原文的“直播必开 zerolatency”应改成场景判断：交互直播通常需要减少 lookahead 和 B 帧；允许数秒延迟的直播可能更重视压缩率。每个编码器的参数也不同，不能把 libx264 的选项原样复制给 NVENC。

**练习**：用第 6 章素材生成两个 GOP 长度不同的文件，记录大小、关键帧位置和起播体验。完成标准是能解释“降低码率后为什么运动画面先变糊”。

## 5. 容器与时间：先懂 PTS、DTS 和 timebase

容器组织多个流、编码参数、时间戳和索引。MP4 常见非分片文件需要完成 moov 等元数据；`faststart` 可以将相应索引移到前部，改善 HTTP 渐进下载。分片 MP4 使用初始化段与后续片段，不能概括为“所有 MP4 索引都在文件尾”。

TS 的固定包长和同步机制有利于传输与恢复，但它不是自动可靠协议，丢失关键内容仍会花屏。FLV、PS、TS 和 MP4 也不是任意编码都能随意互换。

**时间戳是带单位的整数**：`pts=90000, timebase=1/90000` 表示 1 秒。`pts=90000, timebase=1/1000` 表示 90 秒。timebase 就像尺子的刻度，数值本身没有独立意义。

```powershell
python JD/media-learning/media_lab.py timeline
```

输出把 90000 个 `1/90000` 秒单位换为 1000 个毫秒单位。示例用有理数保存精度，不模拟 FFmpeg 的整数舍入和特殊时间戳规则。

PTS 是呈现时间，DTS 是解码时间。存在帧重排时，按解码顺序读取的包，其 PTS 不一定单调；不能为了“修复”强行把所有 PTS 排序。音频一般按连续样本时钟推进，视频按目标显示时刻调度。跨设备绝对时间对齐还需处理 NTP/PTP、设备时钟偏差和网络时延。

音画偏差恒定时，先查起点偏移；偏差逐渐变大时，查采样时钟漂移、错误采样率、丢样本和 timebase 换算。不能把媒体 PTS 直接当 UTC 入库。

## 6. 第一个 FFmpeg 实验：生成、检查、转封装和转码

安装包含 `ffmpeg` 和 `ffprobe` 的工具包，优先从 FFmpeg 官方下载页选择发行来源。先执行版本和功能检查；不同平台的二进制是否含 libx264、AAC、设备支持和硬件接口并不相同。以下命令使用单行，PowerShell 与 Bash 都便于复制。

```bash
ffmpeg -version
ffprobe -version
ffmpeg -hide_banner -encoders
ffmpeg -hide_banner -devices
ffmpeg -hide_banner -f lavfi -i testsrc2=size=640x360:rate=25 -f lavfi -i sine=frequency=1000:sample_rate=48000 -t 12 -c:v libx264 -pix_fmt yuv420p -g 50 -keyint_min 50 -sc_threshold 0 -c:a aac -movflags +faststart sample.mp4
ffprobe -v error -show_streams -show_format -of json sample.mp4
```

如果提示 `Unknown encoder libx264`，应换用含该编码器的构建，或根据 `-encoders` 修改方案，不能据此判断命令语法错误。默认不加 `-y`，避免练习覆盖已有文件。

```bash
# 转封装：编码不变，容器变化
ffmpeg -i sample.mp4 -map 0:v:0 -map 0:a:0 -c copy sample.ts
# 转码：缩小尺寸，重新编码
ffmpeg -i sample.mp4 -vf scale=320:180 -c:v libx264 -preset veryfast -crf 25 -c:a aac small.mp4
# 提取一张图像；输入前 seek 较快，准确性还取决于解码和输入
ffmpeg -ss 3 -i sample.mp4 -frames:v 1 snapshot.jpg
# 导出供 ASR 使用的单声道 PCM WAV
ffmpeg -i sample.mp4 -vn -ac 1 -ar 16000 -c:a pcm_s16le speech.wav
```

`-map` 控制流选择，`-c copy` 控制是否重编码；即使 copy 也要进行协议解析、缓冲和封装，不能称为完全零拷贝。某些转换还需要 bitstream filter，FFmpeg 在部分格式间会自动插入，遇到问题要查看日志。

**验收**：比较输入输出的编码名称、分辨率、duration 和实际解码结果。仅凭命令退出码为 0，不能证明观感、音画同步和所有播放器兼容。

## 7. 采集：摄像头和麦克风怎样进入程序

Linux 摄像头常见 V4L2，Windows 可用 DirectShow/Media Foundation，macOS 常用 AVFoundation。先枚举设备，再选择设备实际支持的像素格式、尺寸和帧率；不要假设每个 USB 摄像头支持 1080p30 原始输出。[S3] 是 FFmpeg 的输入设备说明。

```bash
# Linux，需摄像头、访问权限与相应 FFmpeg 构建
ffmpeg -f v4l2 -list_formats all -i /dev/video0
ffmpeg -f v4l2 -framerate 25 -video_size 640x480 -i /dev/video0 -t 10 -c:v libx264 camera.mp4
# Windows：该命令用于列举设备，通常不产生媒体文件
ffmpeg -list_devices true -f dshow -i dummy
```

V4L2 的典型 MMAP 流程是查询能力、协商格式、申请缓冲、映射、QBUF、STREAMON、DQBUF、使用、QBUF。采集缓冲由驱动和应用共同管理，交给异步处理前必须明确所有权：如果立即归还驱动却继续使用该地址，画面可能被下一帧覆盖。复制或引用可共享缓冲都需要正确的生命周期。

缓冲数量不是固定为 4 就最优，需结合驱动约束和处理耗时测量。MMAP 减少特定拷贝，并不保证整条采集—滤镜—编码链路零拷贝。

**验收**：拔插设备、权限不足、分辨率不支持时，程序有可定位错误；重连有退避和次数上限，不能在失败循环中占满 CPU。

## 8. 读懂 libav：从官方 remux 示例进入 C/C++

先读 FFmpeg 官方 [remux.c][S1]，再读 [decode_video.c][S2]。前者处理容器中的包，后者展示解码器与 parser 的使用，两者输入假设不同，不能简单拼接就变成通用播放器。

```text
打开输入 → 探测流 → 选择流并建立映射
  → 创建输出流并复制 codec parameters
  → 打开输出 IO → 写文件头
  → 循环读取 AVPacket
      → 流编号映射 → 时间基转换 → 交错写入
  → 写尾部 → 释放 packet、IO 与 context
```

官方示例的关键是流映射和 `av_packet_rescale_ts`。下面是流程片段，不是独立可编译程序；完整错误处理、资源释放请跟随上游文件：

```c
/* in_stream/out_stream/pkt 由完整 remux 流程建立。 */
av_packet_rescale_ts(pkt, in_stream->time_base, out_stream->time_base);
pkt->stream_index = output_index;
pkt->pos = -1;
ret = av_interleaved_write_frame(out_ctx, pkt);
/* 根据 API 的所有权约定处理后续引用与清理。 */
```

解码使用 send/receive 状态机：送包后可能得到零帧、一帧或多帧；`EAGAIN` 表示要推进另一侧，不是休眠后无条件重复；结束时按 API 约定送 NULL 包并接收剩余帧。`AVPacket` 是压缩数据包，`AVFrame` 是解码后的图像/样本，两者不是一对一关系。

不要新写基于 `av_register_all`、`avcodec_decode_video2` 的教程工程。编译时安装与运行库匹配的开发包，通过 pkg-config 获取依赖；以所固定 FFmpeg 版本的示例为准。

Linux 开发环境可以按以下步骤编译上游完整示例，而不是编译本章的片段。`<已安装开发库对应的标签或提交>` 需替换成真实版本；头文件与库不匹配时先修复开发环境。示例源文件的许可证和版权说明须保留。

```bash
git clone https://github.com/FFmpeg/FFmpeg.git
cd FFmpeg
git checkout <已安装开发库对应的标签或提交>
pkg-config --modversion libavformat libavcodec libavutil
cc doc/examples/remux.c -o remux $(pkg-config --cflags --libs libavformat libavcodec libavutil)
./remux ../sample.mp4 ../remuxed.ts
```

这些是 Bash 命令，`$()` 使用 pkg-config 生成编译参数。若 sample.mp4 不在父目录，修改输入路径；编译与执行尚未在本机验证。

**练习**：给 remux 工具增加“只保留第一条视频和第一条音频”“打印首尾 PTS/DTS”“输出错误定位”三项能力。验收包括无音频、多流、损坏输入和不兼容输出容器。

## 9. GStreamer：把媒体处理组织成管道

FFmpeg 擅长命令处理与 libav 集成，GStreamer 提供 element、pad、caps 和 bus 等管道抽象。source 产生数据，filter 转换数据，sink 消费数据；caps 描述格式协商，bus 报告错误和结束事件。[S4] 的 hello-world 从创建管道、进入 PLAYING 到接收消息和释放资源展开。

```bash
# 需 GStreamer 命令行工具、视频输出插件与图形环境
gst-launch-1.0 videotestsrc num-buffers=100 ! videoconvert ! autovideosink
```

`tee` 可以分支，`queue` 可以建立独立调度边界，但默认 queue 仍可能因满而阻塞上游。预览、录像和 AI 共用一条无隔离的处理路径时，一条慢分支可能拖住其他分支。设置队列上界、泄漏策略和独立进程时，先确认哪个分支允许丢帧。

**练习**：画出预览与录像两分支管道，故意让一个分支变慢，记录其他分支受影响的条件。不要只增加线程数而不测队列长度。

## 10. 网络基础：RTP、RTCP、RTSP 与 RTMP

RTSP 负责描述与控制会话，媒体常用 RTP 承载；RTCP 提供接收质量反馈及时间映射等信息。常见 RTSP 交互包括 DESCRIBE、SETUP、PLAY 和 TEARDOWN，不同设备支持的细节不同。

UDP 不保证到达、顺序与去重，接收端需要按序号和时间戳重组；RTP 序号会回绕，一帧可以跨多个 RTP 包。TCP 能可靠有序传输，但丢包会引发队头阻塞和积压。因此“弱网一律切 TCP”不是通用结论，应比较花屏、停顿和延迟。

RTMP 常用于推流，其传统生态使用 H.264/AAC 与 FLV 相关封装。浏览器不再依赖 Flash 播放 RTMP，通常由服务端转换成 HLS、WebRTC 或其他受支持方式。扩展 RTMP 的编解码支持要检查客户端与服务端版本。

```bash
# 有可访问的测试摄像机后再执行；不要把生产账号写进公开命令记录
ffmpeg -rtsp_transport tcp -i rtsp://127.0.0.1:8554/camera -t 10 -c copy captured.mkv
```

**抓包练习**：检查 SDP 编码信息、RTP 序号、时间戳、RTCP SR/RR 与实际端口。不应只看 RTSP 控制端口是否连通；“控制成功但没有媒体”常与 UDP 端口、地址通告、NAT 或编码不兼容有关。

## 11. 搭一个媒体服务：先理解转发，再考虑转码

[MediaMTX][S7] 可作为多协议媒体路由入门，[SRS][S5] 常用于直播与实时音视频，[ZLMediaKit][S6] 在监控与多协议转换中很常见。先选一个完成实验，再对照另两个的架构，避免同时运维三套却没理解链路。

按照各仓库当前 README 获取匹配操作系统的发行包或容器镜像。将版本号/提交和配置一起保存，不把 `latest` 当可复现交付。以下以本机 MediaMTX 原生程序、默认启用 RTSP 8554 为实验前提，先按其 README 启动服务，再执行：

```bash
# 推流进程；-re 让文件接近实时读取，不能增加实际带宽
ffmpeg -re -stream_loop -1 -i sample.mp4 -c copy -f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/demo
# 另一终端：工具包需包含 ffplay
ffplay -rtsp_transport tcp rtsp://127.0.0.1:8554/demo
```

先验证 RTSP 推拉闭环，再按所固定服务版本的 README 启用 HLS/WebRTC 输出，并使用该版本给出的播放地址。服务“支持 WebRTC”不代表能把任意 H.265/AAC 输入原样变成所有浏览器可播的流，可能需要 H.264/Opus 转码或不同的输出组合。

**验收**：一个推流端、两个播放端，关闭一个播放端不影响另一个；停止推流后显示离线并清理会话；恢复推流后按规则重连。记录服务 PID、流 ID、编码、在线人数与出口带宽。

## 12. HLS 与 Web 播放：切片不是简单拆文件

HLS 通过播放列表描述媒体切片。客户端需要获取列表、下载片段、缓冲再解码。常规 HLS 延迟受片段长度和客户端缓冲影响；标准 LL-HLS 涉及部分片段和服务端/客户端配合，不能把 FFmpeg 实验性 LHLS 的选项直接当作标准 LL-HLS。

```bash
# 在 sample.mp4 所在目录创建 hls 子目录；以下为 VOD 实验
ffmpeg -i sample.mp4 -c:v libx264 -g 50 -keyint_min 50 -sc_threshold 0 -c:a aac -hls_time 2 -hls_playlist_type vod -hls_segment_filename hls/seg_%03d.ts hls/index.m3u8
python -m http.server 8080 --bind 127.0.0.1
```

先创建目录再执行，并在当前练习目录启动 HTTP 服务。不要在仓库根目录或含凭据的目录启动目录服务。打开网络资源地址 `http://127.0.0.1:8080/hls/index.m3u8` 可检查列表下载；这不代表每个浏览器直接导航都能播放。

[hls.js][S8] 在支持 MSE 的浏览器中解析 HLS 并送入媒体播放链路；部分平台可由 video 元素原生播放 HLS。实际应用先检查原生 HLS 或 Hls.isSupported，再选择路径。HTTPS 页面不能随意加载 HTTP 媒体；跨域时要正确设置 CORS；自动播放可能要求静音或用户操作。

HLS 切片时长常是目标值，实际边界依赖关键帧。`independent_segments` 是对内容独立性的声明，不能把它当作自动修复关键帧的开关。多码率自适应还需要多个编码档位、关键帧对齐与主播放列表，不是只生成两个文件即可。

**验收**：用开发者工具查看列表和片段请求，观察 404、CORS、解码错误和缓冲事件；把“资源下载失败”与“编码不支持”区分开。

## 13. WebRTC：信令、ICE、DTLS 与 SRTP

WebRTC 是一组实时通信能力，不是单独一个 WebSocket 协议。WebSocket/HTTP 常用于交换 SDP 和 ICE candidate；真正的媒体走协商出的传输通道。建立流程可先看官方 [pc1 示例][S9]，它在同一页面连接两个 peer，适合观察 offer/answer 和 candidate，但不是公网多人会议产品。

```text
浏览器 A                        信令服务                     浏览器 B
创建 offer / 本地描述    →       转发 offer         →      设置远端描述
设置远端 answer          ←       转发 answer        ←      创建 answer
ICE candidates           ↔       转发候选           ↔      ICE candidates
候选对连通性检查 → DTLS 协商 → SRTP 音视频传输
```

STUN 协助发现映射地址，TURN 在必要时中继。不是按固定顺序“先主机、再 STUN、最后 TURN”逐级尝试，而是收集候选、形成候选对并按 ICE 机制检查和选定。不要承诺固定百分比的用户需要 TURN；网络分布和策略不同，结果差别很大。

[coturn][S11] 是常见 TURN/STUN 实现。生产需要评估 UDP、TCP/TLS 可达性、证书、认证、短期凭据、relay 端口范围与中继带宽成本；只放行 3478 不代表媒体中继端口可用。不得把匿名开放 TURN 当公开服务。

摄像头/麦克风通常需要 HTTPS 或浏览器允许的 localhost 安全上下文，并经过权限授权。服务端媒体处理可读 [aiortc server 示例][S16]；Go 方向可读 [Pion examples][S10]。这些库解决协议基础，但不会自动实现用户鉴权、房间权限、录制和多租户隔离。

**实验顺序**：本机双 peer → 同局域网两端 → 跨网络 → 强制 relay 验证 TURN。观察 getStats 的 candidate-pair、RTT、jitter、丢包、码率和解码帧，不只检查 ICE connected。

## 14. 弱网与低延迟：用预算定位，不靠堆参数

端到端延迟是采集、编码、上行、服务端排队、下行、接收缓冲、解码与呈现之和。首帧时间是用户发起播放到首帧呈现，两者不是同一指标。GOP 缓存常能减少等待关键帧的时间，但实际落后直播多久取决于缓存起点、发送策略与播放器追赶，不是恒定增加完整一个 GOP。

| 环节 | 应测量的量 | 常见动作与代价 |
|---|---|---|
| 采集 | 曝光、缓冲深度、帧间隔 | 缩短曝光可能使画面更暗 |
| 编码 | 每帧耗时、lookahead、B 帧 | 低延迟配置可能损失压缩效率 |
| 网络 | RTT、抖动、丢包、可用吞吐 | 降码率可能损失清晰度 |
| 队列 | 字节数、最旧数据年龄 | 丢弃须理解码流依赖 |
| 播放 | 解码、jitter buffer、渲染耗时 | 缓冲缩短可能增加卡顿 |

NACK 请求重传，只有来得及赶上播放期限时才有帮助；FEC 用额外冗余抵抗部分丢失；PLI/FIR 请求新的解码入口，频繁请求会增加编码和带宽压力。拥塞控制估计可用带宽，并影响编码目标；不是“发现丢包就无限重传”。

**测量实验**：先在局域网记录基线，再在隔离测试环境注入带宽限制、延迟、抖动和丢包，每次只改一种条件。用被摄时钟与播放画面同屏拍摄估算玻璃到玻璃延迟，跨机器日志测量需时钟同步。提交 P50/P95 延迟、冻结时长、画质变化、测试版本和条件，不只写“延迟 300ms”。

## 15. 硬件加速与多路容量：吞吐不等于零延迟

NVDEC/NVENC、QSV、VAAPI、VideoToolbox 等接口覆盖不同硬件与平台能力。解码、滤镜、编码是否都在设备内完成，决定是否有显存/内存拷贝。`hwdownload` 是回传主存，不能放进步骤后就声称全程零拷贝。

编码会话限制、支持的编码格式/位深/分辨率由型号、驱动和 SDK 决定，不能把消费级卡固定写成 2—5 路。硬件编码质量也应在相同码率、preset 和场景下比较，不能笼统断言总比软件差。

容量从数量级开始算：100 路各 2Mbps 输入约 200Mbps；每路平均 5 个观众则纯媒体出口约 1Gbps，尚未计入协议和重传。2Mbps 连续录一天约 21.6GB，100 路约 2.16TB/天，保留 7 天约 15.12TB，另需冗余与水位余量。

解码内存也需预算：一张 1080p YUV420 图像约 3.11MB，每路保留 10 张、100 路约 3.11GB，仅是图像有效数据，不含对齐、参考帧、上下文和其他缓冲。原始 AI 帧队列尤其容易吃光内存。

**验收**：逐路加压，记录 CPU、GPU、显存、内存、文件句柄、网卡、磁盘吞吐和帧处理耗时；明确哪项先到瓶颈。故障时是否允许软编降级需容量约束，不能所有流同时切软编导致雪崩。

## 16. GB28181 与 ONVIF：接入的是设备生命周期

ONVIF 常用于发现、能力查询、获取媒体配置/URI、事件与 PTZ 等；它不是一种视频编码，也不是所有功能都由一个 Profile 覆盖。需要核对设备支持的 Profile、认证方式、时间设置与厂商差异。

GB28181 涉及注册、心跳、目录、点播、回放、控制与级联等。SIP 信令负责建立和控制会话，媒体常见 PS over RTP，但版本、会话模式和设备实现需要逐项确认。RTP 包边界、PS 包边界、编码 NAL 边界不能当成同一个边界。

```text
设备/下级平台
   ├─ SIP 注册/心跳/目录 → 设备与信令服务 → 设备、通道和会话状态
   └─ RTP 媒体           → 媒体节点       → 转发/录像/播放
平台 API → 权限检查 → 发起会话 → 分配节点和端口 → 信令协商 → 媒体就绪
```

检索并读取了 [WVP 项目][S12] 的 README：项目将核心信令和设备管理后台与 ZLMediaKit 媒体服务配合，并列出设备接入、级联和普通流转国标等场景。它适合用来研究控制面与媒体面如何协作，但 README 的功能声明不等于本次已经验证这些功能。资料记录保留了首次错误命名空间的 404 和正确仓库的成功读取结果。学习时需结合其实际版本文档与适用标准，不用项目 README 替代 GB/T 标准原文。

**联调清单**：设备/通道 ID、注册地址、鉴权、端口、信令传输方式、媒体地址、RTP 模式、SSRC、编码、时区与 NTP。状态机至少区分注册成功、通道在线、点播协商成功、实际收到媒体与可解码。对端返回 200 OK 不等于正在出图。

**验收**：覆盖设备掉线重注册、重复注册、点播超时、端口分配冲突、停止会话、跨 NAT、回放和时间偏移，保留信令与媒体抓包关联 ID。

## 17. 录像与回放：文件和数据库怎样保持一致

录像系统既要产生可独立打开的片段，又要建立时间索引、处理删除和崩溃恢复。普通 MP4 在异常终止后可能缺失关键元数据，分片 MP4 或 TS 具有不同恢复特性，都不能直接保证断电零丢失。

建议索引字段：租户、设备、通道、UTC 起止时间、媒体时间范围、存储路径、大小、编码参数、校验信息、状态。用 `[start,end)` 半开区间定义边界。查询与用户范围 `[qstart,qend)` 重叠的片段，条件为 `start < qend AND end > qstart`，避免边界重复。

```sql
CREATE TABLE recording_segment (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  channel_id VARCHAR(128) NOT NULL,
  start_utc_ms BIGINT NOT NULL,
  end_utc_ms BIGINT NOT NULL,
  object_key VARCHAR(512) NOT NULL,
  size_bytes BIGINT NOT NULL,
  status VARCHAR(16) NOT NULL,
  CHECK (end_utc_ms > start_utc_ms)
);
CREATE INDEX idx_recording_time
  ON recording_segment(tenant_id, channel_id, start_utc_ms);
```

以上是教学结构，数据库版本、约束执行和组合查询性能需实测。文件与数据库不在同一事务中，可用状态机：写临时片段 → 正确封口和刷写 → 同一文件系统改名 → 索引标记 ready。重启后扫描 pending、孤儿文件和缺失文件。原子改名仅约束特定文件系统操作，不能替代持久化与跨系统一致性设计；对象存储应使用其完成上传与可见性机制。

Seek 通常先定位片段，再回退到可解码随机访问点并向前解码到目标时间。“关键帧偏移表”不意味着对任意容器直接跳文件字节就能解码，还需要初始化数据、容器索引与参考状态。

**验收**：写入中结束进程、磁盘满、索引提交失败、文件缺失、删除中失败、时间跳变；恢复后不返回半截录像，孤儿文件有可追溯处理规则。

## 18. AI 分析旁路：丢哪一帧，为什么

实时观看和 AI 分析应有独立资源预算。通常先解码，再按时间/事件抽取图像做缩放、归一化和推理；直接从压缩包里随意丢 P/B 数据会破坏参考关系。只取关键帧也不等于任意包可当 JPEG 解码。

```text
媒体接入 → 实时分发 → 播放器
    ├──→ 录像写入 → 录像索引
    └──→ 解码/抽帧 → 有界图像队列 → 推理 → 规则/跟踪 → 告警事件
                         满时按策略丢弃       │
                                  事件 ID + 通道 + UTC + 模型版本
```

AI 队列要同时限制条目和字节；模型变慢时可以丢过时的已解码帧或降低抽样频率。录像分支的策略通常是保留数据并对过载告警，不能照抄 AI 丢最旧策略。

```powershell
python JD/media-learning/media_lab.py queue
```

本例每步生产一帧、每四步消费一帧，容量 3，消费 `[1,5,9]`，剩余 `[10,11]`，峰值始终 3。它是单线程离散模型，不是线程安全队列，不涉及真实视频解码；真实程序必须处理锁、所有权、停止和内存释放。

动态批处理要设置最大等待时间，避免单路被迫等待凑批。告警要有 event_id、规则版本、去重窗口与证据链接。模型输出不是业务事实，需评估漏报/误报、夜间、遮挡和异常数据；大模型摘要需链接原始证据与时间，避免把推测写成确定事件。

**验收**：故意让推理变慢，观看和录像指标不恶化；队列年龄受控；重复事件不重复触发业务动作；模型失败时标记不可用并保留可观测记录。

## 19. ASR/TTS 与实时语音：不是接一个模型接口

语音链路通常为采集 → 重采样/音频处理 → VAD/端点检测 → ASR → 业务或对话 → TTS → 播放。AEC 使用播放参考信号消除回声；降噪、自动增益和 VAD 解决不同问题。VAD 不是语音识别，也不保证一定识别出说话内容。

[whisper.cpp stream][S13] 明确是麦克风滑窗实时转写示例，依赖 SDL2 等采集环境，不能把重复滑窗推理直接等同于原生流式模型。[sherpa-onnx][S14] 提供流式/非流式 ASR、TTS、VAD 等入口；需要选择匹配的模型、token 文件、采样率和推理提供器。

分清 partial 与 final：partial 结果可能被改写，不能每次都直接追加进最终字幕。转写结果应携带会话 ID、片段 ID、时间范围、是否 final；重试不要导致重复落库。

**落地练习**：先用清晰的人声 WAV 做离线 ASR，测识别错误与耗时；再接麦克风并观察端点检测；最后实现 TTS 播放和打断。用户插话时取消旧生成、丢弃旧播放队列并关联新的 turn_id，防止过期回复继续播出。

指标应拆为首个 partial 延迟、final 延迟、TTS 首音延迟、打断生效时间和识别质量。RTF=处理耗时/音频时长，小于 1 只说明平均处理速度够快，不能保证交互首响足够快。

## 20. 平台架构：控制面与媒体面各负其责

```text
用户/前端
  → API 网关 → 身份/租户/权限 → 设备与会话服务 → 调度服务
                                  │              │
                            元数据库/状态缓存    │选择媒体节点
                                                 ↓
摄像头/推流端 → 媒体节点集群 → WebRTC/HLS/其他出口 → 播放端
                    ├──→ 录像服务 → 文件/对象存储 + 索引
                    └──→ AI 工作者 → 事件总线 → 告警/检索/通知

统一观测：trace/session/stream/channel ID、指标、结构化日志与审计
```

控制面处理鉴权、设备和会话生命周期，媒体面处理持续高吞吐数据。Java/Go 可负责 API、信令和调度，C++/成熟媒体服务器处理媒体。不要为了微服务把每个媒体包都放进普通消息队列；Kafka 等更适合事件、分析结果和业务异步处理，具体架构需成本与吞吐验证。

设备在线状态与真实媒体状态应分别建模。MySQL 存持久元数据，Redis 可存短期状态和限流信息，但不是媒体播放正确性的唯一依据。调度要考虑带宽、编码能力、会话数和回源亲和性，而不只是轮询节点。

迁移和高可用不能只讨论容器重启：媒体会话有状态，故障后需要重建推流/拉流、同步播放授权、处理录像缺口。公网部署还需考虑 WebRTC candidate 公告地址、UDP 端口、负载均衡方式与源站防护。

## 21. 安全与可观测性：能播放之后必须补齐

预览、回放、导出、PTZ 和对讲应分别授权，校验租户与通道归属。播放 URL 需有过期与范围限制，日志避免泄露设备密码和完整令牌。任意取流 URL 会带来 SSRF 风险，应校验协议、地址范围、解析结果与网络出口，避免用户借媒体服务访问内网敏感服务。

TURN 使用认证与配额，信令用 TLS，WebRTC 使用协商的安全传输；不能认为 HTTPS API 自动加密所有 RTSP/RTP。录像涉及隐私，需配置保留期、删除、导出审计与访问控制。FFmpeg 构建和各模型/权重的许可证也需独立核查。

| 用户症状 | 首先查看 | 下一步 |
|---|---|---|
| 一直黑屏 | 有无媒体字节、编码参数、关键帧 | 分离网络、解码、渲染故障 |
| 越播越延迟 | 队列年龄、播放器缓冲、处理速率 | 降负载并按码流规则追赶 |
| 只有声音 | 视频编码兼容、解码错误 | 检查 profile/level/像素格式 |
| 只有内网可播 | ICE/端口/公网候选/TURN | 跨网及强制 relay 验证 |
| 回放时间不准 | UTC 与媒体时间映射、关键帧定位 | 检查时间跳变和实际解码起点 |

核心指标：建连成功率、首帧 P50/P95、端到端延迟、卡顿比例、重连次数、输入输出码率、队列字节与年龄、录像缺口、AI 延迟、TURN 比例。不要给每个无限增长的 session_id 建指标标签，以免监控高基数失控；将其放日志和追踪。

## 22. 落地项目一：园区摄像头预览与录像平台

**需求**：先用 2—4 路授权测试摄像头，实现设备管理、预览、连续录像、按时间回放、离线提示。选择 MediaMTX/ZLMediaKit 等成熟服务作为媒体核心，业务层用熟悉的 Java/Go/Python。

**阶段一**：RTSP 拉流与本地播放，保存编码和设备能力报告。阶段二：浏览器观看与鉴权，验证不同浏览器编码支持。阶段三：切片、索引和回放，采用第 17 章恢复策略。阶段四：ONVIF 或 GB28181 接入、运维与容量报告。

API 最小集合可为 `POST /sessions`、`DELETE /sessions/{id}`、`GET /channels/{id}/recordings?from=&to=`，但播放地址由服务生成并受权限保护，不能让客户端自行拼接任意设备 URL。

**验收**：设备重启后可恢复；多观众共享上游，不为每人重复取流；删除录像后索引一致；磁盘满和节点重启有明确行为；交付架构、配置、抓包、故障记录与实际性能报告。

## 23. 落地项目二：低延迟远程巡检与对讲

**需求**：远程查看、双向语音、跨网络连接与操作审计。媒体层选 WebRTC，信令层实现会话与权限，配置可验证的 TURN 兜底。若需要多人观看，评估 SFU，避免让设备向每位观众独立上传。

**阶段一**：官方 WebRTC 双 peer 示例，看懂 SDP/ICE。阶段二：独立信令服务和跨机器通话。阶段三：公网、TURN relay、音频回声处理。阶段四：弱网与多观众测试。

**验收**：在写明网络条件下达到项目定义的延迟和成功率；断网重连不产生僵尸会话；结束通话释放摄像头和麦克风；撤销权限后不能继续新建媒体会话。应单独验证已有会话撤销机制。实时画面与控制操作关联，但不能把视频链路当作工业安全控制保障。

## 24. 落地项目三：视频 AI 告警与证据检索

**需求**：从授权视频中识别特定事件，保留事件前后证据，支持按通道和时间查询。先选一个可量化任务，如固定区域人员进入，再扩展多模态摘要。

**阶段一**：离线视频抽帧、推理、标注集评测。阶段二：旁路实时消费与有界队列。阶段三：跟踪、去重、告警规则、录像联动。阶段四：模型版本管理、回放复核与灰度发布。

证据前 N 秒可通过录像索引回取或短期环形缓存获得，但缓存边界必须能独立解码。告警发出时后 N 秒还没有发生，应有待完成状态，不返回不存在的完整证据。

**验收**：推理停止不拖慢观看与录像；统计误报与漏报；事件和证据匹配；重复投递不重复发通知；模型升级可回滚。大模型总结附证据时间范围，并把不确定性展示为待复核。

## 25. 落地项目四：会议转写与语音助手

**需求**：上传/采集音频、生成时间对齐转写、可选 TTS 回复与摘要。离线版本先不做实时对话，把音频格式、片段边界和最终结果做正确。

**阶段一**：WAV 检查、重采样、离线 ASR。阶段二：VAD 分段与字幕合并，区分 partial/final。阶段三：流式输入、取消、TTS 与打断。阶段四：摘要、证据定位、权限与删除。

**验收**：长静音、多人交叠、方言、噪声、设备断开有测试记录；客户端断连可取消任务；重试不重复字幕；摘要能定位原始音频。说话人分离与声纹识别是不同任务，不能把临时 speaker_1 直接当真实身份。

## 28. 实验验证边界与继续深入的方法

配套 Python 使用标准库，验证 PCM 数据量、精确时间基换算与 AI 图像队列过载策略。它没有实现 RTP、HLS 或 WebRTC，不代替真实媒体引擎。测试通过仅证明这些教学模型在所测条件下符合预期。

本机没有发现 ffmpeg/ffprobe 命令，文中的 FFmpeg、GStreamer、媒体服务器、浏览器跨网、摄像头、硬件加速和 ASR/TTS 模型实验未在此环境执行。运行时需安装对应工具、取得合法测试媒体和设备权限，按章节验收条件记录结果。

下一步学习不要从“抄一套平台”开始：先完成本地文件实验，再做单机网络闭环，最后选择一个落地项目。每遇到故障，沿输入数据、时间戳、缓冲、传输、解码和渲染逐层验证，逐步形成自己的诊断方法。
