## 2. 环境、解释器、虚拟环境与第一份作品

### 2.1 Python 程序怎样运行

以 CPython 为例，源码解析与编译后由解释器执行字节码，运行中可能生成缓存。Python 语言不等于只有 CPython 这一种实现，也不能简单理解成“每次逐行重新翻译”。

先确认 `python` 指向哪里，再安装依赖。`python -m pip` 比直接敲 `pip` 更容易对应当前解释器。

```powershell
python --version
python -c "import sys; print(sys.executable)"
Set-Location D:\project\001\biographical\JD\python-learning
python -m venv .venv
.\.venv\Scripts\python.exe -m unittest -v
.\.venv\Scripts\python.exe document_lab.py --help
.\.venv\Scripts\python.exe document_lab.py README.md --top 5
```

直接调用虚拟环境解释器，不需要改变 PowerShell 执行策略来激活脚本。此实验不需 pip 安装任何库。`.venv` 是本机生成目录，不应提交到 Git。

## 3. 基础语法、对象引用、集合和函数

参考 P1 的控制流程与数据结构教程。

### 3.1 从一个可直接执行的例子开始

保存为 `price_lab.py`，执行 `python price_lab.py`：

```python
def total(price_in_cents: int, quantity: int) -> int:
    if type(price_in_cents) is not int or type(quantity) is not int:
        raise TypeError("金额和数量必须是整数")
    if price_in_cents < 0 or not 1 <= quantity <= 1000:
        raise ValueError("金额或数量超出范围")
    return price_in_cents * quantity


if __name__ == "__main__":
    print(total(1990, 2))
```

Python 的 bool 是 int 的子类，此处用精确类型判断是为了教学规则拒绝 True/False；一般项目按接口契约选择验证方式。类型提示本身不执行运行时校验。

Python 整数不像固定宽度 int 那样自然溢出，但很大的整数仍消耗资源，外部数据库字段也有范围。金额用最小货币单位整数或按明确精度/舍入规则使用 Decimal，不能把二进制浮点的近似值当精确账目。

### 3.2 变量是名字，对象有可变性

```python
a = ["book"]
b = a
b.append("pen")
print(a)  # ['book', 'pen']
```

赋值没有复制列表。`a.copy()` 是浅复制，内部嵌套对象仍可能共享。`is` 判断对象身份，`==` 判断相等；判断空值常用 `value is None`，不要依赖小整数或字符串缓存来推断身份规则。

列表、字典、集合通常可变；字符串、整数、元组等对象本身不可变，但元组里可以放可变元素。

### 3.3 用合适的集合表达问题

| 类型 | 用途 | 注意 |
|---|---|---|
| list | 有顺序的元素 | 切片通常产生新列表，嵌套元素仍可共享 |
| tuple | 固定结构/不可变序列 | 不等于内部元素全部不可变 |
| dict | 按键查询、聚合 | key 必须可哈希；不能把字典当持久化数据库 |
| set | 去重与集合运算 | 进程内去重不能保证重启后的幂等 |
| Counter | 计数 | 本文词频实验使用，排序规则另行明确 |

理解 for、if、break、continue 后再学推导式。可读的一段循环通常比嵌套三层推导式更好维护。

### 3.4 函数参数最容易踩的坑

```python
# 不推荐：默认列表在函数定义时创建，不是每次调用创建。
def bad_add(item, result=[]):
    result.append(item)
    return result


def add(item, result=None):
    if result is None:
        result = []
    result.append(item)
    return result
```

`*args` 收集位置参数，`**kwargs` 收集关键字参数；`*` 后的普通参数可要求按关键字传入。配套 `bounded_map(..., *, limit=3, timeout=2.0)` 让并发和预算的调用更清楚。

函数里重新绑定名字和修改传入对象不同。不要把“Python 是按引用传递”当完整解释；观察共享对象与局部绑定更准确。

**练习**：给总价函数补货币字段与测试；对嵌套列表做浅复制，解释哪部分仍共享。

**验收**：能解释 None、真假值、相等/身份、默认可变参数与浅复制。

## 4. 类、类型提示、异常与资源管理

### 4.1 类把数据与规则组织在一起

配套 Report 使用 dataclass 自动生成构造、比较与展示方法。`frozen=True` 限制字段重新赋值，但其中的 list 仍可修改，因此是浅层冻结；若需要更严格不可变结果，应换成元组等结构并审视嵌套元素。

不要为了“面向对象”把每个函数都塞进只有静态方法的类。小工具可从函数开始，有状态与生命周期需求时再引入对象。

### 4.2 类型提示帮助工具发现问题

```python
from pathlib import Path

def load_text(path: Path) -> str:
    return path.read_text(encoding="utf-8")
```

这是片段，函数对大文件没有上限控制；配套实验采用有限读取。静态类型检查能发现许多不匹配，但不会自动验证用户输入或确保没有业务错误。Pydantic 在运行时提供另一层数据解析与验证，二者职责不同。

### 4.3 异常要保留因果关系

```python
try:
    raw = path.read_bytes()
except OSError as exc:
    raise RuntimeError("无法读取输入文档") from exc
```

通常只捕获你知道如何处理的异常。不要用空 `except:` 隐藏错误与退出信号；不要把完整堆栈、密钥、用户文档返回客户端。命令行层可把可预期错误转换为说明和退出码，核心函数仍抛出可测试异常。

### 4.4 with 与生命周期

`with` 确保离开作用域时按协议清理资源，异常路径也适用。`async with` 是异步资源管理协议，不表示内部一定无阻塞。文件、HTTP 客户端、数据库事务、临时文件和后台任务都需要明确“谁创建、谁关闭”。

**练习**：读取时故意触发编码错误；确认文件关闭、临时目录可清理，CLI 退出失败而非输出空成功。

**验收**：不会用类型提示代替验证，不会用 broad catch 把真实故障伪装为成功。

## 5. 模块、依赖、打包与测试

参考 P3～P7。

### 5.1 从脚本到包

模块是可导入的代码单元，包组织模块。`if __name__ == "__main__"` 让脚本直接运行时执行入口，被导入时不立即跑 CLI。

项目变大后可以组织为：

```text
pyproject.toml
src/document_service/
    analysis.py       核心规则
    cli.py            参数、输出与退出码
    api.py            HTTP 协议适配
    tasks.py          后台任务适配
tests/
```

核心逻辑不要导入 GUI 窗口或 FastAPI Request，否则很难被 CLI、测试和后台任务复用。

### 5.2 依赖与构建各管什么

pyproject.toml 可以声明构建后端、项目元数据、依赖和工具配置。wheel 是可安装分发格式，sdist 是源代码分发；包含原生扩展的 wheel 往往与平台、架构、Python ABI 有关，不保证一个文件装遍所有系统。

应用需固定解析结果并记录 Python 与平台；库通常声明合理兼容范围。uv 是可选工作流，学会 venv/pip 后再使用其锁定和同步能力，别在同一环境里无序交替多种工具。

### 5.3 测试先关注行为

配套实验用 unittest，不需要安装 pytest。正式项目可以迁移至 pytest，使用 fixture 管理临时文件与数据库，清理逻辑随测试生命周期执行。

本地必须检查的行为：正确统计、重复运行一致、缺文件、错误编码、大小上限、任务顺序、并发上限、一项失败时兄弟任务取消、超时后资源清理。

Ruff 负责部分规范和静态检查，formatter 负责格式；它们不能证明事务正确或模型准确。测试 mock 适合可控分支，真实依赖集成测试用于验证 SQL、队列和服务协议。

**练习**：暂时删除文件大小校验或超时清理代码，确认对应测试失败，再恢复。加入“空文件统计为零”的用例。

**验收**：新环境只按说明就能运行，不依赖 IDE 暗中加的路径；不提交虚拟环境、缓存或私有密钥。

## 6. 迭代器、生成器、数据处理与算法基础

### 6.1 能迭代不代表全部载入内存

迭代器逐项产生结果，生成器使用 yield 延迟计算。生成器通常消耗后不能从头重用，错误也可能直到迭代时才发生。

```python
def valid_lines(path):
    with path.open(encoding="utf-8") as stream:
        for number, line in enumerate(stream, start=1):
            text = line.strip()
            if text:
                yield number, text
```

调用者提前停止遍历时也要考虑资源关闭与生成器生命周期；对需要严格控制的管线可把资源打开范围放在调用侧。逐行读取仍可能遇到一条极长的行，服务端还需要总大小和单行限制。

### 6.2 算法复杂度先用于工程判断

逐条扫描所有商品去关联订单容易出现 O(n×m)，先建 SKU 字典再查询往往更合适。选择 Top K、去重、批量 join、游标分页和有限队列，比一开始刷全部高级算法更贴近这些岗位。

配套词频需要记录不同 token 的计数，内存随词汇数增长；“读取文件有限”不表示没有其他分配。排序是完整排序，大规模场景可考虑堆、分块、近似统计或数据库聚合，先测瓶颈再改。

### 6.3 数据管线要可追溯

记录输入哈希、编码、处理版本、参数、行数、失败样本和输出位置。坏数据不能无声跳过，应有数量、原因和重处理策略。JSON/CSV 解析还需注意字段类型、分隔符、日期时区与小数格式。

**练习**：写逐行 CSV 聚合，限定输入大小；输出总行数、有效行数和无效行原因，验证三者可核对。

**验收**：能说明内存与时间复杂度，知道生成器不等于自动有界的整个系统。

## 7. 并发原理：线程、进程、协程与取消

参考 P1、P8、P10。

### 7.1 先判断工作在等什么

| 工作类型 | 常见起点 | 重要边界 |
|---|---|---|
| 外部 HTTP/数据库等待 | 支持异步的客户端或受控线程 | 依赖连接和配额有限 |
| 纯 Python CPU 计算 | 进程、任务 worker 或算法优化 | 序列化、启动与内存复制成本 |
| NumPy/推理等原生计算 | 测量实际库线程与 GIL 行为 | 多进程叠加原生线程可能过度订阅 |
| 高并发 I/O 协作 | asyncio | 任意同步阻塞都可能拖慢事件循环 |
| GPU 推理 | 独立模型进程/批处理 | 显存、排队与批大小限制 |

本机使用常规 CPython 3.11，其 GIL 限制同一解释器中同时执行 Python 字节码的线程，不代表所有 I/O 和原生库都不能并行。较新版本还存在可选 free-threaded 构建，行为和扩展兼容需按构建核对，不能用一句“Python 永远只能单线程”概括。

### 7.2 async def 不会把同步代码变异步

协程函数调用后产生协程对象，需 await 或调度才执行。事件循环在可让出的位置调度任务；`time.sleep`、同步 requests、CPU 长循环不会因放进 async def 就自动让出。

```python
# 可放进 async 函数中使用的片段
await asyncio.sleep(0.1)                # 让出，不是 time.sleep
result = await asyncio.to_thread(fn)    # 隔离某些同步阻塞
```

to_thread 不会让一般纯 Python CPU 计算自动获得多核收益，取消等待也不保证底层线程立即停止。对外部 HTTP 仍需真实连接/读写超时。

### 7.3 有界并发要限制哪几层

Semaphore 限制同时进入的操作，但若先创建一百万个任务，仍会占大量内存。配套函数只允许最多 100 项、最多 100 并发；大量/无限输入应使用有限队列与固定 worker，而非无上限 create_task。

连接池、任务池、排队长度、上传大小和租户配额各有边界。API worker 数乘以每 worker 并发/模型内存，可能把数据库或 GPU 压垮。

### 7.4 TaskGroup、超时和异常

Python 3.11 的 TaskGroup 在子任务失败时取消其他子任务并等待结束，可能汇总为 ExceptionGroup。配套实验验证失败后 finally 清理已执行。

asyncio.timeout 限制作用域预算，但取消是协作式的；被阻塞的事件循环或不响应取消的任务可能无法按时结束。finally 用于清理，通常不应吞掉 CancelledError；timeout 也不会回滚已完成的远程写入。

### 7.5 实际操作

运行 `python -B -m unittest -v`，重点看失败取消和超时用例。测试使用事件协调失败窗口，而不是只用“睡一秒大概完成了”判断并发正确。

**练习**：在 fetch 中加入同步 time.sleep，观察为什么事件循环变迟钝；恢复后为连接失败和用户主动取消补清理测试。

**验收**：能区别限等待与停止执行，知道“一个信号量”不等于整个系统容量可控。

## 8. HTTP、FastAPI、Pydantic 与接口设计

参考 P8～P10。下面是需要第三方依赖的独立实验，**不属于已经验证的标准库配套程序**。

### 8.1 一个最小服务

另建虚拟环境，安装 FastAPI 标准附加依赖，保存为 `app.py`：

```powershell
python -m pip install 'fastapi[standard]'
```

```python
from typing import Annotated
from fastapi import FastAPI
from pydantic import BaseModel, Field, ConfigDict

app = FastAPI()


class AnalyzeRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    text: Annotated[str, Field(min_length=1, max_length=10000)]


@app.post("/analyze")
def analyze_text(body: AnalyzeRequest):
    return {"characters": len(body.text)}
```

这是 Pydantic v2 风格。执行 `python -m uvicorn app:app --host 127.0.0.1 --port 8000`，访问 `/docs`。学习环境首次安装后记录实际版本并锁定，后续复现不能无限追随最新版。

字段字符上限不等于整个 HTTP 请求字节上限，应在代理/服务器/入口另设限制。简单 CPU 操作用普通函数即可；不要为了看起来先进把所有函数写成 async。

### 8.2 def 与 async def 的调度边界

FastAPI 对普通同步路由/依赖有相应线程池执行机制，但路由里自行调用的普通辅助函数不会自动被转移到线程池。async 路由直接调用同步重任务仍会阻塞当前事件循环。

Pydantic 的默认行为可能进行类型转换；若业务需要严格类型，显式选择 strict 或约束。解析成功不意味着用户有权限，也不意味着 SKU 存在。

### 8.3 HTTP 客户端生命周期

在应用生命周期中复用 AsyncClient，配置超时与连接限制，退出时关闭。不要在热循环里不断创建客户端。检查状态码、业务码、响应大小与格式，异步流式响应也需按协议关闭。

### 8.4 长任务接口不要假装立即完成

`POST /jobs` 返回任务 ID 和接收状态；`GET /jobs/{id}` 查询状态；结果通过受控下载接口获取。可用 202 表达已接收未完成，重试要绑定可信用户/租户和幂等键。

BackgroundTasks 是请求进程内后处理机制，不是可靠持久化队列。若任务必须在崩溃后继续，应先持久记录接收状态，再由 worker 执行。

**练习**：验证非法输入、未知字段、重复提交、越权查询、依赖超时和请求体超限；用 HTTP 测试而非只手点 Swagger。

**验收**：能区分收到请求、创建任务、完成计算和交付结果四个阶段。

## 9. SQLAlchemy、事务、索引与缓存

参考 P11。先理解 SQL 与数据库约束，再学习 ORM。

### 9.1 最小数据模型

任务表至少包含 jobId、tenantId、幂等键、规范化请求哈希、状态、输入引用、输出引用、处理版本、创建/更新时间。用数据库唯一约束保护“同租户同操作幂等键”，不要只在 Python 中先查再插。

请求 JSON 的字段顺序和空白可能不同，幂等比较应基于规范化业务输入；同键不同内容要冲突，不能无声复用错误结果。

### 9.2 Session 是工作单元，不是全局共享字典

一个事务/请求/后台任务有明确 Session 生命周期。SQLAlchemy Session 不应用作多线程共享的可变全局对象；AsyncSession 也不应被多个并发任务随意共用。

```python
# 设计片段：Session 与 Job 需在项目中配置/定义。
with Session(engine) as session:
    with session.begin():
        session.add(job)
        session.add(outbox_event)
```

事务提交与回滚发生在约定范围。不要把整个远程模型推理耗时都包进数据库事务占用连接；先提交任务状态，计算完成后短事务写结果，并处理期间的版本/状态变化。

### 9.3 查询与连接池

通过实际 SQL 和执行计划优化，警惕 ORM N+1、大偏移分页、宽表与大量回传。索引提升特定查询，也增加写与空间成本。连接池总预算应乘应用实例数，不能每个实例都设成数据库最大连接数。

SQLite 适合本地工具与一些轻量需求，不能用其测试结果证明 PostgreSQL/MySQL 的并发锁语义一致。

### 9.4 Redis 是额外副本与资源

缓存命中提高读取效率，未命中回源并设置 TTL；写库和失效缓存间仍存在失败窗口。失效事件、版本与重试需按一致性要求设计。

Redis 锁有租约、暂停和网络边界；看门狗也不是任意场景的强一致保障。业务关键正确性优先用数据库唯一约束、条件更新和幂等记录维护。

**练习**：并发创建相同任务，模拟提交失败和 Redis 不可用；证明没有重复有效任务，失败后可重试。

**验收**：能解释事务边界、唯一约束、缓存新鲜度与多副本连接总量。

## 10. Celery、可靠任务、幂等与调度

参考 P12，特别是任务幂等、acks_late 与重试说明。

### 10.1 后台任务解决的不只是“异步跑”

任务长、需要重试、需要隔离 CPU/GPU 资源或需在 Web 重启后恢复时，适合独立 worker。任务消息建议传 jobId 和输入引用，不把巨大文件或敏感文档塞进消息体。

数据库提交成功但 publish 前崩溃会丢消息；先 publish 后提交可能处理不存在/回滚的记录。Outbox 把业务记录与待发事件放同一事务，再由独立发送者投递，消费者仍需处理重复。

### 10.2 确认不等于业务一定只做一次

早确认可能让崩溃任务不再重投；延迟确认可能让已执行但未确认的任务重复运行。具体崩溃和 worker lost 的重投还受 Celery 配置、broker 与版本影响。不能只设置 acks_late 就宣称零丢失、零重复。

worker 原子领取任务，检测处理版本；临时结果写入后，再以条件更新确认结果属于当前有效执行。外部写入使用业务幂等键，不靠“任务 ID 不重复”推导副作用不重复。

### 10.3 重试与调度分开设计

暂时网络错误可有限退避重试；格式不合法不应一直重试；失败超过阈值需人工处理与受控重放。记录 attempt、nextRetryAt、errorCode、输入/处理版本。

调度器负责什么时候触发，worker 负责执行；多实例 scheduler 可能重复触发，仍需领取与幂等。长时任务还要定义心跳、租约、失联后的恢复和结果未知。

强制时间限制/进程终止可能打断清理，不能替代依赖超时。取消已排队、取消正在执行、撤销业务副作用是三个不同动作。

**练习**：在输出写好后、任务确认前终止 worker；恢复后重复消费不产生两份有效结果或重复收费。

**验收**：用故障窗口表说明哪里会重投、怎么去重、什么情况需要查询外部真实结果。

## 11. NumPy、Pandas 与数据质量

参考 P13～P15。

### 11.1 数组原理决定性能

NumPy 的数组包含形状、dtype、步长等信息，许多运算在原生实现中执行。向量化通常减少 Python 层循环开销，但仍可能产生大中间数组，广播也可能放大内存需求。基本切片常是视图，进阶索引常返回副本，需按具体操作核对。

dtype 决定范围、精度和内存，不能为了省内存把所有 float64 直接降成 float32，金额和高精度计算需要业务验证。

### 11.2 Pandas 先关注正确性

```python
# 需要 pandas；订单 CSV 应事先约定列与编码。
df = pd.read_csv("orders.csv", dtype={"sku": "string"})
df["quantity"] = pd.to_numeric(df["quantity"], errors="raise")
summary = df.groupby("sku", dropna=False)["quantity"].sum()
```

缺少导入与输入数据时这是片段。生产处理中还要验证必需列、重复主键、负值、单位、日期时区与总量核对。`errors='coerce'` 会把异常转成缺失，必须统计，不能静默当作正常零值。

链式赋值与 Copy-on-Write 的行为随 Pandas 版本演进；优先使用明确 `.loc[...] = ...` 并阅读所用版本文档，而非背诵“所有切片一定是副本”。

本次读取的 Pandas 主分支文档明确指出：3.0 起 Copy-on-Write 为默认行为，链式索引赋值不能用来更新原对象。使用旧版本时也应避免依赖含糊的视图/副本行为。

### 11.3 大数据不是一个 read_csv 参数就解决

chunksize 可以分块读取，但后续把所有块 concat 回去仍会吃完整内存。聚合状态、join 与排序也要有预算，必要时使用数据库/列式工具或外部排序。

### 11.4 数据泄漏比模型选择更先检查

训练/验证/测试先分开，再只用训练集拟合标准化、缺失填补与特征选择。时间序列按时间与信息可用性划分，重复实体可能需要分组拆分。Pipeline 有助于把预处理和模型绑定，不能自动修复错误切分。

**练习**：构造缺失、重复、非法日期和单位不一致数据，输出质量报告；检查清洗前后数量是否守恒或有明确原因。

**验收**：能证明结果正确与可追溯，再讨论向量化快了多少。

## 12. 机器学习、PyTorch、推理服务与 MLOps

参考 P15～P18。

### 12.1 先做可解释基线

以工单分类为例，先定义类别、人工标注标准和数据划分，再做多数类/规则/线性模型基线。用每类 precision、recall、混淆矩阵与误判样例评估，不只看总体准确率。

数据版本、划分、随机种子、特征处理和训练参数都要记录。固定种子有助复现，不保证所有硬件、库与算子上逐位一致。

### 12.2 PyTorch 学习顺序

Tensor 与形状 → Dataset/DataLoader → 模型前向 → loss → autograd → optimizer → 训练循环 → 独立验证 → 保存和加载。P16 basics 按这些步骤组织，先跑官方小数据例子，不从大模型训练开始。

训练与推理模式不同：`model.eval()` 改变 Dropout/BatchNorm 等行为，`torch.no_grad()` / inference_mode 影响梯度记录等；一个不自动替代另一个。输入归一化、标签映射与 tokenizer 等预处理应随模型发布。

### 12.3 推理服务架构

API 校验/鉴权 → 有界任务队列 → 已加载模型的 worker → 结果校验 → 输出与指标。模型在合适的生命周期加载，不要每个请求从磁盘重新加载。

多个 Web worker 可能复制多份模型占用显存/内存；预处理线程、BLAS 线程、多进程会叠加。批处理可提升吞吐但增加等待，动态 batching 需结合延迟目标与输入形状。

### 12.4 ONNX 与加速需要数值验证

导出成功不代表所有形状/算子都被目标执行提供程序支持。比较原始与目标运行时的输出、误差、任务指标、冷启动、延迟和内存。量化同样需要代表性校准与质量回归，不能只报模型变小。

### 12.5 MLOps 的最小记录

代码 commit、数据集与划分、依赖环境、训练参数、权重、预处理、指标、阈值和已知限制。MLflow 等工具帮助追踪，但权限、数据来源和发布审批仍需项目设计。

发布后观察输入分布、业务效果、超时和资源，不把“API 活着”当模型质量正常。灰度与回滚要覆盖模型和预处理的兼容组合。

**练习**：先做 CPU 基线分类 API；测试无效输入、模型加载失败、低置信度、批量上限及版本回滚。

**验收**：模型准确性和服务可靠性分别有测试，不能用单个成功请求代替评估。

## 13. RAG、Agent、SSE 与文档助手

本节承接主线工程能力。可结合 [AI 方向资料](./01-AI大模型应用工程.md) 深入，先用模拟模型验证系统，再连接真实模型。

### 13.1 RAG 每一步都可能失真

上传 → 解析/OCR → 清洗 → 带来源的分块 → embedding → 索引 → 受权限限制的检索 → 重排 → 带引用回答。

保存 sourceId、文档版本、页码/段落、解析版本、chunkId 与索引版本。检索必须限制可信租户/用户可见范围，不能先取所有秘密文档再指望提示词阻止泄露。

文档哈希用于识别内容，不自动替代权限与业务去重策略。更换 embedding 模型可能改变维度与向量空间，需要版本化索引和重新验证。

### 13.2 Agent 是受控工具循环

读取用户目标 → 选择允许工具 → 验证参数与身份 → 执行 → 记录结果 → 决定结束/继续。设置轮数、时间、费用与并发预算；模型产出的“工具调用”不是直接执行任意 Python 代码的授权。

先提供只读工具，例如搜索已授权文档、按固定公式计算指标；写操作经过确定性业务规则与必要确认。工具结果也可能不可信，要验证格式、大小和来源。

### 13.3 SSE 与取消

SSE 使用 text/event-stream，事件以空行分隔；需要适当刷新、代理缓冲配置和心跳。响应头已发送后，不能把中途错误可靠改成 HTTP 500，应定义 error/done 事件并让客户端检查终止状态。

客户端断开后清理任务和上游连接；取消等待不一定停止上游计费/计算，需核对模型客户端行为。后台持久任务与当前连接不是同一生命周期，断开是否取消任务应明确约定。

### 13.4 怎么证明比普通搜索更有用

构建包含可回答、缺证据、跨版本、数字计算、越权、提示注入等样例的评估集。分别测检索覆盖、引用正确性、回答依据、拒答、延迟和费用，不只打一个“综合分”。

**练习**：先用固定模拟答案做一条文档检索链，记录引用；再更换真实模型，比较是否引入无证据结论。

**验收**：用户能回到原文，缺少证据会说明不足，模型不能绕过权限或直接修改业务数据。

## 14. CLI、桌面应用与跨平台交付

参考 P21、P22；对照原文跨平台应用场景。

### 14.1 一套核心，多种入口

核心 analyze 返回数据或抛异常，CLI 解析参数、格式化结果；GUI 显示进度与错误；API 做协议与身份校验。不要让核心函数依赖弹窗、控制台输入或全局 Web 上下文。

argparse 是标准库且足够完成首个工具，Typer 可改善类型化参数、帮助与子命令。无论选哪种，都约定参数、覆盖输出策略、退出码、日志与机器可读模式。

### 14.2 GUI 的响应性与生命周期

UI 线程只做交互，耗时 I/O/计算转交受控后台任务；结果通过框架支持的信号/事件回到界面线程。显示“取消中”不等于后台已终止，必须收到结果或确认资源清理。

保存文件前避免覆盖用户数据，临时文件失败可清理，配置目录采用目标平台约定，不写死开发机绝对路径。

### 14.3 打包不是跨平台编译魔法

PyInstaller 通常需要在目标操作系统上构建对应产物；原生依赖、架构、动态库、资源文件和签名会影响运行。onefile 会有解包与启动行为，不表示源码绝对不可提取，也不等于只有一个文件需要维护。

只在开发机运行成功不够：Windows/macOS/Linux 分别在干净环境测试安装、启动、读写权限、中文路径、离线条件、卸载和日志位置。macOS 签名/公证、Windows 签名等按交付需求处理。

**练习**：把配套 CLI 打包为目标系统程序，在没有开发环境的测试机运行；保存版本、构建日志与验收记录。

**验收**：核心结果与源码运行一致，错误可诊断，配置与用户文件不因升级丢失。

## 15. 性能分析、观测、容器与发布

### 15.1 先定位 CPU、内存还是等待

```powershell
python -B -m cProfile -o profile.out document_lab.py README.md
python -c "import pstats; pstats.Stats('profile.out').sort_stats('cumulative').print_stats(15)"
```

这是小输入练习，不代表完整服务压测。cProfile 有测量开销；原生/GPU 工作与异步等待还需合适工具和依赖指标。tracemalloc 能观察部分 Python 内存分配，不代表进程所有 native/GPU 内存。

### 15.2 最小观测集

请求数、错误率、延迟分布、事件循环延迟、活动任务、队列长度与最老任务年龄、拒绝数、连接池等待、模型版本/耗时、CPU/RSS/GPU。日志用 requestId/jobId 关联，但不要把无限 jobId 作为指标标签。

在异常日志中保留必要错误上下文，避免保存完整私密文档、访问令牌和无上限模型输入输出。

### 15.3 部署与容量预算

一个进程的全局对象只在该进程内共享，多 worker 会复制缓存、连接池与模型。总连接、模型占用与后台线程要乘副本和 worker 数。

依赖固定、镜像可追溯、非 root、秘密外置、健康检查与就绪判断分开。单机容器可以是合理起点；只有明确扩容与运维需要时再引入 K8s。

### 15.4 退出与回滚

撤流 → 不再领取新任务 → 等在途任务或按策略取消 → 保留可恢复状态 → 关闭客户端、池和文件 → 退出。数据库不可用不应盲目通过活性探针重启全部副本。

发布流水线覆盖静态检查、测试、必要集成、构建、部署、冒烟和指标观察。数据库与模型/索引版本兼容要先规划，代码回滚不能自动撤销破坏性的迁移。

**练习**：让 HTTP 依赖变慢、取消连接、重启 worker；观察队列、内存与错误恢复，而不是只看服务是否启动。

**验收**：性能报告记录环境、数据、负载、持续时间、错误率、P95/P99 和正确性结果。

## 16. 落地项目一：可恢复的文档处理平台

### 16.1 阶段交付

| 阶段 | 新增内容 | 验收 |
|---|---|---|
| V0 | 已提供的标准库文本 CLI | 正确统计、错误输入、取消清理测试 |
| V1 | 包组织、pytest、HTTP API | 相同核心可由 CLI/API 调用 |
| V2 | SQL 任务、对象存储引用、幂等 | 重复提交不重复产生有效任务 |
| V3 | Outbox、Celery、有限 worker | 崩溃恢复、重复消费和重试 |
| V4 | 文档解析、OCR 或分类模型 | 质量集、失败样本与版本记录 |
| V5 | RAG、引用与流式交互 | 权限隔离、缺证据拒答、中断清理 |
| V6 | 容器、观测与交付 | 新环境复现、退出与回滚 |

只有 V0 是本次已交付并测试的代码，V1～V6 是逐步实现的项目任务。PDF/OCR 等不是本地 .md/.txt 统计器已经支持的功能。

### 16.2 最小状态机

received → queued → running → succeeded / failed；取消可区分 cancel_requested 与 cancelled。状态附处理版本和执行尝试，旧 worker 不能在新任务已取消/重跑后覆盖有效结果。

输入保存到受控存储，数据库只存引用和元数据。输出先写临时位置，验证完整后发布引用；清理孤立临时文件需要后台维护。

### 16.3 故障矩阵

| 注入故障 | 预期 |
|---|---|
| 文件错误编码/超限 | 明确拒绝，不占用模型任务 |
| 同键同请求重复 100 次 | 同一逻辑任务与明确状态 |
| 同键不同文档 | 冲突，不返回另一份报告 |
| worker 计算后确认前退出 | 允许重投，只有一个有效结果 |
| 模型输出非法格式 | 标记失败/需重试，不能伪造成功 |
| 用户断开或取消 | 按约定保留/停止任务并释放资源 |
| 越权 jobId/文档引用 | 拒绝访问，后台任务也不绕过租户边界 |

**交付**：源码、依赖、迁移、模拟器、测试数据、接口/事件契约、结果样例、观测与恢复手册。

## 17. 落地项目二：ERP / WMS 数据集成与报表

对应订单、库存、供应链、财务与 BI 场景。先用两个模拟 HTTP 系统，不需要接真实企业账号即可验证流程。

### 17.1 一条业务链

外部销售单接收 → 原始记录 Inbox → 字段/单位规范化 → 本地订单入库 → 库存/出库结果回传 → 差异对账 → 报表。

定义外部单号与本地单号、租户、版本、业务时间、商品编码、币种和计量单位。不能仅用商品名称 join，也不能把件、箱和公斤无条件相加。

### 17.2 同步与重放

每个供应商适配器处理鉴权、分页、业务码与字段。限制每租户并发和配额；使用稳定游标或带回看窗口的增量方案，处理迟到更新。返回 200 但业务错误码不成功时，仍需记录失败。

重放入口按范围、版本与原因审计；同一外部单不能重复出库或重复记账。对账输出缺单、状态不一致、数量/金额差异和无法匹配项。

### 17.3 报表校验

抽样核对与总量平衡：输入多少、去重多少、无效多少、入库多少；金额、数量按币种/单位分组。Pandas 只是工具，正确性依赖数据契约与校验。

**验收**：模拟重复推送、乱序更新、配额限制、数据库回滚、回传超时与断点重启，给出可追踪差异和修复结果。

## 18. 落地项目三：可追溯的财报研究助手

对应原文投研专题。目标是“事实与计算可核验”，先不做自动交易和收益优化。

### 18.1 数据时间与版本

财报期末日期不等于信息公开日期，更不等于当时系统已经获取。至少区分报告期、公告时间、抓取时间、修订版本和当时可用时间。历史研究必须只使用当时可获得的信息，不能把未来修订数据放进过去。

### 18.2 三层输出

原文事实附页码/段落；计算结果附输入数、单位和公式；模型推断明确标识依据和不确定性。一个数字不能只有模糊引用，表格跨页、单位“元/万元”、合并/母公司口径需要解析和核对。

### 18.3 回测与基线

先用简单规则/线性基线，按时间滚动验证，考虑训练窗口、标签跨度、交易成本、滑点、停牌与幸存者偏差等适用因素。评估多次调参造成的选择偏差，保留独立测试期。

Qlib 提供研究基础设施，不能替代数据许可、时点正确性、现实交易约束和人工审查。历史表现不构成未来结果保证。

### 18.4 项目边界

先收集有权使用的少量公开报告，做文本和表格引用检索、确定性指标计算、证据不足回答和版本对比。引用评估与数字复算通过后，再考虑训练领域模型。

**验收**：旧时点查询不读未来数据，指标可手工复算，无证据问题不编造，报告与数据版本可复现。

## 19. 微调、偏好优化与强化学习入门

参考 P19、P20，先完成第 12 章基线和评估。

### 19.1 不同方法改变不同部分

提示词改变输入与指令；RAG 提供外部证据；微调改变模型参数。知识频繁更新且要求出处时，微调不天然替代检索；格式/任务适配也应先评估较便宜的提示与程序方案。

LoRA 通过低秩适配减少部分可训练参数，仍需加载基础模型并占显存。量化微调的精度、算子与硬件要求需要实际兼容验证，不要从一个“低显存”标题推断任意机器能训练。

### 19.2 训练流程

任务定义 → 数据授权与去重 → 训练/验证/测试隔离 → 基线 → 小规模训练 → 独立评估 → 风险与性能回归 → 权重/适配器与预处理一起版本化 → 灰度。

数据格式、tokenizer、截断、padding、loss mask、模板和最大长度都会影响结果。训练 loss 下降不证明业务更准确，也不证明不会遗忘其他能力。

### 19.3 SFT、DPO 与 PPO

SFT 用示范输入输出学习任务；偏好数据比较多个回答；DPO 等方法使用偏好对优化，不应简单等同于“跑一个在线环境强化学习”。PPO 通常涉及策略、奖励、采样与稳定性等复杂工程。

奖励可能被模型钻空子；自评分不等于客观事实正确。金融序列决策还涉及状态、动作、交易成本、非平稳和风险约束，不能从“能训练”跳到“可上线交易”。

**练习**：只在小型、可承受资源的数据集上比较提示词基线和 SFT，固定测试集与费用预算，展示错误样例而非仅展示漂亮回答。

**验收**：能说明训练改变了什么、没有证明什么、如何回滚以及为什么值得增加训练成本。

### 20.2 容易误解的说法

| 简化说法 | 更准确的边界 |
|---|---|
| Python 一行一行直接执行源码 | 需区分语言、实现与字节码执行 |
| 有类型提示就不会传错类型 | 提示本身不做运行时验证 |
| dataclass frozen 是深不可变 | 内部可变对象仍可能改变 |
| GIL 让所有线程完全不能并行 | 取决于实现/构建、I/O 和原生扩展 |
| async def 里面都异步 | 同步阻塞仍阻塞事件循环 |
| to_thread 能随取消立即停止 | 线程执行可能继续，需设计其生命周期 |
| 信号量让所有任务内存有界 | 任务创建数和等待队列也需限制 |
| 超时说明外部写入失败 | 可能只是没有等到结果，需幂等与查询 |
| BackgroundTasks 是可靠队列 | 请求进程崩溃后不保证恢复 |
| acks_late 实现精确一次 | 仍有重投、配置与业务幂等边界 |
| ORM 让事务自动正确 | 约束、隔离、并发与资源范围仍需设计 |
| Pandas 所有切片一定是副本 | 版本、索引方式和 Copy-on-Write 影响行为 |
| eval() 自动关闭梯度 | 模式与梯度记录是不同概念 |
| 多 worker 必然提高模型吞吐 | 可能复制模型并耗尽显存/内存 |
| 打成 exe 就能跨所有系统 | 目标平台和原生依赖仍需分别构建测试 |
| 微调 loss 下降就是业务变好 | 需要独立评估、回归、成本与风险验证 |

### 20.3 毕业验收

交付源码、依赖与环境、示例输入输出、正常与失败测试、数据/模型/索引版本、接口与事件契约、性能报告、恢复步骤和已知限制。

至少能演示：重复提交不重复副作用；超时后没有失控任务；坏数据有去处；引用能回到原文；权限无法被猜 ID 绕过；worker 重启后任务可恢复；发布失败可回滚。

回到 [原岗位文档](./04-Python工程化与算法服务.md)，把技术名词逐个转换成“我能解释的原理、能运行的代码、能证明的业务结果”。
